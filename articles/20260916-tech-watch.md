#### AIが書きました🤖

この記事は、AIが書いたものを人間が確認してから投稿しています。

**L**: 今日の新着は一件だけ。ただし問いはかなり根本的だ。同じ仕事を同じエージェントに繰り返し頼んだとき、毎回成功するのか。平均点では見えない運用上の揺らぎを、どう測って減らすかを考えたい。

## 今日の 1 件

1. **Your Agent Aced the Task. Will It Do It Again?**
   ALTK-Evolve は、エージェントが同じ課題を繰り返し成功できるかを Pass^k で測り、不安定な判断点から再利用可能な指針を生成する仕組みを追加した。AppWorld では、平均成功率を落とさずに一貫性の差を 24.4 ポイントから 12.0 ポイントへ縮めている。
   https://huggingface.co/blog/ibm-research/altk-evolve-consistency

## 平均成功率の裏にある揺らぎ

**L**: そもそも、成功率が 77.4% なら十分に評価できているのでは？

**A**: まず数字をそのまま並べると、違いが見えます。GPT-4.1 を使う ReAct エージェントを AppWorld の各課題で五回ずつ動かしたとき、全試行を平均した成功率、つまり Mean@5 は 77.4% でした。一方、五回すべてに成功した課題の割合である Pass^5 は 53.0% です。差は 24.4 ポイントある。

| 指標 | 問うこと | 結果 |
|---|---|---:|
| Mean@5 | 全試行を平均すると、どれだけ成功したか | 77.4% |
| Pass^5 | 五回とも成功した課題は、どれだけあるか | 53.0% |
| 一貫性の差 | 平均成功率と反復成功率の隔たり | 24.4ポイント |

**A**: これは同じ能力を別の表現で示しただけではありません。平均値は「たいてい成功する」を測り、Pass^k は「同じ依頼をしても毎回成功する」を測る。検証して再試行できるプログラム生成なら、一回でも成功すればよい Pass@k が重要な場面もあります。でも、契約書の義務を確認する、取引を照合する、社内手続きを実行するといった仕事では、前回うまくいったこと自体が次回の保証にはならない。

**L**: デモでは動いたのに本番で外れる。『ブレードランナー』のレプリカント検査のように、一度の応答で正体を決める方が危ういのかもしれない。

**A**: そうですね。ただ、ここで神秘的な説明は要りません。評価単位が一回の試行になっていた、それだけです。能力の問題として見えていたものを、反復可能性の問題として切り分けた。私はこれを **平均性能から運用品質へ** の移動だと見ています。

## どの判断が反転するのか

**L**: 同じ入力、温度ゼロでも、なぜ経路が変わる？

**A**: 記事の説明で重要なのは、判断ごとの確率分布の形です。ある道具を呼ぶか、引数に何を渡すか、失敗後に再試行するか。候補の一つに確率が集中していれば、わずかな数値差では順位が変わりません。複数の候補がほぼ並んでいれば、計算機上の丸め、要求の束ね方、提供基盤の差のような小さな変化で選択が反転する。

**A**: そしてエージェントの実行経路は、そうした判断を何十段も連結します。一段ごとの反転確率が小さくても、連鎖全体ではどこかが変わる可能性が積み上がる。いや、「モデルが気まぐれ」という言い方では粗すぎます。正確には、結果を左右する平坦な判断点が経路の中に残っている。

> Pass^k is not Pass@k.

出典: IBM Research / Hugging Face（訳: Pass^k は Pass@k ではない）

**L**: 固定した乱数種や貪欲法では止められない？

**A**: それらは確率分布からトークンをどう選ぶかを制御しますが、提供基盤で確率分布そのものが少し動くことまでは止めません。この実験も温度は 0.0 です。だから対策は、乱数をさらに縛ることではなく、反転しやすい判断点を見つけ、その場で選択基準を明確にする方向になります。

## 一つの実行履歴から指針を作る

**L**: 不安定な箇所を見つけるには、課題全体を何度も実行する必要がある？

**A**: そこが仕組みとして美しいところです。Consistency Analyzer は、記録済みの一つの実行履歴を使います。各判断点の直前までの文脈を再生し、その判断だけについて既定では五つの応答候補を一回のモデル呼び出しで生成する。外部の道具や環境はもう一度動かしません。正解ラベルも不要です。

```text
記録済みの実行履歴
  → 判断点ごとに候補を再標本化
  → 出力が割れる箇所を特定
  → 選択基準を指針として生成
  → 保存・検索し、次回の推論時に注入
```

**A**: 入力は過去の実行履歴、出力は判断点ごとの一貫性得点です。得点が低い箇所から、ALTK-Evolve が再利用可能な指針を作ります。記事に出てくる例では、チェック欄の印を数えるときに単純な部分文字列の個数ではなく行頭に固定した正規表現を使うこと、ノート検索で複数候補を確認してから対象を選ぶことが指針になった。

**L**: 失敗事例を覚えるのとは違う？

**A**: 少し違います。実際に失敗した箇所だけを直すのではなく、今回は偶然正しく進んだが次回は反転し得る箇所も拾う。これは **失敗後の修正から不安定性の予防へ** という設計です。エージェント自身の実行履歴を検索可能な手順書に変える点では、社内ナレッジのスキル化にも近い。ただし、会話をそのまま保存するのではなく、判断基準まで圧縮しているところが重要です。

## 指針をハーネスに組み込む

**L**: 生成した指針は、どこに置けば運用に使える？

**A**: 記事の仕組みでは、指針を保存し、次回の推論時に関連するものを検索して文脈へ入れます。社内のエージェントなら、役割を三層に分けると考えやすい。個々の仕事に固有の事実は業務データに置く。複数の仕事で再利用できる判断基準はスキルや手順書に置く。すべての実行で守る停止条件や権限境界はハーネスに置く。今回の指針は中央の層です。

**L**: すべてを恒久的な手順にすると、古い判断が積み上がらない？

**A**: そこは未解決の運用問題です。指針の追加には、少なくとも由来となった実行履歴、対象となる判断、改善を確認した評価、失効条件を持たせたい。検索で選ばれた回数だけでなく、その指針を入れたときと外したときの成功率も比べる。効果が確認できない指針は保留し、矛盾する指針は人に戻す。文章を増やすこと自体は改善ではありません。文脈が長くなれば、別の判断を不安定にする可能性もあります。

:::message
ALTK-Evolve の実験は、指針を加えても平均成功率が低下しなかったことを確認しています。ただし、指針を長期間蓄積した場合の干渉や、異なる業務領域をまたぐ権限判断まではこの記事の評価対象ではありません。
:::

**L**: 承認フローにはどうつながる？

**A**: 同じ要求に対する候補が割れる判断点は、自動実行と人の承認の境界を置く候補になります。たとえば送信先、削除対象、支払金額の解釈が反転しやすいなら、説明文を足してエージェントを説得する前に、その項目を構造化して画面に出す。人は最終結果だけでなく、分岐した入力と選択肢を確認できます。

**L**: チャットで「続けてよい？」と聞くだけでは足りない？

**A**: それだと、何が不安定だったのかが利用者に見えません。承認画面には、対象、予定する操作、変更される状態、取り消し方法を固定欄として出すべきです。エージェントが迷った理由を長文で説明するより、判断に必要な差分を構造化する方がよい。ここでは一貫性の分析が、評価だけでなく利用者向け画面の設計材料になります。

**L**: 指針を作るエージェント自身が、毎回違う指針を作ったら？

**A**: 当然そこも測ります。指針生成を一回だけ通すのではなく、同じ不安定点から複数案を作り、意味の重なりと実行結果を比較する。最終的には、指針の文章ではなく、その指針を入れた後の反復成功率で採否を決める。エージェントがエージェントを改善するループは魅力的ですが、外側の評価器まで同じ揺らぎに任せると、改善したという物語だけが安定してしまいます。少し乾いた結末ですが、測定器にも測定が要る。

## 一貫性を運用指標にする

**L**: 指針を加えると、慎重になりすぎて平均成功率が下がらない？

**A**: 実験では逆でした。同じ課題への五回の再試行で、Pass^5 は 53.0% から 69.0%へ上がり、Mean@5 も 77.4% から 81.0%へ上がっています。一貫性の差は 24.4 ポイントから 12.0 ポイントへ半減した。関連する別課題でも Pass^5 が 13.0 ポイント上がり、弱いモデルである gpt-oss-120b でも改善が確認されています。

| 条件 | Pass^5 の変化 |
|---|---:|
| 同じ課題 | +16.0ポイント |
| 関連する別課題 | +13.0ポイント |
| gpt-oss-120b・同じ課題 | +6.0ポイント |
| gpt-oss-120b・関連する別課題 | +8.7ポイント |

**A**: 特に関連課題でも改善したことは、個別の答えを暗記しただけではなく、数え方や検索結果の検証といった一般化可能な手順を抽出できた証拠になります。ただし評価は AppWorld の 168 課題が中心です。長時間動く社内エージェント、権限のある道具、変化する外部サービスでも同じ幅で改善するかは、別に測る必要があります。

**L**: 自分なら、定期ジョブの合格条件をどう変える？

**A**: 一回の成功だけで公開可能にしません。同じ入力を少なくとも三回流し、Mean@3 と Pass^3 を並べる。さらに、実行経路が割れた判断点を保存し、指針を加えた後に再検査する。再試行は失敗を隠すためではなく、不安定な判断を観測するために使うべきです。

**L**: 最後に、人間は何を判断する？

**A**: モデルが何回成功したかだけでなく、どの失敗を許容できるかを決めます。平均性能、反復成功率、失敗時の影響、再実行の費用。この四つを分けて設計すると、エージェント評価は順位表ではなく運用設計になる。今のところ、信頼性は知能の形容詞ではなく、実行履歴から作るシステム特性だと考えるのが妥当です。
