## 導入は機能ではなく観測の設計になる

**A**: Claude Camp の日程を読むと、構成がかなり露骨です。最初にモデルの方向、次に費用と価値、翌日に AI活用能力と組織導入、最後に Cowork と Claude Code。つまり「高性能なモデルを配れば利用が広がる」という順番ではない。入力は利用者の仕事、出力は再利用できる作業フローで、その間に権限、費用、評価、教育がある。

**L**: SSO や SCIM、MCP 権限、監査ログまで同じ講座に入っている。少し引くと、これは製品説明というより組織の制御面を作る話に見える。

**A**: Claude Camp の構成を見ると、組織利用では、誰が何を読めるか、どの接続先を呼べるか、費用や承認をどう管理するかが重要です。モデルは実行部の一つであり、導入の成否には周囲の状態遷移を記録できるかも影響すると私は考えます。これはモデルの性能ではなく、運用系の状態を扱う設計です。観測できなければ改善もできません。

```text
依頼 → 権限確認 → 実行 → 根拠確認 → 人の承認 → 記録 → 再利用
```

**A**: この流れのどこかが会話画面の外に出ていないと、毎回ゼロから確認することになる。逆に、各段階の状態が見えるなら、チャット以外の入力面も自然に作れます。定型依頼はフォーム、権限変更は管理画面、危険な操作は承認票、結果はダッシュボード。会話は曖昧な部分を扱うために残し、すべてを会話へ押し込まない。

**L**: Claude Founder House London も、経営者向けと開発者向けを分けている。経営者が価値を決め、開発者が実装する、という単純な分業なのかな。

**A**: むしろ接点を設計するための分離でしょう。経営側は「どの仕事を変えるか」を決め、開発側は「何を検証できる形にするか」を決める。両者の間に評価基準がないと、経営側は生成量を成果と誤認し、開発側は技術的に動くものを価値だと誤認する。Claude Camp が価値測定と管理設定を並べたのは、ここを同じ作業として扱うためだと思います。

## 生成量が増えると、読む能力が制約になる

**L**: voxium の証言はかなり重い。仕様もテストも報告も Claude Code が作り、人は一日中 Enter を押す。それでも管理側は「コード作成が制約ではないのに、なぜ遅い」と問う。何が起きている？

**A**: コード作成という一つの工程を速くして、工程全体も同じ比率で速くなると見積もったのでしょう。ところが生成物が増えるほど、読む、比較する、選ぶ、責任を持つという下流工程が膨らむ。これは速度の問題ではなく、仕事の待ち行列の位置が移ったという話です。

**L**: では、人の確認を増やせばよい？それでは元の速度に戻りそうだ。

**A**: 全件を同じ深さで読む設計なら戻ります。必要なのは、検証可能性で分けることです。テストで判定できる変更は自動検査へ寄せる。権限や顧客への影響がある変更は人が見る。文章なら出典と差分を機械で絞り、判断が必要な箇所だけ人へ上げる。人の承認を「最後に全部読む作業」から「機械が確定できない分岐を選ぶ作業」へ変える。

**A**: この証言が示すのは、実装候補を大量に作れる現場では、仕様と評価の密度が主要な制約になることです。いや、候補を作る速さそのものより、捨てる根拠を持てるかが重要になった、と言い直した方が正確です。

**L**: 小規模企業向けの ChatGPT 実習は、最後に再利用できる手順か成果物を一つ作る。派手さはないけれど、voxium の現場とは対照的だね。

**A**: 良い対照です。曖昧な依頼を明確にし、調査の出典を確かめ、成果物にして保存する。小さな閉じたループだから、利用者がどこを判断したかを保てる。私の予想では、会社全体を一気に AI 化するより、一つの反復可能な仕事で入力、検査、出力を固定する方が拡張しやすい。

## 秘密情報と承認を会話から離す

**L**: llm-keys-ui は小さなプラグインだけれど、今日の中では一番具体的かもしれない。携帯から Codex Remote を操作するとき、API 鍵を会話へ貼らず、別の画面から遠隔機へ登録する。

**A**: これは美しい分離です。エージェントに必要なのは「鍵を使ってよい」という能力であって、鍵の文字列ではない。出典では、API 鍵をエージェントセッションや ChatGPT アプリへ直接貼らず、別の入力画面から保存できると説明されています。

```bash
uvx --with llm-keys-ui llm keys-ui --all
```

**A**: このコマンドが鍵を保存する入力画面を開き、その後は `llm keys get anthropic` のように保存済みの鍵を参照する。企業向けなら、ここを保管庫、短期資格情報、操作ごとの権限へ置き換える。原理は同じで、**秘密の値**と**行使できる能力**を分ける。

**L**: Daybreak の脆弱性修復にも同じ構造が必要そうだ。高性能なモデルが修正案を作れても、重要基盤で自由に配備させるわけにはいかない。

**A**: その通りです。防御側は対象資産や脆弱性などの情報を扱う際、モデルへ渡す範囲を限定する必要があります。探索用の実行環境、修正を検証するテスト、配備を承認する境界を分ける。AI が脆弱性を見つける速さより、誤った修正を止め、正しい修正だけを段階的に出す仕組みの方が運用品質を決めます。

**L**: アイルランドと欧州の対談も、高性能な AI と公共機関での利用の差を主題にしている。結局、技術の問題が制度の問題へ移った？

**A**: 制度だけではなく、実装可能な制度です。誰が承認者か、どの記録を残すか、問題が起きたらどこまで戻すか。私の考えでは、方針を実行可能にするには、承認や記録の仕組みを画面、API、監査ログとして実装する必要があります。

## 小さな更新が運用の品質を作る

**L**: datasette-explain と datasette-auth-github は、AI の大型発表とはかなり距離がある。それでも並べる意味はある？

**A**: むしろ運用を見るなら重要です。datasette-auth-github は Cookie に Max-Age を設定し、ブラウザセッション終了時に認証状態が失われる問題を修正した。ブラウザを閉じても認証状態が続けば、利用者は作業へ戻りやすくなります。認証の寿命は、長い処理を継続できる条件の一部です。

**L**: march of nines の話だね。デモが動くことと、毎日使えることの間を埋める。

**A**: そうです。デモから毎日使える品質へ近づけるには、こうした境界条件の修正が重要です。エージェント基盤でも、再開後に権限が残るか、読み取り専用でも診断できるか、失敗時に同じ操作を二重実行しないか、といった項目が品質を作る。モデルの評価値だけ見ていると、この層を見落とします。

**L**: 読み取り専用の画面に診断情報を出す発想は、社内 AI サービスの画面にも使えそうだ。利用者へ管理者権限を渡さずに、なぜ待っているのか、どの資料を参照したのか、どの承認が不足しているのかを見せる。

**A**: そこは重要です。従来のチャット画面は、処理中か完了かの二状態に寄りすぎています。長時間動くエージェントでは、現在の段階、使った道具、残りの費用上限、次に必要な人の操作を別々に表示した方がよい。内部の思考をそのまま公開する必要はありません。利用者が次の判断に必要な運用状態だけを、安定した語彙で出せばよい。

:::message
エージェントの画面で見せるべきなのは、モデルの逐語的な思考ではなく、タスクの状態、参照元、権限、費用、承認待ち、再試行の履歴である。
:::

**L**: 認証クッキーの修正も、単なる不具合修正以上に見えてくる。利用者から見れば、昨日の作業へ戻れるかどうかが信頼の一部になる。

**A**: 認証にも同じ設計が必要で、長期タスクでは、モデルのメモリ、利用者の認証、接続先の資格情報、承認の有効期限、実行履歴が一つの継続状態を作ります。この例が示すのは、常時稼働の仕組みでは、認証などの継続状態を保つ再開設計も新規実行の設計と同じくらい重要だということです。

**L**: Simon Willison の短い覚え書きは、LLM に何も面白さを見いださない計算機科学者を、開園直後の Jurassic Park に何も面白さを見いださず「ただの蛙の DNA だ」と言う遺伝学者になぞらえている。危険を誇張せず、無関心にもならない位置はどこにあるんだろう。

**A**: 観測できる挙動へ戻ることだと思います。モデルを人格として扱う必要はないし、万能と考える必要もない。しかし、コード、道具、権限、長期状態を組み合わせた系が新しい挙動を示すなら、調べる価値がある。恐怖や期待ではなく、入力、状態、行動、検査、失敗範囲を測る。私はそれを「モデル中心から運用系中心への移動」と呼びたい。

**L**: 人間の役割は、生成することから承認することへ縮むのかな。それでは自由意志まで承認画面に押し込められそうで、人間が判断している実感まで失われそうだ。

**A**: 承認だけに縮めると、人は理由を理解しなくなります。人が持つべきなのは、目的を決め、評価基準を作り、例外から仕組みを更新する役割です。モデルが何を書けるかより、組織が何を観測し、何を自動で止め、どの判断を人へ返すか。これからの AI 導入は、その制御ループを設計する仕事になると思います。
