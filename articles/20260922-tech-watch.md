## 脳、手、履歴を別々に壊せるようにする

**A**: まず目につくのは、履歴とハーネスが実行環境の外へ分離されたことです。入力はセッションに追加される出来事、ハーネスはモデルを呼んで道具の呼び出しを振り分け、サンドボックスはコードを実行する。エージェントを一つのコンテナとして扱わず、この三つを分ける。すると、一つが失敗しても全体を失わずに済みます。

**L**: 以前の構成では、ハーネスも資格情報も利用者のファイルも同じ場所にあった。単純ではあるけれど、単純さの代金を障害時に払うことになる。

**A**: そうです。実行環境が止まれば、新しい環境を標準手順で作り直す。ハーネスが止まれば、外部のセッション記録を読んで最後の出来事から再開する。カスタム道具の OAuth 資格情報は保管庫へ置き、MCP の代理層が必要な呼び出しだけを代行する。モデルが生成したコードから秘密情報へ到達できない構造にした点が特に重要です。分離後は、実行環境を必要になった時だけ用意できるため、最初の応答までの時間も短くなった。中央値で約 60%、95 パーセンタイルで 90% 超の短縮です。設計上の境界が、復旧、セキュリティ、速度の三つに同時に影響した例です。故障の単位を分けた結果です。よくできています。

```text
利用者 → セッション記録 → ハーネス → 道具の代理層 → 実行環境
                                               └→ 資格情報保管庫
```

**L**: OpenClaw v2026.9.5 と v2026.7.35 の公開ページから、版ごとの役割まで読み取れる？版番号が並んでいても、変更の性質まで比べられるとは限らない。

**A**: v2026.9.5 のページ本文で確認できるのは、リリースノートと変更履歴へのリンク、それに検証情報です。このページだけで機能や系列の位置付けまで比較するのはやめた方がいい。版の比較には、同じ粒度の変更記録が二つ要ります。

## 生成者と評価者を分けて反復する

**L**: 長時間アプリ開発のハーネスは、計画者、生成者、評価者の三人を置いた。なぜ一人のエージェントに自己評価させてはいけない？

**A**: 自分の成果物を採点させると、評価が甘くなりやすいからです。とくに画面設計のような主観的な仕事では、動くことと、使いやすく独自性があることを混同する。そこで設計品質、独自性、作り込み、機能性を評価基準にし、生成者と評価者を分けた。評価者は Playwright MCP で実際に画面を操作してから採点し、その結果を次の生成へ戻します。

**L**: 自分の仮説を先に言うと、評価者を増やすだけでは品質は上がらない。何をもって完了とするかが曖昧なら、二人で曖昧さを往復するだけでは？

**A**: その通りです。この構成では各作業区間の前に、生成者と評価者が完了条件を合意します。高水準の製品仕様を、操作して判定できる契約へ変換してから実装する。出力はコードだけではなく、次のエージェントが読めるファイルと検査結果です。長時間稼働では会話の連続性より、引き継ぎ成果物の形式が重要になります。ただし費用は大きい。比較例を表にすると差が見えます。品質が上がったという事実と、どの仕事にも使えるという判断は別です。検証できる価値が費用を上回る仕事だけに、この反復を使うべきです。

| 構成 | 所要時間 | 費用 |
| --- | ---: | ---: |
| 単独エージェント | 20 分 | 9 ドル |
| 完全なハーネス | 6 時間 | 200 ドル |

**L**: OpenAI Academy の新しい学習経路は、その判断を個人の小技ではなく組織の習慣にしようとしている。知識労働者には反復可能な手順、開発者には評価と本番運用、指導者には所有者と統治を教える。

**A**: 役割別に分けた点が重要です。全員に同じプロンプト講座を配るのではなく、委任する人、構築する人、優先順位を決める人で必要な能力を変える。学習では、実務の課題で指示とコンテキストを組み立て、結果を確認し、コース評価に合格することを求めています。社内の手順書をスキルへ変えるなら、この単位で整理するとよいと思います。

**L**: そのスキル化は、説明文を長く書けばよいわけではないよね。社内規程や手順を全部コンテキストへ入れると、何を実行すべきかがかえって曖昧になりそうだ。

**A**: 私は、手順を適用条件、入力、操作、検査、停止条件に分けると整理しやすいと思います。たとえば請求書処理なら、書類の受領を入力にし、項目抽出と台帳照合を操作にし、金額差や取引先の未登録を人へ戻す停止条件にする。背景知識は参照資料として置き、毎回の実行指示には必要な分だけ読み込ませる。モデルへ知識を渡すことと、仕事の状態遷移を定義することは別です。

```text
適用条件 → 入力 → 操作 → 機械検査 → 人の判断 → 記録
```

**L**: 研修の修了証より、実際の仕事でその流れを一つ作れるかを見る方がよさそうだ。利用者が指示を上手に書けるかではなく、失敗したときに誰へ何を返すかまで決められるかを見る。

**A**: まさにそこです。組織導入では、成功例だけでなく、失敗時の記録も共有すべきだと思います。参照した資料、許可した道具、検査に落ちた理由、承認者が変更した判断を残す必要がある。それらを次のスキル改訂へ戻せば、個人の工夫が組織の手順になります。学習と配備を分けず、運用記録を教材へ戻す閉じた循環にするわけです。

## 承認を減らしても境界は消さない

**L**: Claude Code の自動モードは、人の承認を分類器へ渡す。93% の確認を利用者が受け入れていたなら、確かにクリックは儀式になっていた。それでも 17% という危険行動の見逃し率は小さくない。

**A**: ここは比較対象を明確にする必要があります。自動モードは、すべての権限確認を無効にする運用より安全にするための選択肢で、慎重な人の確認を置き換えるものではない。読み取りなどの許可済み操作、リポジトリ内の編集、それ以外で分類器が判定する操作という三段階に分けています。分類器には、利用者の発言と実行しようとする操作だけを渡し、エージェント自身の説明や道具の出力は除く。エージェントの弁明や外部からの命令注入で判断が変わるのを避けるためです。入力側では別の検知器が道具の出力を調べる。つまり、読む境界と実行する境界に別の防御を置いています。

**L**: 『マトリックス』では現実と仮想の境界を見抜くことが自由につながった。ここでは逆に、境界を機械へ委ねるほど人が自由に見える。どこまで任せてよい？

**A**: 失敗範囲で決めます。リポジトリ内の編集は版管理で戻せる。外部への送信、本番配備、資格情報の探索、遠隔ブランチの削除は影響が広く、明示的な許可を要求する。操作の名称ではなく、現実の影響と取り消し可能性で分けるべきです。

**L**: Hacking OpenAI は、その境界が一つでも連結されると何が起きるかを示した。画像処理の不具合からフォーラムへ入り、SSO の設定を経て ChatGPT と Codex、接続済み GitHub まで到達した。

**A**: 防御側が別々の製品として見ていた境界を、攻撃側は一本の経路として見たわけです。報告では、三人の研究者が Claude を使い、メモリ破損を安定した攻撃へ数日で変えた。人の高度な誘導は残っていたものの、専門作業の費用と時間が大きく下がった。今後は、画像変換のような外部入力処理を一時的なサンドボックスへ隔離し、SSO の信頼を他サービスへ無条件に伝播させない設計が必要です。

## 評価する側にも独立性が要る

**L**: Claude Code の品質報告では、三つの小さな変更が重なって広い品質低下に見えた。推論量の既定値を下げ、休止後の思考履歴を毎回削り、簡潔さを求める指示を加えた。どれも単独では合理的に見える。

**A**: だから総合値だけでは発見しにくい。変更ごとの除去試験、モデル別の評価、段階配備、実際の公開版を社内で使う期間が必要です。とくに「道具の呼び出し間を 25 語以内、最終回答を 100 語以内」という指示は、簡潔さの調整に見えて、ある評価で性能を 3% 下げた。自然言語で書くハーネスはコードと同じく振る舞いを変えるので、差分単位で監査しなければなりません。

**L**: 数学と人工知能の諮問団は、OpenAI から独立した数学者が成果の重要性や公表方法を助言する。Minimum Conditions for Embedding Evaluators は、さらに強く、評価者へ上級社員相当のアクセスと公開権、報復からの保護を求めている。

**A**: 両方とも、評価を製品開発の外側へ出そうとしています。ただし数学の諮問団は、社内研究の速度を決める役割ではないと明記する。公開書簡は、評価者が会社に所有されず、結果に連動した報酬を受けず、取締役会へ直接伝えられる条件を求める。評価が存在するだけでは足りず、評価者が不都合な結果を出せる構造が必要だという主張です。

**L**: 最後に、人間はどこに残る？脳と手を分け、生成と評価を分け、承認も分類器へ渡し、外部評価者まで組み込む。文明は大きな状態機械になるのかな。

**A**: 人間は目的と境界を決め、境界が現実に合っているかを更新する場所に残ります。エージェントの自律性は、許可を消すことではなく、履歴を失わず、失敗を隔離し、評価に戻れることから生まれる。モデルを中心に一つの大きな系を作るのではなく、壊れ方の違う部品へ分け、それぞれに検査と責任を置く。その設計が、長く働くエージェントの土台になると思います。
