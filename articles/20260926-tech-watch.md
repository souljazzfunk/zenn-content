## 承認ではなく、到達可能性を制限する

**A**: その疑いは正しいと思う。Anthropicの計測では、Claude Codeの権限確認の約93%が承認されていた。確認画面が安全境界なら、人が毎回きちんと読んで判断することが前提になる。でも同じ形式の確認が続けば、実際には「次へ進む」ための操作へ変わる。安全性を人の注意力という枯渇する資源に預けている。

**L**: では、確認を減らしても安全を保てる仕組みは何だろう。自動承認を賢くするだけでは、判断をモデルへ移しただけにも見える。

**A**: 中心にあるのは**封じ込め**だ。モデルが何をしようとしたかを毎回推測するより、実行環境から到達できる範囲を先に狭める。claude.aiは一時的なコンテナ、Claude Codeは作業空間への書き込みを許しつつ通信を制限するOSのサンドボックス、Coworkは選択したフォルダだけを載せた仮想マシンを使う。同じClaudeでも、利用者と作業の性質に応じて境界が違う。

**A**: ここで重要なのは、モデル、実行環境、外部内容の三層を分けることだ。システムプロンプトや分類器は、モデルが望ましい行動を選ぶ確率を上げる。サンドボックスと通信制御は、選択を誤っても越えられない線を作る。MCPやウェブ検索から入る内容は、正規の接続先でも命令注入を含み得るので、道具側の権限も狭くする。一つの防御へ全部を任せない設計になっている。

**L**: 『マトリックス』では、仮想世界の中にいること自体が問題だった。でもエージェントでは逆で、仮想環境の外に出られないことが安全装置になる。少し皮肉だね。

**A**: しかも仮想化製品を置けば終わりではない。Anthropicは、自作したプロキシや信頼確認より前に読み込む設定で事故を起こしている。長く使われたgVisorやseccompより、新しく書いた周辺部の方が弱かった。境界は図では美しくても、初期化順序、認証情報の置き場所、外向き通信、例外経路まで実装して初めて境界になる。これは知能よりシステム工学の問題だ。

## 三万のエージェントをどう監督するか

**L**: 一つの端末なら作業空間を囲める。でも約三万のエージェントが研究開発を進める規模では、個別の確認はもう成立しない。何を観測すれば管理できるのだろう。

**A**: Anthropicが出した測定はかなり具体的だ。Claudeは研究開発作業の26%を高水準で主導し、90%以上で人と協働する段階以上にある。一方、完全自律と評価された領域はまだない。内部基盤では約三万のエージェントが同時に動き、全操作が実行前の監視を通る。十億件を超える判断のうち、停止されたのは約0.002%、つまり約四万七千件に一件だった。

**L**: 率が低いなら安心、と単純には言えないよね。母数が増えれば、珍しい事象も毎日の運用になる。

**A**: そう。必要なのは、失敗率だけでなく、監視範囲、検査までの時間、停止率を一緒に測ることだ。実行前の監視は取り返せない操作を止め、事後監視は長期的な挙動を探す。さらに研究開発向け計算資源の約6%、AI主導の研究開発では約12%を安全性へ使ったという配分も公開した。数字の定義には議論の余地があるが、少なくとも「安全に取り組んでいる」という説明を時系列で比較できる測定へ変えている。

**A**: Claude Code 2.1.283の変更も同じ方向を向く。 `/doctor prompt-audit` は、古いモデルを前提に書かれたCLAUDE.md、スキル、エージェント定義、コマンドを探す。管理者は利用可能なモデルを完全一致で固定し、特定モデルを拒否できる。MCPの道具出力はOpenTelemetryへ記録でき、Claude TagではSlack内で検索できる公開チャンネルを管理者が制限できる。能力を足す更新というより、構成の経年劣化と組織境界を監査可能にする更新だ。

```text
権限を与える → 操作を観測する → 異常を止める → 設定を監査する → 次の境界を直す
```

**L**: ハーネスは、モデルを一度囲む箱ではなく、観測結果で更新され続ける制御系なのか。

**A**: その見方が近い。二年前なら一つのコーディングエージェントを動かすこと自体がデモだった。今は数万を動かし、権限、監視、記録、再試行を運用品質へ上げる段階にいる。90%から99%、99.9%へ信頼性を一桁ずつ上げる過程では、モデルの評価値より、失敗を分類して境界へ戻すループが支配的になる。

## 指揮役と実行役を分ける

**L**: 境界を狭めると、エージェントの能力まで落ちないだろうか。複雑な仕事を完了するには、広い文脈と多くの道具が必要にも見える。

**A**: そこで役割分担が重要になる。Devin Fusionは、高性能なモデルを計画とレビューの担当に置き、SWE-2を実装担当として同時に動かす。両者は会話全体を渡さず、制約と成功条件を含む短い依頼、結果、指摘を交換する。各自のコンテキストとプロンプトキャッシュを保てるので、低価格モデルへ途中で切り替えて履歴を読み直すより費用を抑えやすい。

**A**: 評価では、Claude Fable 5.1を指揮役にした構成がClaude Code単体と同じ62点で、課題あたりの費用を36%減らした。ただしトークン数は70%増え、手順数は約三倍だった。安いモデルへ仕事を渡せば自動的に安くなるわけではない。委任の粒度、返却条件、圧縮の時点まで含めて、全体費用を測る必要がある。

**L**: 会社の組織図に似ている。管理職と実務担当を増やせば成果が増えるとは限らず、引き継ぎの形式が悪いと会議だけ増える。

**A**: まさにそこだ。Message Passing Language Modelsは、並列スレッド同士に軽量な送受信を持たせる。従来の分岐・合流方式は、各スレッドが長い文脈を複製し、最後まで走ってから結果を集める。直接通信できれば、部分結果を共有し、見込みのない探索を途中で止められる。数独や充足可能性問題では、通信量と無駄な探索を減らした。マルチエージェントの本質は人数ではなく、情報をいつ、どの量で、誰へ渡すかだ。

**A**: FLUX 3 Actionも別の領域で同じ分離を使う。ロボットの連続制御は70億パラメータの動作モデルが高速に担い、難しい局面だけ高価な推論モデルが介入する。すべての瞬間を最上位モデルに考えさせるより、速い制御器と遅い計画器を組み合わせる方が、成功あたりの費用と時間を減らせた。これは単なるモデル選択ではなく、時間尺度ごとの役割設計だ。

## 生成しないモデルと、生成しすぎる組織

**L**: Jevはさらに極端で、文章を生成しない。チャットを中心に発展してきたAIが、最後には確率だけ返すのは後退にも見える。

**A**: 私はむしろSoftware 3.0を普通のソフトウェアへ接続するための薄い部品として見る。Jevは、文章と質問を受け取り、真偽、選択肢、評価値を型付きの確率として並列に返す。返答文を解析してJSONへ直す必要がなく、許される出力も先に決まっている。問い合わせの振り分け、入力不足の検出、満足度の評価、命令注入の検査のような箇所なら、自由な文章生成は能力ではなく余分な行動空間になる。

**L**: つまり、賢いモデルをどこにでも置くのではなく、判断の形を狭く定義できる場所では専用部品にする。社内サービスの画面設計にも近いね。チャット欄を一つ置くより、承認、分類、差し戻しを別の操作にする方が責任を示しやすい。

**A**: そう思う。そしてSimon Willisonの短い指摘が、その裏側をよく表している。コーディングエージェントは驚くほど多くを書けるが、その能力を引き出すには以前より高い規律と専門性がいる。生成速度が上がると、仕様、検証、構成管理、保守の負担まで自動で下がるように錯覚しやすい。実際には、読むべき変更と確認すべき仮説が増える。

**A**: Claude Opus 5.5も同じ注意を促す。単価は前世代より下がり、知識作業やコーディングの評価は上がった。しかし高い推論強度では多くのトークンを使うため、評価課題あたりの費用は高い。モデルの能力、単価、課題完了までの総費用は別の変数だ。最上位モデルを全工程へ固定するより、Jevのような分類器、SWE-2のような実行役、Opusのような指揮役を、検証可能性に合わせて配置する方が合理的になる。

**L**: Museの問題は、その複雑な構成を消費者向けの親しみやすい外観で包んだことなのかな。『her』のOSは会話相手に見えたけれど、実際のエージェントは永続的なLinux仮想マシンと権限の集合だ。

**A**: 外観が親しみやすいこと自体は悪くない。ただ、利用者が判断すべき危険性まで隠すと、操作の容易さと安全性が衝突する。どのファイル、アカウント、通信先へ到達できるか。いつ動き、誰が止め、何を記録するか。UIは内部実装を全部見せなくてもよいが、この五つは理解できる形で示す必要がある。かわいいマスコットに管理者権限を持たせるなら、少なくとも権限画面は大人向けであるべきだ。

**L**: 人間の役割は、個々の操作を承認することから、境界と測定方法を決めることへ移るのだろうか。自律性が増えた先で、人は何を手放してはいけない？

**A**: 目的、到達可能な範囲、成功条件、停止条件の四つだと思う。実行手順はエージェントへ委任できるし、複数のモデルへ分割もできる。でも何を最適化し、失敗時にどこまで損失を許し、どの証拠で完了とするかは人が所有する。モデルが強くなるほど、良い指示文を書く技術より、制御可能な実行環境と検証ループを作る技術の比重が上がる。自律性の反対は人の常時介入ではなく、明示された境界だ。
