## 出力を終点にしない

**A**: この記録で最初に目に入るのは、少なくとも 20 羽という指定で作られたカカポが紙吹雪の中で跳ねる画面だ。でも、仕組みとして重要なのは絵柄より受け渡しだと思う。Simon Willison は 3 枚の写真を Claude Opus 5.5 に見せ、HTML 5 Canvas 上で動くピクセル画を依頼した。そこで得た HTML をダウンロードし、次にローカルの Claude Code へ渡して動画化を頼んだ。最初の生成物が、次の作業の入力になっている。

**L**: チャットなら、HTML が出たところで「できました」と言って終わりやすい。けれど本人が欲しかったのはコードではなく、Keynote に置ける 15 秒の動画だった。完成の定義が一段先にあるね。

**A**: 成果物ではなく中間物として扱うと、小さい例ながらエージェントの作業設計をかなりよく表している。モデルの出力を最終成果と見なさず、**中間成果物**として保存し、別の実行環境で開き、操作し、目的の形式へ変換する。入力は写真と自然言語、途中は HTML と JavaScript、実行面はブラウザ、最後は動画ファイルだ。形式が変わるたびに、次の道具が読める境界を作る必要がある。

**L**: Software 3.0 の自然言語が、Software 1.0 の短いスクリプトを作り、そのスクリプトがブラウザを動かす。層が混ざっているようにも見える。

**A**: 混ざっているというより、役割が分かれている。自然言語は「何を完成とするか」を置く。Claude Code はその要求を、時刻、座標、画面寸法、録画先という実行可能な値へ落とす。Playwright は決められた通りにブラウザを操作する。モデルに画面を眺めながら 15 秒間クリックさせ続ける必要はない。一度計画をコードへ圧縮すれば、残りは決定的な実行になる。ここは美しい分担だと思う。

**L**: エージェントが何でも直接操作するより、短いプログラムを残した方がよい場面がある。再実行もしやすいし、人も読める。

**A**: 今回の Playwright スクリプトは依存関係、画面サイズ、クリック列、録画時間を一つのファイルに閉じ込めている。中心部分は概念的にはこれだけだ。

```python
clicks = [
    (3.0, 640, 360),
    (4.2, 160, 120),
    (5.4, 1120, 120),
]

for second, x, y in clicks:
    wait_until(second)
    page.mouse.click(x, y)
```

**A**: 入力は「何秒後に、どこを押すか」という列で、出力は録画された動画だ。途中のループは単純だから、失敗したときも調べやすい。複雑な知能を実行時に使い続けるのではなく、知能を使って小さな手順を作り、その後は普通のソフトウェアに任せている。

## 曖昧な依頼を検査可能な値へ変える

**L**: 元の依頼には「3 秒まではクリックしない」「複数のクリックを領域内へ散らす」「15 秒の動画」という条件があった。かなり具体的だ。もし「紙吹雪を自然に出して」だけなら、同じ結果にはならなかったかもしれない。

**A**: 私もそこが決め手だと思う。動画の見た目には主観が入るけれど、実行条件は検査できる。録画時間は 15 秒か。最初のクリックは 3 秒以降か。座標は 1280 × 720 の範囲内か。クリックは中央だけでなく四隅や辺にも置かれているか。自然言語の要求を、このような測定可能な条件へ変換すると、自動化のループを閉じやすくなる。

**L**: 「成功したか」をエージェント自身が判断できる仕事ほど、自律化しやすいという話につながる。今回は映像の美しさを完全には採点できなくても、制作工程の大半は検査できる。

**A**: そう見るのがよい。ここには二種類の検査がある。機械的な検査では、ページが開くか、スクリプトが例外なく終わるか、動画ファイルが生成されたか、長さや解像度が指定通りかを確認できる。人の検査では、発表の締めに使いたい雰囲気になっているかを見る。全部を数値化しなくても、機械が担える部分を先に固定すれば、人は最後の短い判断に集中できる。

**L**: 承認フローとして考えると、人が最初から最後まで画面を操作するのではなく、生成された動画だけを見る。承認点を末尾へ寄せられるわけだね。

**A**: ただし、承認点を減らせばよいとは限らない。今回の対象はローカルの HTML と録画で、外部サービスへの公開や既存ファイルの破壊は含まれない。だから実行の危険範囲が小さい。もし同じエージェントが発表資料を上書きし、共有先へ投稿するなら、動画生成と公開の間に人の承認を置くべきだ。自律性はモデルの賢さだけで決めず、失敗したときに何が変わるかで決める。

**L**: かわいいカカポの画面でも、運用の原理は同じか。見た目が映画の対話相手のように滑らかでも、裏側にはファイル形式、座標、待ち時間、権限という地味な境界がある。

**A**: まさに実行の問題だ。デモでは「自然言語から動画ができた」と一行で言える。でも実際には、参照画像を渡し、HTML を保存し、ローカル URL を開き、画面サイズを固定し、時間に沿って操作し、録画を閉じる。この鎖の一つでも曖昧なら、再現性が落ちる。モデルが強くなるほど、周囲の境界を明示する価値はむしろ上がる。

## 観察できる境界を置く

**L**: ここまで聞くと、コードを残すこと自体が作業記録になっているように思える。会話だけなら、どの操作が動画を変えたのか後から追いにくい。座標と時刻の列なら、紙吹雪が多すぎたときにどこを直すか分かる。

**A**: それは重要だ。エージェントの内部の考えを詳しく保存するより、外に現れた操作を構造化して残す方が有用なことが多い。今回は「3.0 秒に中央を押した」「4.2 秒に左上を押した」という事実がコードにある。動画が期待と違えば、入力の列、ページの状態、録画結果を順に比較できる。可観測性を推論の説明だけに求めず、道具の入出力へ置いている。

**L**: 失敗した場合も、全部を最初から生成し直す必要はない。HTML が正しければ録画だけ再実行し、クリック配置が悪ければ列だけ直せる。工程を分けることが再試行の範囲を狭めるんだね。

**A**: そう。私はこれを**成果物の境界による再開**と呼びたい。写真から HTML を作る段階、HTML を操作する段階、画面を動画に保存する段階を分ければ、正常だった成果物を再利用できる。長時間動くエージェントでも同じで、検査済みの中間成果物を残せば、障害のたびに最初へ戻らずに済む。コンテキストの節約というより、実行状態をファイルへ退避する設計だ。

**L**: ただ、中間ファイルが増えると、どれが正しい版か分からなくなる危険もある。短い作業なら一つのディレクトリで済むけれど、チームでは命名や履歴が必要になる。

**A**: その通り。最小の例をそのまま組織へ拡大すると、今度は版管理、所有者、保存期間が問題になる。どのプロンプトから生成した HTML か、どのスクリプトで録画したか、完成動画がどの版に対応するかを結び付ける必要がある。ただし、最初から大きな管理基盤を作る必要はない。まず成果物に安定した名前を付け、入力と出力の対応を実行ログへ残す。それで不足した時点で仕組みを増やせばよい。

## 小さなハーネスを残す

**L**: この作業を一度きりの小技ではなく、繰り返せる仕組みにするなら、何を残すべきだろう。プロンプト、HTML、Playwright スクリプト、完成動画の四つで足りる？

**A**: 最小構成ならかなり近い。私はそこに実行条件を一つ加える。ブラウザの種類、画面寸法、依存関係、入力ファイルの場所が分からないと、同じコードでも結果が変わり得るからだ。今回のスクリプトは依存関係をファイル先頭に記し、1280 × 720 を明示し、録画先のディレクトリも指定している。小さなハーネスとして必要な情報が、短いコードの中に見える形で残っている。

**L**: 10 年前なら、この程度でも人が画面録画ソフトを開き、秒数を見ながらクリックしたと思う。今はエージェントが操作コードを組み立てる。10 年後には、途中の HTML や録画手順を意識しなくなるのかな。

**A**: 利用者は意識しなくなるかもしれない。でも、作る側は意識した方がよい。隠された工程が消えるわけではなく、ハーネスの中へ移るだけだからだ。製品化で信頼性を高める段階では、読み込み待ち、保存完了の確認、失敗時の再試行など、扱う検査や処理が増えていく。

**L**: すると、この例の価値は高度な映像生成そのものより、完成物までの距離を一つの流れとして扱ったことにある。人間が「これを発表に使いたい」と思った瞬間から、必要な道具が連鎖した。

**A**: そう思う。生成モデルは素材を作り、コーディングエージェントは素材を扱う手順を書き、ブラウザ自動化は手順を再現する。ここで重要なのは、各段階の出力が次の段階の入力として明確なことだ。モデルが何を知っているかだけでなく、何をファイルとして残せるか、どの道具へ渡せるか、どこを検査できるかが完成度を決める。

**L**: 人間の創作は、道具が増えるほど分断されるのではなく、意図を保ったまま形式を変えていく仕事になるのかもしれない。最後に残る人の役割は何だろう。

**A**: 今回なら「発表の締めで、カカポを跳ねさせたい」と決めたことだと思う。その目的はログや検査項目からは出てこない。エージェントは目的を実行可能な鎖へ変えられるが、何を喜びとして残すかまでは自動的に決まらない。人が目的を選び、機械が検査可能な工程を連結すれば、生成物を次工程の入力として再利用できる。
