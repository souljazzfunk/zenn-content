## 常駐するなら、作業面より境界面が広くなる

**A**: dotsの説明で重要なのは、能力の一覧より権限の分け方だと思う。利用者本人の**常駐エージェント**はChatGPT、Slack、Teamsをまたいで文脈を持ち、自分のクラウド計算機とブラウザーを使う。組織向けの専用エージェントは、個人の代理ではなく、会社が専用のID、認証情報、接続先を与える。つまりチャットボットを増やしたのではなく、組織図に機械の担当者を追加しようとしている。

**L**: 担当者なら、仕事を待つだけでは足りない。でも先回りしてよい範囲をどう見せる？

**A**: 常駐エージェントは、利用者が操作していない時間の先回り調査を、接続済みアプリの読み取り専用操作に限定する。書き込みや送信はできず、動作中の作業はActivity Viewから追える。さらにCustom Rulesで、個別の操作を許可、承認必須、禁止に分ける。社内向け画面で必要なのは「何でもできます」という入力欄ではなく、現在の権限、次に実行する操作、承認が必要な理由を同じ場所に出すことになる。

| 層 | 自律実行できる範囲 | 人に戻す地点 |
|---|---|---|
| 先回り調査 | 接続済み情報の読み取り | 新しい接続先が必要なとき |
| 通常作業 | 明示した規則の範囲 | 規則外の書き込みや送信 |
| パスワード変更などの特定の機密操作 | 実行しない | 本人が操作 |
| 安全上の懸念を検知したとき | エージェントの作業が一時停止または終了 | 利用者が状況を確認 |

**L**: 「承認ボタンを置く」だけではなく、平常時の自律性を狭く定義するのが先なんだね。管理者だけが規則を知るのではなく、依頼する人にも現在の範囲が見える必要がありそう。

**A**: その表示は監査のためだけではない。依頼者が最初から実行可能な範囲を理解できれば、途中で承認待ちになる回数も減る。権限を隠れた設定にせず、作業の状態として見せることが、チャット以外の入力面を設計する理由になる。

**A**: そう。承認は最後の関門で、境界の全体ではない。専用の実行環境、認証情報をモデルへ見せない仕組み、読み取り専用の接続、操作ごとの規則、監視による停止が重なって初めて、常駐を製品として説明できる。OpenAI自身の例でも、請求書は用意できても送信前に人の承認へ戻している。便利さの演出より、この戻し方の一貫性が信頼を作る。

**L**: 蒸留活動の報告は、モデルの回答を盗むというより、内部の考え方を別の形で取り出そうとした話なんだね。接続が増えると、どの中間物まで境界として扱う？

**A**: OpenAIが確認したのは、暗号や保存会話の侵害ではなく、モデルとのやり取りを操作して保護された推論を見える形に再現する活動だ。関連する型は1万5千超の利用者群へ広がり、対策は不正アカウントの停止、登録と基盤の強化、配信出力の検査、第三者サービスとの連携まで及んだ。接続先を増やすエージェントでは、通常の文章だけでなく、道具の出力や会話圧縮の断片も境界を越えるデータとして扱う必要がある。

**L**: すると、組織のAI運用は「何を答えてよいか」だけでなく、「どの中間物を保存し、再利用し、外へ渡してよいか」を決める仕事になる。その範囲を誰に見せるべきだろう？

**A**: 常駐エージェントが同僚に近づくほど、人間向けの職務分掌だけでは足りない。ID、接続先、読み書きの範囲、推論記録、費用、停止条件を一つの運用単位として持つ必要がある。利用者が「いま何を任せ、次に何を承認するか」を短く理解できる表示が、その単位の入口になる。

## チームの作業フローは、共有ファイルだけでは揃わない

**A**: Codexの講座が扱う項目は、**共有コンテキスト**、リポジトリ指示、承認とサンドボックスの既定値、MCP接続、再利用可能なスキル、自動化、ワークツリーだ。どれも単体では新奇ではないけれど、チーム運用では一つの制御系として揃える必要がある。

**L**: `CLAUDE.md`や`AGENTS.md`を書けば、共有は済むと思いがちだよね。でも、実行条件はどこに置く？

**A**: 指示ファイルは判断基準を渡すが、実行環境までは固定しない。同じ手順書を読んでも、接続できる道具、変更できる場所、承認を求める条件、並列作業の分離方法が違えば結果は揃わない。ここはよくできていて、再現可能なチーム運用を次の対応関係として分解できる。

```text
業務ルール      → リポジトリ指示・スキル
利用可能な道具  → MCP接続と権限
危険な操作      → 承認規則
実行の隔離      → サンドボックス
並列作業        → ワークツリー
定期実行        → 自動化
```

**A**: DevDayの要約が示す「人とエージェントの共有作業面」も、この延長にある。共有画面だけを作っても、裏側の規則が利用者ごとに違えば協働にはならない。社内ナレッジのスキル化では、説明文を長くするより、「いつ起動するか」「どの資料だけを読むか」「何を変更してよいか」「どの状態で止めるか」を契約として短く書く方が再利用しやすい。

**L**: 2025年は個人が一つのエージェントへ上手に頼む話が中心だった。2026年は、チームが複数の実行主体へ同じ境界を配る話へ移ったように見える。

**A**: Simon Willisonの一年の整理もそこを通っている。コーディングエージェントが日常利用できる水準を越え、OpenClawのような常時稼働の個人エージェントが広がり、次にソフトウェア工場が「人がコードを書かず、読まなくても品質をどう確かめるか」を問うた。モデルの出力品質だけではなく、隔離、検証、費用上限、停止条件まで含むハーネスが製品の一部になった。

## 長時間推論は、長時間の自由行動ではない

**L**: Gemini 4 Argonの100万出力トークンは、長い仕事を一回で進められるという意味だよね。**長時間エージェント**のハーネスは簡単になる？

**A**: 一部は変わるが、不要にはならない。いや、出力上限だけの話ではない。Argonは64Kから100万へ出力上限を広げ、Google社内では大規模なRust移行や、プロファイルを使った反復最適化に使われている。長い一つの軌跡で多くの試行を保てる一方、誤った前提も長く持ち続けられる。だからGoogleは一般提供の前に段階展開し、推論と操作の監視、停止、隔離した実行環境を併記している。

**A**: OpenAIの安全性論証は、その周辺設計をさらに形式化する。整合性の学習、封じ込め、監視を技術面の三層にし、運用面では反対意見、複数責任者の拒否権、停止手順、監査、重大度別の連絡経路を求める。特に重要なのは、監視が無効なら学習を開始できず、夜間に警告が確認されなければ自動停止するような、失敗時に安全側へ倒れる制御だ。

> It should be challenging for humans and agents to start noncompliant runs.
>
> — OpenAI, "Towards safety cases for frontier AI training"

**L**: 長く考えられるモデルへ、長く自由に動ける権限を同時に渡す必要はないわけだ。どの単位で区切るのがよい？

**A**: むしろ逆で、能力の時間幅が伸びるほど、権限は段階化した方がよい。短い区間ごとに成果物を固定し、検査を通し、次の権限を開く。一度の実行で完了させる方式より、チェックポイントを持つ反復の方が、失敗箇所も費用も説明しやすい。成功率を一桁ずつ上げる作業は、推論量より再試行と観測の設計に多くを使う。

| 信頼性を上げる段階 | 成功率 |
|---|---:|
| 最初の段階 | 90% |
| 次の段階 | 99% |
| さらに次の段階 | 99.9% |

## 性能と費用の改善は、仕事の分配を変える

**A**: **GPT-6.1 Sol**は、エージェント型コーディング、コンピューター操作、専門業務でAstraに近い性能を、標準入出力料金の5分の1で提供する。キャッシュ済み入力は100万トークン当たり0.10ドルだ。長いプロジェクト指示や社内資料を何度も参照するエージェントでは、モデルの単価だけでなく、同じコンテキストを再利用できるかが費用設計の中心になる。

**L**: 高性能モデルを全工程へ固定するより、Solを通常経路にして、難しい判断だけAstraへ送る方が自然になりそう。その切り替えは何を測って決める？

**A**: その分配を支えるのが評価だ。Open TTS Leaderboardは音声という別分野だが、設計が参考になる。人の好みを唯一の順位へ押し込まず、明瞭度、話者類似度、処理速度、最初の音声までの待ち時間を分ける。客観指標による1モデルの評価を数週間から数時間へ短縮し、その結果を人による比較対象の選定にも使える。エージェントでも、成功率、費用、待ち時間、承認回数を別々に測れば、どのモデルをどの工程へ置くかを決めやすい。

**A**: Claude Sonnet 5.5の実使用記録も、平均性能だけでは足りない例だ。観察を分けると、性能改善と終了失敗が同じ記録に現れている。

| 観点 | 観察 |
|---|---|
| 速度 | Anthropicによれば30%以上向上 |
| 費用 | Anthropicによれば多くの作業で最大30%低下 |
| コーディング性能 | Simon Willisonは一部の課題でOpus 5.5に近いと評価 |
| 失敗例 | 最大思考量のペリカン生成で128,000トークンを使い切り、SVGを出力できず |

**A**: 推論量を増やす設定は、難題を解く能力と、終了条件を失う危険の両方を持つ。モデル選択と同じくらい、思考量の上限と成果物の検査が重要になる。

**L**: 『2001年宇宙の旅』では、境界を握る機械と人の目的がずれていった。境界を決める側までエージェントに任せ始めたら、最後に残る人の責任は何だろう。

**A**: 目的と許容損失を引き受けることだと思う。エージェントは規則を適用し、失敗から候補を提案できる。でも、何を守るために速度や費用を犠牲にするかは、組織の価値判断だ。技術的には、常駐エージェントは一つのモデルではなく、権限、観測、記憶、評価、停止を束ねた小さな運用制度として見るのが正確だ。
