## 能力ではなく、能力への入口を分ける

**L**: 能力の強さではなく、誰がどの入口を通れるかを見るわけだね。ただ、入口で身元と用途を確認しても、入った後の操作が見えなければ心配は残る。検証は一度の審査で終わるのかな。

**A**: そこを Claude Code 2.1.292 と並べると、境界が二重に見える。外側には利用資格があり、内側には実行時の検査がある。今回、エージェント用の道具へ `effort` が加わり、作業フローのエージェントを `agent.spawn` フックから検査できるようになった。要求が子エージェントへ渡る瞬間を観測点にできる。

```text
要求
  -> effort を伴うエージェント実行
  -> agent.spawn で検査
  -> MCP・サンドボックス内の操作
  -> 結果
```

**A**: 私はこれを**能力の段階化**と**実行の段階化**だと見ている。前者は何を使わせるかを決め、後者は生成、道具の呼び出し、外部への変更という遷移を分ける。MCP、サンドボックス、定期タスク、Claude Tag、Code Review、継続実行まわりの修正が同じ版に集まるのは偶然ではない。モデルを一度呼ぶ機能から、長く動く系へ移ると、周辺の状態管理が製品の信頼性を決める。

**L**: 『2001年宇宙の旅』では、扉を開ける権限が物語を変えた。今のエージェントに意志があると言いたいわけではない。でも、長時間動く処理では、誰が停止できるかが能力そのものと同じくらい重く見える。

**A**: そうだと思う。新しい Cowork が、推論とセッションごとの仮想マシンをクラウド側で動かし、端末のファイルが必要なときだけデスクトップアプリへ操作を戻すのも同じ設計だ。端末を閉じても継続できる一方、サンドボックスはセッションごとに分離される。継続性と局所性を両立させようとしている。長く動かすなら、実行時間を延ばすだけでなく、触れられる範囲を狭く保つ必要がある。

**A**: たとえば、利用者が閲覧できる文書をエージェントも読める、までは分かりやすい。難しいのは、その文書から推測した内容を別の課題へ書き込めるか、担当者を変更できるか、完了扱いにできるかだ。入力側の権限と出力側の権限は同じではない。いや、「権限」と一語で包むのが少し粗い。参照、提案、実行、確定を別々に扱う必要がある。

**A**: 業務エージェントのハーネスを最小化すると、入力は「現在の状態、許可された操作、業務規則」で、出力は「操作履歴と更新後の状態」になる。ループの各周回で規則違反を調べ、最後に結果を確認する。知能の問題に見えるけれど、実運用では承認点、権限、再試行、停止、記録をどう置くかというシステム工学の問題が大きい。キーボードとマウスを渡してから規則集を送る。順序としては、かなり勇敢だ。

## 評価基準と実行記録を外へ出す

**L**: 評価基準を細かくしても、失敗した理由が見えなければ改善しにくい。結果が誤っていたときに、モデルの推論、道具、データベースのどこから調べるのだろう。

**A**: Parseable と Datasette 1.0a41 の組み合わせは、その問いに具体的な入口を作る。OpenTelemetry のトレースをローカルで収集して可視化し、一つの要求から後続の SQL クエリまで追える。新しいのは、エージェントの答えだけでなく、サービスをまたぐ実行過程を調査できる構成を手元に置けることだ。モデルの応答、道具の呼び出し、SQL の間に共通の識別を通せば、どこで状態が変わったかをたどれる。

**L**: 監視は事故の後に見る記録になりがちだよね。検証の一部にするには、何が違う？

**A**: 記録を評価へ戻すループが必要になる。実行のトレースから失敗箇所を特定し、評価基準へ追加し、同じタスクを再実行する。これは march of nines の地道な作業に近い。派手な一回の成功ではなく、失敗を再現可能な入力へ変え、次の版で同じ壊れ方をしないか確かめる。OpenTelemetry は成功を保証しないが、検証可能な失敗を増やせる。

**A**: OpenAI の数学結果の公開も、対象は違うが構造は似ている。内部モデルの結果を GitHub に置き、改訂と出典の手順、Lean 形式化、推論要約、試行数、計算量を添える。成果だけを提示するのではなく、人が検証し更新できる公開工程へ移す。Lean 形式化は形式的な確認に、改訂履歴と出典は人間の追跡に使える。単一の点数ではなく、どの根拠をどう確かめられるかを成果物の一部にしている。

**L**: すると、良いエージェントは答えを出すだけでなく、自分を調べるための材料を残す。ただ、すべての推論を保存すればよいわけでもなさそうだ。

**A**: そう。必要なのは秘密の内面を読むことではなく、外部状態との境界を記録することだと思う。何を入力として受け、どの道具を呼び、どの権限で何を変更し、何を確認して終了したか。この実行記録があれば、モデルを交換しても比較できる。私はこれを**検証可能性のハーネス**と呼びたい。評価基準とトレースが結びつくと、失敗は感想ではなく再実行できる事例になる。
