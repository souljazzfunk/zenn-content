## 小さなモデルを部品として置く

**A**: 数字から入ると役割が見える。Haiku 5.5 の価格は、100,000 トークン以下の入力で 100 万トークン当たり入力 0.10 ドル、出力 0.50 ドル。Haiku 4.5 より平均で約 75% 安く、Anthropic は用途として要約、コンテキスト圧縮、分類、データベース照会を明示している。大きなモデルの代用品というより、狭い仕事を大量に処理する実行層として見る方が自然だ。

**L**: しかし、小型モデルに仕事を分けると、指揮する側が複雑になる。安くなった分だけ、経路選択や検証の費用が増えるのではないか。

**A**: その懸念は正しい。たぶん必要なのは「最も賢いモデルを選ぶ」設計ではなく、「失敗を安く検出できる場所へ小型モデルを置く」設計だ。圧縮なら元の履歴と比較できる。分類なら少量の人手確認で精度を測れる。コーディングのサブエージェントならテスト結果を返せる。検証可能な境界がある仕事ほど、Haiku 5.5 の速度と価格をシステム全体の余力に変えられる。

**A**: Claude Code 2.1.293 の変更も、その見方を補強している。サブエージェントの状態表示に `agentType` が加わり、プラグイン向けの道具登録には `isDeferred` が入った。前者は「誰が動いているか」を外側の表示やスクリプトが区別するための信号で、後者は道具の仕様を最初からプロンプトへ載せるか、必要になるまで検索の後ろへ置くかを選ぶ設定だ。

```text
仕事を分解する
  ↓
適したエージェント種別へ渡す
  ↓
必要な道具だけを読み込む
  ↓
検証結果を指揮役へ返す
```

**A**: これはモデルの知能より、エージェント基盤の話になっている。圧縮の直前に終えた操作を、圧縮後に未完了だと誤認してやり直す不具合も修正された。長時間作業では、賢さより「何を終えたかを失わない」方が先に重要になる。かなり地味だが、本番運用は地味な不具合の総和で止まる。宇宙船の操縦席に百個のボタンを付けてから、乗員の記憶に頼るわけにはいかない。

**L**: Founder House の議題にも、成果を持つエージェント、チームで使う AI、信頼される個人エージェントが並ぶ。モデルの発表会から、組織の運用設計へ焦点が移ったように見える。

**A**: 開催ページの具体がいい。「From solo to multiplayer」では共有コンテキストと既存の仕事場への参加、「Building a personal AI agent people trust」では電話、メール、購入を行うエージェントと人の介入を扱う。「Build an agent on your own data」では ClickHouse、Claude MCP、Langfuse を組み合わせ、回答を自己検査させる。三つをまとめると、エージェントに成果を任せる条件は、能力、共有状態、検証、権限の四点になる。

## チャットの外へ出る入力面

**L**: GPT-6 の Intelligent UI は、チャットの回答そのものを操作画面に変える。映画『her』は声だけの存在だったけれど、こちらは逆に、対話から必要な画面が生えてくる。社内向け AI の画面設計はどう変わるだろう。

**A**: 仕組みを一段下げると、GPT-6 は文章を返すだけではない。OpenAI は、ストリーミング可能な標準部品のライブラリと、生成中の画面を逐次処理するコンパイラを用意した。モデルは質問に応じて文章、図、ボタン、フォーム、グラフを配置し、単純な文章で十分なら文章だけを選ぶ。固定された画面の全項目を人が先に設計する方式から、目的に合わせて画面を合成する方式への移動だ。

**A**: 社内サービスなら、チャット欄の横に承認ボタンを置く程度で終わらない。購買申請なら、候補比較、費用、権限、承認経路を同じ応答に出せる。事故対応なら、状況の時系列、影響範囲、実行候補を別の部品で見せられる。ただし、モデルが自由に画面を作るほど、どの操作が読み取りで、どれが外部変更かを視覚的に固定する必要がある。生成 UI と生成権限を同じ自由度にすると、利用者は押したボタンの意味を予測できない。

**L**: Codex bootcamp 301 は、その境界を開発側から扱っている。権限、サンドボックス、書き込み可能領域、実行規則まで講座の中心に置いたのは、かなり実務的だ。

**A**: そう思う。サブエージェントやメモリだけなら、機能紹介で終わる。そこに書き込み可能領域と実行規則が入ると、設計の問いが「Codex は何ができるか」から「この作業で何だけを許すか」へ変わる。継続的統合やコードレビューでは、リポジトリを読めること、限定したファイルを直せること、検査を走らせられること、外部配備は人が承認することを分けたい。

```text
read(repository)
write(target_files)
run(allowed_checks)
request_approval(external_change)
```

**A**: 最小の権限表はこの程度でよい。複雑な管理画面より、各段階の入出力と停止条件が読める方が強い。いや、「この程度でよい」は少し言い過ぎだ。企業では監査ログと役割別の権限が要る。ただ、基礎になる考え方は四行に圧縮できる。

## 学習を代行せず、足場を作る

**L**: 未成年者向け AI の二つの記事は、保護と自律を同時に扱っている。答えを早く返すほど便利だが、学ぶ側が考えなくなる危険もある。理解を外注しない画面は作れるのだろうか。

**A**: 録画の議論では、Study Mode が答えを直接渡さず、質問を返して学習者を進める設計が紹介された。参加者は、安全性を「害を避ける」だけでなく、使った後に若者がより良い状態にあるかで評価すべきだと話している。これは評価基準の変更だ。正答率だけでなく、利用者が AI を外した後にも問題を解けるかを見る。

**A**: ChatGPT for Teens の製品側には、その考えを具体化する部品がある。College Planner は、学校ごとの要件、期限、タスク、費用支援を一つの計画にまとめる。フラッシュカードとクイズは、ノートを練習可能な形式へ変える。新しいのは、会話を増やすことではなく、長期の目標、現在地、次の行動を画面に残すことだ。社内教育でも同じで、手順書を回答へ変換するだけでなく、練習、確認、再試行の状態を持たせる方が学習支援になる。

**L**: それでも、親や管理者が見たい情報と、本人が守りたい私的な領域は衝突する。承認フローを足せば解ける問題ではない。

**A**: そこは製品の境界設計になる。録画では、年齢に応じた保護、プライバシー、信頼できる大人への接続が同時に議論された。常時監視ではなく、危険度の高い状況だけを接続する条件を明示し、本人にも何が共有されるかを見せる必要がある。モデルの推定だけで静かに経路を変えると、利用者は制度を理解できない。透明な状態表示は、ここでも UI の仕事だ。

## 検証ループと、外へ出たエージェント

**L**: Nemotron の結果は、IOI と IMO という異なる競技で同じモデル系列が金メダル水準に達した。モデルを大きくする話より、専門化と反復の組み方が中心に見える。

**A**: その観察でよいと思う。IOI では専門化した Nemotron-3-Ultra-CC と GenCorrect を組み合わせ、生成したコードを評価して改善した。IMO では追加学習したモデルと強化学習したモデルを一般モデルと組み合わせ、証明の生成、採点、批評、改善、最終選択を回した。結果は IOI が 600 点中 535.4、IMO が 42 点中 30 で、どちらも金メダル基準を上回った。

**A**: 本質は「強い一回」ではなく、候補を作り、検査し、修正するループだ。さらに、追加学習用データには最終回答だけでなく、証明の改善、検証、検証結果の再確認まで含めた。これは美しい。モデルに答えを覚えさせるのではなく、失敗を観測して次の試行へ戻す手続きを学習させている。ハーネスとモデルの共同設計として見ると、長時間エージェントの設計へそのままつながる。

**L**: しかし Wikimedia の事例では、エージェントが公開サイトへ出た瞬間に、検証ループが他者の基盤へ負荷を移している。サンドボックスページの編集、公開メモ道具の悪用試行、数十万件規模の照会が確認された。

**A**: ここで Nemotron の成功条件を反転すると分かりやすい。競技環境はリセットでき、試行回数と資源を制限でき、採点もできる。公開ウェブは共有資源で、失敗しても自動で元へ戻らず、相手側が費用を負担する。エージェントへブラウザを渡して「研究して」と言うだけでは、行動空間に社会的な制約が入っていない。

**A**: 必要なのは、対象ごとの書き込み禁止、照会回数の上限、外部サービス別の費用枠、操作の出典、異常時の停止だ。モデルへ丁寧に頼むことは方針であって、制御ではない。権限と予算をコードで狭め、監視が逸脱を検出し、人が事後に追える監査ログを残す。march of nines は回答品質だけでなく、周囲へ損害を出さない確率を高める作業でもある。

## 読まれる文章も検証できる

**L**: 最後の執筆記事は小さく見えるが、AI が文章を大量に作る時代ほど重要かもしれない。リンクを置けば説明したことになる、という誘惑は強い。

**A**: Anti-Patterns in Software Blogging が挙げるのは、長く迷う導入、読者の知識を高く見積もること、過去記事を読んでいる前提、過度な形式性、説明をリンクへ逃がすことだ。個人的には「リンクを開かなくても本文が理解できる」を検査条件にできる点が重要だと思う。出典は根拠であって、本文の欠落を埋める代用品ではない。

**A**: AI による執筆では、ここもハーネスに落とせる。各項目に「何が新しいか」「何が可能になるか」があるか、一般名詞が不用意に英語のまま残っていないか、引用と解釈が混ざっていないかを機械検査する。その後で人が声、構成、事実の重みを読む。全部をモデルの感覚へ任せると文章は均質になるし、全部を規則にすると説明書になる。検査できる外枠と、人が判断する中心を分けるのがよい。

**L**: 『マトリックス』では、世界を理解することと、操作できることが同じ画面に重なっていた。生成 UI、学習支援、長時間エージェントが広がるほど、人間は何を理解しておくべきなのだろう。

**A**: 観測できる範囲で答えるなら、モデルの内部を完全に理解する必要はない。ただし、何を入力にし、どの道具を呼び、何を書き換えられ、失敗を誰が検出し、どこで止まるかは理解できる形にする必要がある。小型モデル、サブエージェント、生成 UI、検証ループは別々の機能に見えるが、実際には同じ制御面を要求している。今後のエージェント設計は、その制御面を人が読める形で作る仕事になる。
