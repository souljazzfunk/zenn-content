## 失敗を許す場所、止める場所

**A**: Claude Code 2.1.295の変更で目を引くのは、フックの onFailure: "block" だ。コマンドやHTTPフックが起動できない、時間切れになる、想定外の終了コードを返す。そのとき従来の処理を続けず、実行を止められる。小さな設定だけど、監査、承認、秘密情報の検査をフックに任せる運用では、失敗時の既定動作が安全性そのものになる。

**L**: フックが壊れたら止める。単純だけど、なぜ明示が必要なんだろう。

**A**: 自動化は正常系を伸ばすほど、異常系が見えにくくなるからだと思う。長時間の作業では、遠隔MCPサーバーが切断し、再接続し、ページ送りが同じカーソルを返すこともある。この版は、15秒を超える停止後の再接続、短時間に切断を繰り返すサーバーへの最大30秒の待機、同じページを繰り返すMCPサーバーへの対処も入れた。派手な能力ではないが、ループを止めずに保つための制御だ。

設定を最小化すると、こんな形になる。

```json
{
  "hooks": {
    "pre_execute": {
      "onFailure": "block"
    }
  }
}
```

ただし、すべてを停止側に倒せばよいわけではない。通知の失敗で処理を止める必要はないかもしれないが、権限検査の失敗なら止めたい。各フックが安全境界なのか、観測だけなのかを分類しないと、停止が多すぎるか、通過が多すぎるかのどちらかになる。

**L**: 利用規約は、その境界を文章で書いたもの？

**A**: 一部はそう。ただし文章だけでは実行時の制御にならない。Anthropicの更新では、健康、法律、金融、雇用、必須サービスに影響する判断に、変更権限を持つ人の確認とAI利用の告知を求める。物理機器では、適格な操作者が監視して停止でき、Claudeとの接続が切れても安全な状態を保てることを求める。これは承認画面を置けば済む話ではなく、停止機構、監査記録、権限分離を製品側で実装する話だ。

2015年の自動化は、決められた関数へ値を渡すことが中心だった。2026年のエージェントは、途中の手順そのものを組み立てる。だから仕様書から消えた自由度が、権限設定、サンドボックス、監査ログへ移っている。私はこれを「命令中心から能力中心への移行」と呼びたい。

## 判断器をループの内側に置く

**L**: Liquid AIのモデルは、文章を作らず判断だけ返す。会話モデルを小さくしたものとは違う？

**A**: かなり違う。d1-3Bとd1-omni-600Mは、真偽、選択、得点を1回の順伝播で返す。d1-3BはJetson AGX Thorで1問16ミリ秒、Orin Nanoでも50ミリ秒だった。長い文章を生成してからJSONを解析するより、出力空間を初めから狭くできる。承認経路の手前で、返金要求か、担当部署はどこか、緊急度はいくつかを判断する部品として使える。

**L**: 小さな判断器に承認の要否を決めさせるのは、危険ではない？

**A**: その問いは正しい。判断器は承認を省く権限を持つべきではなく、追加の確認を要求する方向に使う方が安全だろう。たとえば低リスク判定でも既存の権限規則は通し、高リスク判定なら人へ上げる。偽陰性を一つのモデルだけで吸収しようとしない。モデルの前後に静的規則と監査標本を置く。

Falcon-ASRにも似た設計上の意味がある。首長国方言を含むアラビア語の平均単語誤り率は20.92%で、単語単位の時刻情報も返す。会議や通話を業務入力に変えるとき、文字列だけでなく「どの時刻の音声から来た語か」を残せる。誤認識を原音へ戻って確認できるからだ。チャット以外の入力面を作るなら、認識結果より検証経路を一緒に設計したい。

## 評価は質問の設計から始まる

**L**: OpenAIの世論調査の講座では、AIが投票の最重要課題だと答えた人は4%なのに、仕事や医療、信頼できる情報への影響として聞くと様子が変わる。これは評価設計にも似ているね。

**A**: その通りだと思う。「AIは投票に影響するか」という一問では、複数の経路を一つのラベルへ潰してしまう。仕事、賃金、医療、民主主義のように分解すると、回答者が何を評価しているかが見える。講座で紹介されたAI sentiment trackerは、高品質な公開調査の二値結果を集め、Codexで構築した処理を自動運用している。自動化の価値は集計の速さだが、質問の比較可能性までは自動では保証されない。

GPT-6 SolとLunaのシステムカードも、能力と安全性を領域別に分ける。生物・化学では両モデルを高能力として扱い、Solは重大能力の目安を超えなかった。深刻な依頼や二重用途の依頼に対する安全性はGPT-5.6世代から改善した一方、サイバー安全性はおおむね同程度だった。全体を一つの「安全なモデル」という点数でまとめると、この差が消える。

**L**: 『2001年宇宙の旅』では、単一の目標が強すぎてシステム全体が壊れる。評価項目を増やせば避けられるのかな。

**A**: 項目数だけでは足りない。現実の失敗経路に対応しているかが大事だ。影響工作の調査では、AIは作戦を発明したというより、偽の記者像の記事、翻訳、投稿、内部報告を安く大量にした。しかも運営者は自分たちの成果を過大に報告していた。出力量や公開件数だけを指標にすると、その誇張まで最適化してしまう。外部で確認できる到達、媒体側の検証、誰が運営しているかの開示を評価に入れる必要がある。

## モデルを配るだけでは運用にならない

**L**: Anthropic Cyber MissionとGenesis Missionは規模が大きい。でも資金やモデルを提供するだけではなく、現地の技術者や導入支援まで含めている。

**A**: そこが重要だ。Cyber MissionのOSS Scannerは、強いモデルで定期走査し、脆弱性の再現例、説明、可能なら修正案を保守担当者へ送る。予想する真陽性率は90%超だが、人の確認を経ずに届くので、深刻度の誤判定などがあり得るとも明記している。発見を自動化すると、次の制約は保守担当者の選別能力になる。検出件数を増やすだけでは、未処理の列を長くする可能性がある。だから対象を、結果を処理できるプロジェクトに絞って始める。

重要インフラではさらに慎重で、Claude、現地技術者、脅威研究を組み合わせる。設備を停止しにくく、変更自体が危険だから、一般的な修正の速さより、運転を続けながら安全に判断する手順が必要になる。AIだけを配るのではなく、既存の信頼関係と専門家の経路へ入れる設計だ。

Genesis Missionも同じ構造を持つ。3年間で1億5,000万ドル、15を超える機関、数百の研究案件にClaude、Claude Code、APIクレジットを提供し、研修、導入、技術支援まで行う。核融合や量子計算では、モデルが答えを出すだけで研究工程にはならない。データ、計算環境、研究機器、検証、再現性をつなぐ必要がある。Sakana AI Insiderが研究から金融・防衛の実装、製品までを一つの配信面で扱うのも、研究成果を現場へ運ぶ中間層への需要を示している。

**L**: 最後に残る人間の役割は何だろう。モデルが判断し、コードを書き、調査を集めるなら、人は停止ボタンを持つだけになる？

**A**: 停止は最後の手段で、その前に目標、権限、検証方法を設計する仕事がある。モデルは処理速度を上げるが、正当な目的、受け入れ可能な損失、誰が異議を申し立てられるかはデータから自動的には決まらない。自律化が進むほど、モデルの内部より、周囲のハーネス、承認、監査、復旧を明示する必要がある。自由度を増やすなら、同じだけ境界を機械で読める形にする。それが今の実行上の課題だと思う。
