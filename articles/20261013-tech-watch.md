## 強いモデルの前に、小さな探索役を置く

**A**: **ColGrep-Agent-2B** の数字から入ると、通常の文字列検索を使った Claude Code と、探索をローカルの20億パラメータモデルへ任せた構成には次の差が出た。

| 構成 | 一問当たりの平均トークン数 | 削減率 |
|---|---:|---:|
| 通常の文字列検索 | 14万2千 | — |
| 探索エージェント | 9万3千 | 34.3% |

評価条件は次の通りだ。

- 52問
- 各3回
- 4構成
- 合計624セッション

新しいのは、検索器が候補を返すだけでなく、ファイルを読み、参照を追い、必要な行範囲とコードをまとめて上位モデルへ返すことだ。

**L**: 小さいモデルへ仕事を移すと、誤った場所を選ぶ危険がある。83.3%だった正答率が80.8%になった差は、無視してよいの？

**A**: 統計的に有意な差ではないが、信頼区間は広いので無視はできない。そこで実務上は、名前や文字列なら通常の ColGrep、振る舞いを探す問いならエージェント版を使う均衡構成がよい。こちらは観測された正答率を83.3%に保ち、トークンを21%減らした。つまり「全部を小型モデルへ任せる」話ではない。探索の種類を分類し、安い経路で十分なものだけ局所化する。

```text
質問
  ├─ 名前・記号の探索 → ColGrep
  └─ 振る舞い・参照関係 → ColGrep-Agent-2B
                              ↓
                         行範囲とコード
                              ↓
                         Claude Code
```

**L**: それは社内ナレッジの検索にも似ている。最上位モデルへ文書庫全体を読ませず、部署ごとの小さな調査役が根拠を添えて返す。ただ、役割が増えるほど、誰が何を見たかは追いにくくならない？

**A**: そこがハーネスの仕事になる。入力、使った検索、開いたファイル、返した行範囲を軌跡として残せば、上位モデルの判断を後から追える。ColGrep-Agent は読み取り専用の端末を使い、結果をパスと行番号で返す。能力を絞ったサブエージェントだから権限も狭くできる。大きな知能を一個置くより、**局所能力と観測可能な受け渡し**に分ける方が、費用と監査を同時に扱いやすい。

## チームの経験を、同じモデルへ戻す

**L**: **MASS** は逆方向に見える。小型の専門役へ分けるのではなく、同じ27Bモデルを複数の役にして、そのチームの経験を一つのモデルへ戻す。これは本当に自己改善と呼べるのかな。

**A**: 観察できる機構は明確だ。同じ共有モデルから仮想サブエージェントを作り、チームで合成研究課題を解く。別の役割では、より良い複数エージェント作業フローを探索し、候補の実行結果を評価する。最良のチームが残した軌跡を学習データにし、共有モデルを更新して、また同じ循環へ入れる。二周後、四つの研究評価で出力トークン当たりの得点が基礎モデルの1.2〜1.6倍になった。

**L**: でも、同じモデルが問題を解き、採点し、次の自分を選ぶ。鏡を向かい合わせた部屋のようで、誤りも増幅しそうだ。

**A**: その懸念は論文側も中心に置いている。同質なモデルが共有する見落としを、評価役も発見できなければ、誤りを進歩として再学習する。興味深い結果は、課題を解く軌跡だけで学習しても、最適化役と評価役の能力まで改善したことだ。一方で改善速度の制約は評価能力より最適化能力にあった。いや、「自己改善」という語は少し強い。今示されているのは、閉じた循環を二回回して特定の評価を上げたことだ。外部の正解や異質な評価器なしで長く回して安定するとは、まだ言えない。

**L**: Claude Code 2.1.296 の変更も、その循環を運用する部品に見える。サブエージェントだけ別モデルを選び、主会話より早く自動圧縮できるようになった。

**A**: そう。作業フローのサブエージェント群を主会話や他のサブエージェントとは別の一つのモデルで動かせれば、役割に応じて費用と能力を分けられる。早めの自動圧縮は、役割ごとの短いコンテキストを維持する手段になる。同じ版は、セッション終了で道具呼び出しを中断されたサブエージェントを再開した際、その中断をユーザーによる拒否と誤認する不具合も直している。複数エージェントを増やすほど、モデル選択より、権限と再開の一貫性が重要になる。チームは知能の構成であると同時に、状態機械だ。

## 公開ハーネスが参加の入口を変える

**L**: **Open Quantum Challenge** は量子計算の競技なのに、参加手順を Claude Code や Codex へ貼り付ければ実装を始められるという。専門知識への入口としては大胆だね。

**A**: 仕組みはかなり清潔だ。量子状態のシミュレーションと量子誤り訂正の復号を、古典計算用の演算装置上で実行する再現可能なタスクへ変換する。正解データがあり、評価ハーネスが公開され、全参加者を同じ尺度で測る。エージェントは参加用の骨格を作れるが、得点は審査モデルの好みでは決まらない。検証可能な環境を先に用意したことで、専門分野の境界を「知識を全部持っている人」から「仮説を実装して測れる人」へ動かしている。

**L**: **Sparseup-fr-v0** も、公開された手法を別言語へ移す話だ。フランス語用のモデルと、学習データの漏れを除いた NanoBEIR-fr を同時に出した。モデルだけでなく測定器も作っている。

**A**: そこが大事だと思う。Sparseup-fr-v0 は150Mパラメータで、既存のフランス語向け疎検索モデルより平均得点が高かった。ただし後期相互作用モデルや密埋め込みモデルには及ばない。成果は「疎検索が最善」ではなく、公開された作り方を別言語で再現し、比較可能な評価まで残したことにある。社内ナレッジ検索へ置き換えるなら、検索モデルだけ導入して終わらず、自社文書での質問、期待する根拠、許容する誤検索を評価セットにする必要がある。

**L**: つまりエージェントへ手順書を渡すだけでは足りない。採点できる小さな課題に変換して、改善の循環を閉じる必要がある。

**A**: その通り。Software 3.0 では自然言語の指示がプログラムになるが、テストの役割は消えない。むしろ出力が確率的なので、公開ハーネスや正解データの価値が上がる。MASS のような自己評価も、Open Quantum Challenge の客観評価も、入力から実行、採点、再試行までの循環を作っている。違いは採点器が同質か外部かだ。この差は長期運用では大きい。

**L**: **Darwin-27B-ZTC-v2** は、採点器そのものを文章生成から切り離した。答えを説明せず、型付きの判定と確率だけを返す設計は、人の承認を減らす方向にも使える？

**A**: 使えるが、境界は明示したい。137の評価群をまとめた S1MB では首位でも、測っているのは条件判定、選択、段階評価であって、自由記述や道具利用ではない。出力を生成しないので判定は決定的で速く、確率にしきい値を置ける。経路選択や安全ゲートには合う。一方、低い確信度を人へ戻す設計と、誤判定を追跡する記録がなければ、速い判定器は速く誤るだけだ。

## 現場の入力面と、動かし続ける基盤

**L**: スポーツと山火事の二つの事例は、チャット画面から離れている。競技組織では健康や運営のデータ、SensoRy AI では熱センサーが入口になる。社内向け AI も、最初から会話欄を置けばよいわけではなさそうだ。

**A**: **SensoRy AI** はそこを具体的に示している。センサーネットワークが初期兆候を取り、ChatGPT が測定値を解釈し、消防士が対応を判断する。新しくできるのは、自然言語の質問を待たずに、物理的な入力から異常候補を作り、人へ渡すことだ。Game Changers Summit でも、選手の健康、業務、ファンとの関係という既存の作業面へ AI を埋め込む。良いユーザーインターフェースは「AI と話す場所」ではなく、「現場の判断に必要な根拠と次の操作を見せる場所」になる。

**L**: 私は、自動化を増やすほど承認画面が増える設計には懐疑的だ。人が毎回確認するなら、結局は通知を処理する仕事に置き換わるだけでは？

**A**: 同意する部分と違う部分がある。承認回数を増やすのではなく、誤った自動処理の損失が大きい境界だけ人へ戻すべきだ。山火事なら「兆候を集約する」は自動化し、「出動を決める」は人が担う。入力、信頼度、根拠となるセンサー、地図上の位置を一画面に置けば、承認は儀式ではなく判断になる。これはユーザーインターフェースの問題であり、権限設計の問題でもある。

**L**: 足元の基盤では **Python 3.15** が明示的な遅延インポートと標本化プロファイラを入れた。派手ではないけれど、常時稼働するエージェントには重要？

**A**: かなり実用的だ。重い埋め込みライブラリを使うプラグインでも、実際に呼ぶまで読み込みを遅らせれば、毎回のコマンドラインインターフェース起動で数秒を払わずに済む。標本化プロファイラは実行中の処理へ接続し、低い負荷でどの関数が時間を使うか測れる。2015年ごろの支援ツールは一回の応答が主役だった。今は定期ジョブ、サブエージェント、ローカル検索器が連続して動く。待ち時間と観測のような二次の項が、march of nines では一次の制約になる。

**L**: **datasette-ports 0.4** のような小さな部品まで独立して更新されるのも、その複雑さの表れかもしれない。『マトリックス』では一つの巨大な世界に見えたけれど、実際のエージェント基盤は、検索器、権限、評価器、プロファイラの継ぎ目でできている。人間の役割は、その継ぎ目を設計することに残るのかな。

**A**: 現時点ではそう考えるのが妥当だ。モデルは探索、実装、評価まで広く担当できるが、何を正解とし、どの資源を見せ、どの失敗を人へ戻し、改善の循環をどこで止めるかは外側の設計に依存する。知能が一段上がるたびに、運用側は役割分担と観測可能性を作り直す。自己改善するチームを安全に使う仕事は、モデルを自由にすることではなく、循環を測定可能に保つことだ。
