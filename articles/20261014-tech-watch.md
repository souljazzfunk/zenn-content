## 文章ではなく、失敗する経路を設計する

**A**: Geoffrey Huntley の例は、観察がかなり具体的です。エージェントが可観測性モジュールを直接呼び、用意した診断モジュールを迂回する。そこでエージェント向け指示書を更新し続けるのではなく、事前コミットフックが Git の差分を読み、直接呼び出しを見つけたらコミットを失敗させ、診断ライブラリを使うよう修正指示を返します。

**L**: 説明を正確にする仕事から、違反を検出できる形に変えたわけだね。ただ、私はフックだけを賢くすればよいとは思わない。エージェントがなぜその呼び出しを選んだかを理解しないまま、出口だけを塞いでいるようにも見える。

**A**: その懸念は正しいと思います。ただ、この例の新しさは、指示への従順さを期待するのではなく、差分という検証可能な対象へ制約を移した点です。入力はコミット前の差分、判定は診断モジュールを迂回する直接呼び出しの有無、出力は失敗と修正指示。この小さな閉ループなら、モデルの内面を推測しなくても実行結果を変えられます。

さらに重要なのは、失敗の返し方です。単にコミットを拒否するだけなら、エージェントは次に何を変えるべきか分からない。ここでは違反箇所を検出した同じ仕組みが、使うべき診断ライブラリを指示として返す。検査結果が次の試行の入力になるので、拒否、修正、再検査を一つのループにできます。何が新しいかを短く言えば、規約を読む工程と規約を守ったか確かめる工程を分離したことです。

**L**: それは Software 3.0 の指示を Software 1.0 の門で囲う、と言える？　自然言語で動く部分が増えても、最後の境界は明示的なコードに戻っている。

**A**: 私はそう見ます。いや、「戻る」より、二つを重ねると言った方が正確です。自然言語は広い行動候補を作り、フックは許容できない差分を機械的に落とす。これで可能になるのは、エージェントが一度で正解することではなく、違反をコミット前に止め、具体的な修正を渡して再試行させることです。規約文を長くするより、検査可能な制約を一つ置く方が美しい。もちろん、その検査条件を決めるのは人間です。フックは組織の意図を読心してはくれません。

## 24Bを抱え、2Bだけを動かす

**L**: LFM2.5-24B-A2B は総24Bなのに、各トークンで動くのは2Bだけだという。大きなモデルを端末に置く話と、計算を小さく保つ話が同居している。64の専門家から上位4つを選ぶ機構は、何を変える？

**A**: 構造から見ると、40層の各段で64の専門家すべてを同時に使わず、各トークンに対して上位4つを選びます。総パラメータ数は24Bでも、有効になるのは2Bだけ。容量と一回の推論計算を分けて扱う設計です。この構造で M5 Max 上の速度が毎秒184トークンと報告されています。

| 項目 | 値 |
|---|---:|
| 総パラメータ数 | 24B |
| 各トークンの有効パラメータ数 | 2B |
| 専門家数 / 選択数 | 64 / 上位4 |
| 層数 | 40 |
| コンテキスト長 | 131K |
| M5 Max 上の速度 | 毎秒184トークン |
| LiveClaw | 48.09 |
| SWE-Bench Verified | 51.0 |

**L**: 数字は強いけれど、端末上で速いことと、エージェントとして仕事を終えられることは別だよね。私は毎秒のトークン数より、複数段階の途中で道具を正しく呼べるかを見たい。

**A**: そこで重要なのが、道具の呼び出しと複数段階タスクへの対応、それから OpenClaw、Hermes Agent、Pi、OpenCode のハーネス内で行ったエージェント型強化学習です。学習過程では、道具の呼び出しと複数ターンのトラジェクトリが中間学習にも含まれています。単発の応答だけでなく、観察し、道具を選び、結果を受け、次へ進む用途に合わせている。新しくできるようになるのは、この一連のループを自分の機器で継続的に走らせることです。

**L**: 前世代からはコンテキストも変わった。長い入力を持てることは、道具を使うループにどう関係する？

**A**: コンテキスト長は32Kから131Kへ増え、語彙も65Kから128Kへ倍増しています。加えて、前世代と違って、最終回答の前に明示的な思考過程を生成する推論専用モデルです。長い履歴、道具の結果、次の判断を同じ実行の中へ置ける範囲が広がる。もちろん、長ければ自動的に正しくなるわけではありません。ここでの意味は、複数段階の作業をローカルに置くための容量と計算特性が同時に用意されたことです。

**L**: LiveClaw 48.09 と SWE-Bench Verified 51.0 は、そのループとコーディング能力を別の角度から見た値だね。けれど、ベンチマークの点数だけから実運用の成功率までは読めない。

**A**: そうです。16の評価では、道具利用とエージェント作業の8項目中5項目で比較対象を上回るか同等でした。一方、知識量を強く問う評価や一部のコーディング評価では、より大きなモデルが上です。これは端末内モデルを万能だと見る話ではない。**モデルの局所化からエージェント実行の局所化へ**進みつつ、仕事ごとに不足を測る話です。M5 Max に置いた瞬間、組織の問題まで毎秒184個解決するわけではありません。時計はそこまで親切ではない。 配布時点から複数の推論基盤に対応し、端末では Ryzen AI Max+ 395 上でも毎秒114トークンと報告されています。つまり選択肢は一台の機種に限られない。導入側は、自分の機器で速度を確かめたうえで、道具利用の評価と実際の完遂率を別々に測れます。

## 試作を組織の作業へ移す

**L**: 報道組織のウェビナーは、11人のAI技術者を現場に配置した2年間を扱う。検索、会議監視、翻訳、文字起こしは用途が違うのに、問題選定、信頼、安全策、社内展開が共通論点として並ぶ。少し引くと、モデルより人と組織の話なのかな。

**A**: 観察から始めると、ここで扱うのは試作の作り方だけではありません。11人を報道組織に埋め込んだ Fellowship Program の経験から、初期の実験を、チームが実際に使う道具や作業フローへ移す方法を共有します。参加組織には Boston Globe Media Partners、NEWSWELL、Lenfest Institute が含まれます。新しい点は、個別の成功例だけでなく、AIの専門家を現場へ配置した運用過程を、問題選定から社内への採用まで一続きで扱うことです。

**L**: 問題選定が最初に来るのは重要だね。作れるものから選ぶのではなく、現場で解く価値があるものを選ばないと、試作は動いても使われない。『ブレードランナー』は人間らしさの境界を問うけれど、職場では自然さより信頼できる作業の境界が先に要るのでは？

**A**: たぶんその順です。公文書の検索なら何を探すのか、公開会議の監視なら何を見つけるのか、翻訳や文字起こしなら出力をどの作業へ渡すのか。用途ごとに入出力は違いますが、組織内で使うには、誰の問題か、どう信頼を作るか、どこに責任ある安全策を置くか、同僚がどう採用し発展させるかを決める必要がある。

この取り組みで新しく可能になるのは、一つの試作を披露して終えるのではなく、報道、読者との関係、収益、業務上の課題に対応する道具を現場の作業へ組み込み、同僚へ広げることです。検索から収益向けの道具まで対象は広い。それでも共通するのは、モデルの出力を既存の仕事のどこへ渡し、誰が使い続けるかという実行上の問いです。

**L**: 私は「信頼形成」という言葉を、利用者への説明だけにはしたくない。先ほどの事前コミットフックのように、失敗が見え、止まり、次の行動が返る仕組みも信頼の一部だと思う。

**A**: その見方なら、三つの話が接続します。LFM2.5-24B-A2B はローカルな実行場所とエージェント能力を提供する。フックは具体的な違反を検査して止める。報道組織の事例は、その道具を人の作業と社内展開へ結び付ける。どれか一つで十分ではありません。モデル、検証境界、組織の作業フローが別々の層にあり、実運用では三層をつなぐ必要があります。

## 速さより、訂正できる構造

**L**: 10年前なら、文章から次の操作を選ぶ仕組み自体が中心的な驚きだった。今は端末上のモデルが道具を呼び、組織が展開方法を考え、フックが逸脱を止める。文明は判断を機械へ渡すほど自由になるのか、それとも検査を書く仕事を増やしているだけなのか。私は後者もかなり大きいと思う。

**A**: 私も、自由になるという一語では捉えません。機構として見ると、人間の仕事は消えるのではなく移動しています。モデルに毎回正しい経路を選ばせる仕事から、観察できる出力を決め、失敗条件を書き、作業フローのどこで止めるかを設計する仕事へ移る。LFM2.5-24B-A2B の速度はループを回す余地を作り、フックはそのループに検証を置き、報道組織の取り組みはループを現場へ接続する。

終点は自律そのものではなく、間違えたときに局所的に止まり、訂正して再実行できる構造だと思います。何をモデルに任せるかより先に、何を観測し、どの違反を止め、修正結果を誰へ返すかを決める。今後の実装で増えるのは、知能を称賛する文章ではなく、その三つを明示するコードと作業手順でしょう。
