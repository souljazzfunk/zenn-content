## 内部を見せることが、評価を制度に変える

**A**: Anthropicの発表で重要なのは、外部評価を依頼したという事実より、アクセスと公表権を分離して設計した点です。METRの6人は、顧客情報、弁護士との秘匿情報、モデル構造などの除外領域を除き、社内のリスク評価班に近い情報へ到達できます。しかもAnthropicが要求できるのは、事前に定めた機密区分の編集であって、評価結果の公表禁止ではありません。

> Anthropic can’t veto publication, but we can require them to redact information if it falls into narrow, predefined categories like the ones above.

出典: Anthropic「An update on independent evaluators」

**L**: そこは違いが大きいと思う。透明性は全部を公開することだと考えがちだけれど、危険な情報や顧客情報まで公開すればよいわけではない。では、独立性を失わずに秘密を守る境界はどこに置く？

**A**: 今回は三段階です。第一段階は限定した調査で、公表にはAnthropicの承認が要る。第二段階は情報範囲が広がり、公表前承認は不要になる。第三段階がMETR型で、社内に近いアクセスと独立公表を組み合わせます。これは**埋め込み型評価**として見ると分かりやすい。評価者を製品の外から呼ぶのではなく、開発組織の情報経路へ置きつつ、報告経路は組織の指揮系統から切り離す。監査を一回の試験ではなく、継続する運用にしています。

**L**: Claude Code 2.1.301の更新にも、判断を外から見られるようにする動きがある。細かな変更履歴だけれど、長時間動かす側には何が変わる？

**A**: OpenTelemetryの道具判断イベントに、許可方式、分類器の判定、遮断理由の分類が加わりました。無人再試行には利用上限の解除時刻が遠すぎる場合の待機上限を設定できる。作業フローエージェントが手順を飛ばしたのに成功扱いになる不具合も直った。入力は要求、出力は判断と実行結果、そして観測経路へ判定理由を流す。この三つが揃って初めて、失敗を再現して規則を直せます。

昨日の2.1.300が実行中の介入点を増やした更新だとすれば、2.1.301は**判断経路の可観測性**を詰めています。派手な能力追加ではないけれど、90%の成功を99%、99.9%へ近づける、信頼性を一桁ずつ上げる工程は、こういう記録と境界条件の修正です。運用では、成功例より失敗時の判定理由を集められることが次の改善を可能にします。

## 記憶を隠れた状態から操作面へ出す

**L**: My Fishは名前こそ親しみやすいけれど、表示しているのはかなり厳密な状態だ。記憶の内容だけでなく、いつ読まれ、どの返答で一緒に使われたかまで見せる。これはチャット画面に何を足したことになる？

**A**: **メモリの出所情報**です。My Fishの一覧には、分類、事実数、利用回数、最終利用日時が出る。個別項目から学習元の会話へ戻れます。関係図では、最近使った記憶を中央へ寄せ、利用頻度を大きさで示し、同じ回答に使った記憶を線で結ぶ。30日以上使われていない記憶は薄くなる。さらに会話中にも「確認した記憶」「新しく覚えたこと」が小さな表示部品として現れます。

これは単なる履歴画面ではありません。モデルの内部状態を説明しようとするのではなく、製品が保持した外部メモリの読み書きを利用者の操作対象へ戻している。利用者は元の会話を確認し、不要なら機能全体を無効にできる。社内向けAIなら、ここへ保持期限、共有範囲、削除、管理者方針を加えると、記憶が監査可能な業務データになります。

**L**: 『her』のOSは、覚えているから親密に見えた。でも現実の製品では、忘れ方と根拠を見せない親密さは危うい。自分は、記憶の量より訂正のしやすさを優先したい。

**A**: 同意します。いや、少し言い直すと、量と訂正は別の軸ではありません。訂正できない記憶は、増えるほど将来の回答へ誤差を配る状態です。My Fishが示した設計は、記憶を隠れた個人化から、観測・参照・無効化できる制御面へ変えることです。

OpenAIのStudy Modeも、答えを一度に出す代わりに、問い、ヒント、説明、理解確認を段階化します。教師は既知の教科で質問の質を確かめ、生徒の最終説明から復習点を判断できる。ここでもAIの賢さを前面に出すより、人が途中状態を見て介入できる流れを設計しています。

## 一つのモデルではなく、能力の切り替え方を設計する

**L**: Muse Spark Open、Apertus 1.5、Granite Switch 4.1は、規模も公開方法も違う。ただ、道具を使うモデルを運用する側から見ると、共通の問いがある。能力は一つへ詰め込むべきか、専門機能を切り替えるべきか。

**A**: Muse Spark Openは大きな統合型です。主な構成は次の通りです。

| 項目 | Muse Spark Open |
|---|---|
| 総パラメータ | 約8160億 |
| トークンごとの稼働 | 約420億 |
| 専門家 | 各層256個から8個を選択 |
| 入力 | テキスト、画像、音声、動画 |
| 文脈 | 最大100万トークン |
| 主用途 | 複数ファイル修正、長時間の不具合調査、道具呼び出し |

混合専門家構造なので計算は420億相当でも、重み全体はメモリへ置く必要があります。公開重みだからローカルで制御できますが、BF16版は約1.5TBで、実行基盤は小さくない。画像や画面録画を見ながらコードを直す共通の認知核としては魅力的で、配置費用との交換になります。

Apertus 1.5は別の価値を足しています。8Bと70Bの重みだけでなく、学習データ、途中の重み、強化学習と選好調整の資料、評価カードを公開する。文脈は従来の4倍に伸び、画像と音声を同じトークン列へ入れ、道具利用の学習には実行で検証したトラジェクトリを使います。能力そのものに加えて、どう作り、どう測ったかを再実行できる点が設計の中心です。

**L**: Granite Switchは逆に、一つの基礎モデルへ専門部品を差し替える。これを企業の道具管理に置き換えると、どう見える？

**A**: Activated LoRAが会話、安全判断、音声認識などの専門機能を切り替え、基礎モデルのKVキャッシュを共有します。一つの提供口で、音声を文字にし、要約し、有害性を判定する。全部を別サービスへ投げる構成より、状態の受け渡しとGPU使用量を抑えられます。

ここで共通するのは**能力の配線**です。Museは大きな共通モデルの内部で専門家を選び、Apertusは公開された学習・評価工程まで含めて能力を構成し、Graniteは専門アダプターを差し替える。社内エージェントでも、モデル名を一つ決めるより、入力形式、道具権限、評価器、専門部品をどの境界で切り替えるかが運用品質を決めます。

## 画面と端末が、エージェントの境界になる

**L**: FLUX.3の座標枠、詐欺検出の端末内処理、Antigravityの3次元表示。用途は離れているのに、人とAIが同じ対象を指すための面を作っているように見える。

**A**: FLUX.3 Image Kleinは、文章生成と複数参照画像の編集に加え、0から1000へ正規化した座標枠をプロンプトへ書けます。対象の配置や、参照画像のどの領域をどこへ動かすかを明示できる。生成画面における承認可能な中間表現です。言葉だけで「もう少し左」と繰り返すより、利用者とモデルが同じ座標を参照できます。

シンガポールの詐欺検出は、処理場所が境界です。軽量分類器が受信文を低消費電力で選別し、疑わしい場合だけ調整済みGemmaが広い会話文脈を確認する。利用者の同意のもと端末内で完結し、政府とGoogleは会話へアクセスしません。安全機能を強くするために中央へデータを集めるのではなく、二段階の計算を端末へ置いています。

Antigravityでは、蛋白質検索、ProtNLMによる機能予測、構造評価、文献統合を一つの作業環境へ集めました。研究者が3次元構造の残基を選び、注記すると、その視覚状態がエージェントへ戻る。エージェントも候補領域を強調して仮説を説明する。候補は実験検証中であり、AIが発見を確定したわけではありません。価値は、数日に分かれていたデータベース調査を一つの対話へ圧縮し、人が検証対象を選べることです。検索結果、立体構造、文献という異なる情報を同じ画面で指し示せるため、エージェントの提案をその場で採用、修正、保留できます。

**L**: 人間の役割は、最後に承認ボタンを押すだけにはならないと思う。何を見せ、どこを触れ、どの記録を外へ出せるかを決めること自体が仕事になる。文明がAIへ判断を渡すほど、その接点は増えるのだろうか。

**A**: 私の見方では、増えるべきなのは確認画面の数ではなく、検証可能な状態です。評価者には内部情報と独立した公表経路、利用者には記憶の出所と訂正経路、運用者には判断ログと停止条件、専門家には共有できる対象表現を渡す。モデルの能力が上がるほど、周囲には小さな制御面が必要になる。知能の問題に見えたものが、アクセス、状態、観測、再実行を設計するシステム工学へ移っています。
