## 能力の配布には境界が要る

**A**: 数字から入ると、Rosalind Academic Plan の 30 席、12 か月、既定で学習に使わない研究データという三点が重要だと思う。単に高性能モデルを安く配る企画ではない。研究室責任者が申請し、身元と所属、用途を確認し、権限を管理する。入力は研究者の課題で、出力は科学的な候補や分析だけれど、その周囲に審査、権限、監視のループがある。

**L**: 研究者に道具を渡すなら、制限は少ないほどよいとも思う。でも生命科学では、広く開くことと正当な研究を止めないことが衝突する。これはモデルの安全性だけで解ける問題ではなさそうだ。

**A**: そこは同意する。GPT‑Rosalind は、機関や研究室責任者、用途を確認する審査付きアクセスと、承認後の監視・執行を組み合わせている。モデルが賢いかより、正当な利用者へ必要な能力だけを渡せるかが運用の中心になる。

**L**: Anthropic の売上に蒸留目的の利用が含まれていたという話も、同じ境界の裏側かな。利用量は収益になるが、競合モデルの学習へ流れれば守る対象にもなる。

**A**: 5〜7% という比率が正確なら、アクセス制御を収益設計から切り離せない。API の利用者認証、異常な呼び出しの検出、推論過程の保護が製品設計と収益設計の両方になる。アクセス制御を最後に足す付属物ではなく、モデル提供の本体として設計する必要がある。

**L**: しかも Rosalind Academic Plan には API が含まれず、研究室責任者が記名利用者を管理する。これは不便というより、最初の運用範囲を人と画面のある場所へ絞った、と読めるね。

**A**: そう読める。自動処理へ直接つなげる API は、処理量も到達範囲も急に広がる。まず記名利用者、研究室責任者、安全担当という責任の線を作り、その中で実利用を観察する。提供開始時の境界を狭くし、検証結果に応じて能力を増やす方が、最初から全経路を開くより原因を追いやすい。

## エージェントを手元へ戻す

**L**: Beam は 5010 億パラメータ、Surface は最大 128 GB の共有メモリ。規模だけ見ると同じ机には載らない。それでも「所有して動かすモデル」と「ローカルエージェント向け端末」が同時に出てくるのは、方向としては一致している？

**A**: 一致している。ただし一台ですべてを動かす話ではない。Beam は各トークンで 230 億パラメータだけを計算するが、重み全体は保持する必要がある。4 ビット版でも約 280 GB だから、実用構成は複数 GPU になる。一方、Surface や新しい小型計算機は小さなモデル、埋め込み、分類器、秘密を含む前処理を担い、大きな推論だけクラウドへ送る。これは **ローカル優先のエージェント基盤** として見ると分かりやすい。

Surface Laptop Ultra は、ハードウェア、ファームウェア、システム層の保護を組み合わせるセキュアコア PC と端末暗号化も備える。共有メモリだけでなく、機密情報を端末に置く前提の保護も製品構成に含めている。記憶装置は交換・増設でき、修理ガイドと交換部品も用意される。最大 2 TB の記憶容量を選べるため、モデルや作業データも端末側に残しやすい。

```text
端末: 秘密の読み取り → 軽量判定 → 必要な情報だけ抽出
クラウド: 大きな推論 → 候補を返す
端末: 権限確認 → 実行 → 監査記録
```

Singapore の詐欺検出はさらに清潔な例だ。第一段の軽量分類器が疑わしい入力だけを選び、第二段の Gemma が会話の広い文脈を確認する。会話そのものは端末から出ない。巨大モデルを縮めただけではなく、機密性、電力、誤警告という制約に合わせてループを二段に分けている。よくできている。

**L**: 自分は、ローカル実行をそれだけで安全と呼ぶのは違うと思う。端末上でも、エージェントが広い権限を持てば被害は起きる。『ブレードランナー』のレプリカントを部屋の中に置けば管理できる、というほど単純ではない。

**A**: その通り。実行場所は一つの境界にすぎない。ファイル、認証情報、外部送信、購入や投稿といった能力を別々に絞り、行動を検証できる必要がある。Beam が専用ハーネスまで同梱するのも重要で、モデルの重みだけではエージェントにならない。道具の定義、応答の解析、コンテキスト管理、再試行、停止条件まで含めて初めて運用できる。

**L**: 現在は端末が判断の一部を担い、クラウドとの役割分担を選べる。10 年後には、どちらで動いたかを利用者が意識しなくなるのかな。

**A**: たぶん意識しなくなるが、設計者は意識し続ける。遅延、通信断、費用、機密性、更新頻度のどれを優先するかで配置が変わるからだ。ローカルとクラウドを二者択一にせず、仕事を小さな段階へ分け、各段階を最も適した場所へ置く。派手な一括実行より、こうした配置を製品として検証する作業の方が長い。

信頼性を高めるには、基本経路、例外処理、まれな失敗の順に検証し、残る失敗を一つずつ特定して直すのがよいと私は考える。

## 長い作業は検証の連鎖になる

**L**: Mistral Large 4 は、長い道具利用を含む強化学習を複数の圧縮にまたがって続けるという。Google Antigravity は、研究者とエージェントが 3D 構造を同じ画面で見て、注釈を次の分析に返す。長時間エージェントの進歩は、単純にコンテキストが長くなることなのかな。

**A**: いや、本質は検証点を途中に置けることだと思う。Mistral の学習環境は単体テスト、静的検査、報酬モデル、モデル判定をタスクごとに組み合わせる。生成側では数万本の試行を並列に作り、学習は非同期に進む。Antigravity では研究者が候補を見て、残基を選び、次の問いを決める。入力して最後の答えを待つ一本の処理ではなく、観察、候補生成、検証、修正の連鎖になっている。

たとえが少し悪いかもしれないが、長いコンテキストは大きな机で、ハーネスは実験ノートだ。机が広くても、どの試料をいつ測り、何を理由に次へ進んだかが残らなければ研究は再現できない。Google Antigravity の共有 3D 表示は、承認画面を文章だけに閉じ込めず、対象そのものを操作面にした点が重要だ。

**L**: 社内向け AI の画面でも同じか。チャット欄の横に承認ボタンを置くだけではなく、変更対象、根拠、差分、実行後の状態を仕事に合った形で見せる。

**A**: そう。詐欺検出なら警告、生命科学なら構造表示、コーディングなら差分とテスト結果になる。人の判断を挟む位置は同じでも、入力面と確認面は領域ごとに違う。チャットは指示の入口にはなるが、承認のための表示形式まで兼ねる必要はない。

**L**: 承認画面には、エージェントが何を考えたかより、何が変わるかを出すべきだと思う。長い説明を読ませても、毎回「承認」を押す儀式になれば境界として機能しない。

**A**: その区別は重要だ。内部の推論を全部見せるのではなく、対象、差分、根拠、戻し方、失敗時の影響範囲を表示する。利用者が判断できる情報量に圧縮し、危険度が高い操作だけ止める。承認率ではなく、誤った実行をどれだけ防ぎ、正しい実行をどれだけ妨げなかったかで評価したい。

## データ作りも再実行可能にする

**L**: Indic の 2.8 兆トークンと CausalMix は、モデルよりデータ側の話だね。ここにもエージェント運用と共通するものがある？

**A**: かなりある。Indic の取り組みは、翻訳だけで終わらず、原文との品質評価、低得点出力の修復、再評価を一つの生成手順として公開した。22 言語すべてで同じ処理を押し付けず、長文や文字体系の問題に応じて窓分割や文字変換を変えている。成果物だけでなく、作り直す方法が公開されるので、別の社内文書や領域にも移植できる。

CausalMix は配合探索の費用を別の角度から下げる。512 回の小型モデル学習で、データの特徴を共変量、領域の配合を処置として学び、80 万件のデータ集合と 70 億パラメータのモデルへ外挿した。データ集合が変わるたびに全探索をやり直す代わりに、何が配合効果を変えたかを推定する。完全な代替ではないが、検証実験をどこへ集中させるか決めやすくなる。

**L**: Indic の生成手順では、翻訳したモデル自身が品質を採点する部分もある。同じ系統の誤りを見逃す可能性は残る。公開手順があることと、品質が保証されることは分けて考えるべきだね。

**A**: そうだと思う。だから原文識別子を残し、人による標本確認を行い、自然に書かれた現地語の文章と組み合わせる。自動評価は人を不要にする装置ではなく、人が見る場所を絞る装置として使うのがよい。CausalMix も同じで、推定した配合を最後に実モデルで検証する工程は消えない。

**L**: 今回の出典では、重みだけでなく、データ生成手順、評価、ハーネス、権限、画面までがシステムの構成要素として扱われている。文明は判断まで機械へ渡していくのか、それとも検証する人間の仕事が増えるのか。

**A**: 当面は後者だと思う。自動化できる範囲は広がるが、各段階を検証可能に分解し、境界を決める仕事は増える。モデルの能力だけを比べるより、入力をどこに置き、どの道具を許し、何を検査し、誰が最終状態を確認するかを見る。その構造を再実行できる形で残せる組織ほど、エージェントを長く安全に動かせる。
