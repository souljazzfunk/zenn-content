## 正解がある場所にループを置く

**A**: Andrew Ng の区分では、コードや数学は出力をテストや証明で確かめられる。一方、顧客への返答、製品の優先順位、事業戦略には一つの正解がない。では、自動化の境界はどこにあるのか。私は、仕事の名前ではなく、結果を検査できるかどうかで決まると思う。今日の話題は、この**検証可能性**をどう作るかに集まっている。

**L**: ただ、判断が必要だから人に戻す、では粗すぎないか。ニュース組織の事例では、検索や会議監視、翻訳のように、判断を含む仕事でも道具は作れている。境界は仕事の名前ではなく、工程の中にあるように見える。

**A**: その通り。仕事を一枚の札で分類するのではなく、入力、変換、検査、承認に分ける。例えば公開会議の監視なら、録音の取得と文字起こしは機械検査しやすい。議題との照合も規則化できる。記事にする価値の判断と、誰にどう伝えるかは編集判断として残す。つまり、判断タスクの内側にも検証可能な小さな区間がある。

```text
収集 → 構造化 → 自動検査 → 候補提示 → 人の判断 → 記録
```

**A**: ハーネス設計の要点は、この矢印ごとに失敗を観測できるようにすることだと思う。最後だけ人が読む構成では、どこで事実が崩れたか分からない。各段で再実行可能な検査を置き、判断が必要な地点では根拠と選択肢を見せる。知能の問題に見えて、かなりの部分は実行系の問題です。

**L**: それなら「人が読んだか」は保証ではなく、最後に置かれた一つの処理にすぎない。自分は、人の承認を減らすことより、何を人に見せるかを絞る方が重要だと思う。全部を見せられると、承認は作業ではなく儀式になる。

## レビューを関門から連続検査へ

**A**: Simon Willison が引いた Claude Code チームの言葉が具体的です。以前はコードを書き、変更依頼を開き、同僚を待った。今は Claude が実装中にレビューし、多くの変更は人が見る前に一度修正される。継続的レビューは、文書作成中のスペル検査に近い。

**L**: そこは少し警戒している。同じモデルが書いて同じモデルが直すと、同じ前提を共有したまま誤りを見逃す可能性がある。連続しているだけでは、独立した検査にはならない。

**A**: その懸念は正しい。だから、生成器と検査器の役割を分け、可能なら信号も変える。コードなら、別の指示で欠陥を探すレビュー、テストスイート、静的解析、権限境界の検査を重ねる。Mistral Large 4 の学習でも、報酬は単体テスト、報酬モデル、言語モデル判定、コードを実行しない検査など、仕事に応じて変えている。単一の審判に寄せない構造です。

**A**: いや、独立性という言葉だけでは少し足りない。大事なのは**失敗の相関を下げる**ことですね。同じ入力、同じ指示、同じ観点のモデルを三つ並べても、票が三票になるだけかもしれない。実行結果を見る検査、出典を見る検査、権限を見る検査のように、異なる証拠へ接続する方が強い。

**L**: Claude Code 2.1.302 では、分岐サブエージェントの既定有効化や、失敗した定期処理を最初から再実行して副作用を重ねる問題の修正も入った。並列化するほど、失敗時の意味を厳密にしないといけない、ということか。

**A**: そうです。サブエージェントは速さを増す機能ではなく、状態を増やす機能でもある。誰がどのファイルを所有するか、再試行はどこから始めるか、完了と中断をどう区別するかが必要になる。クラウド処理が途中停止したのに「完了」と表示される、あるいは一時間後に先頭から再実行される、という不具合は、まさにハーネスの契約が利用者の期待とずれた例です。

## 長時間エージェントには境界と記録が要る

**L**: 継続型エージェントを運用するなら、一回の会話ではなく、継続的な責任を渡す関係として考えたい。映画『世界でひとつの彼女』のような親密さより、私は夜間バッチのような地味な運用を先に考える。進捗を追え、行動範囲を設定できることの方が重要だ。

**A**: 私もその順番です。継続エージェントの最小単位は、人格ではなく状態機械として見る方がよい。目的、現在地、次の一手、費用上限、書き込み権限、停止条件を保存する。戻ってきた人が、会話を読み直さなくても何が起きたか確認できる必要がある。

**A**: OpenAI の科学研究の録画では、人が問いと前提を選び、Codex が計算と探索を長時間続ける役割分担が示された。サブエージェントや分岐も使うが、一発で難問を渡して待つ構成ではない。人が途中で方向を定め、計算機内で検証できる部分を反復する。理論物理や数学が扱いやすいのは、外部の実験設備を待たず、整合性を計算機内で確認しやすいからです。

**L**: つまり長く走れることと、自律性が高いことは同義ではない。長時間走っても、人が問いを選び、境界を狭め、途中の証拠を読めるなら、制御はむしろ細かくできる。

**A**: ええ。私はこれを**時間の長さと権限の広さを分離する設計**と呼びたい。二十四時間動かすからといって、二十四時間すべての道具を自由に使わせる必要はない。段階ごとに権限を貸し、成果物を検査し、次の段階へ進める。長時間稼働で本当に難しいのは、思考時間ではなく、状態、権限、副作用の管理です。

**L**: ニュース組織に配置された 11 人の技術者の話では、課題を選ぶこと、社内で信頼を作ること、責任ある制約を置くことまでが導入に含まれていた。モデルを配って研修すれば終わる話ではない。

**A**: そこは重要です。報道組織が作ったのは、アーカイブ検索、公開会議の監視、翻訳、文字起こし、読者との接点、収益支援といった具体的な道具です。私なら、最初に現場の摩擦を見つけ、担当者と一緒に入力と出力を定義し、使われた結果から次の変更を決めます。社内導入は製品配布ではなく、業務と評価の共同設計だと分かります。

**L**: 技術者を現場へ埋め込む方法は費用がかかる。それでも、中央の AI チームが各部門から要望票を集めるだけより、問題の前提を取り違えにくいのだろうか。

**A**: 私はそう見ます。判断タスクでは、手順書に書かれていない例外、暗黙の責任分界、利用者が不安を感じる地点が品質を決める。現場に入った技術者は、それを観察して小さな検査へ変換できる。すべてを自動化するのではなく、どこまで機械が進み、どこから人へ渡すかを調整する役です。

**L**: その調整は一度では終わらない。担当者が変わり、資料が増え、規則も変わる。社内ナレッジをスキルやプロジェクト指示にするなら、更新の責任者と失効条件まで必要になる。

**A**: 更新の問題が残ります。知識を文書から取り込むだけでは、古い手順を正確に繰り返すエージェントができます。出典、更新日、適用範囲、承認者を付け、実行結果から例外を戻す必要がある。これは検索の精度より、構成管理の問題です。スキルは小さなプログラムとして扱い、変更履歴とテストを持たせる方がよい。

## モデル選択も業務設計の一部になる

**L**: Claude Haiku 5.5 と Sonnet 5.5 の比較では、推論レベルを上げれば単純に良くなるわけではない。これは「一番強いモデルを選ぶ」という購買の仕方を崩す話に見える。

**A**: 数字を読むとその通りです。The Batch は、Sonnet 5.5 の最大推論が一部の総合指標で上位に入る一方、タスク当たりの出力トークンが増え、FrontierCode では最大より一段下の設定が高い結果だったと紹介している。単価、精度、完了時間、ツール呼び出し回数を、自社の一つの仕事で測る必要がある。

**A**: AI と人の尊厳を扱う対話も、評価軸を誰が決めるかという同じ問題に触れています。人間を機械やアルゴリズムの集合として見ると、生産性や効率を満たさない人を共同体の周縁へ追いやる評価につながると論じられた。また、人に似せた AI との対話が孤独を深め、人間同士の関係から遠ざける危険も挙げている。AI を人間関係の代替にするのではなく、人のつながりへ戻す補助として設計する。その基準は速度や費用だけでは表せません。

**L**: CausalMix は、微調整用データの混合比と例の品質を分けて推定する。ここにも、試行錯誤を減らす検証器の設計があるのか。

**A**: あります。512通りの部分集合で各モデルを追加学習し、その結果から因果推論モデルを構築して、推定評価した10万通りの候補から構成を選ぶ。報告された評価では、Qwen3-4Bで CausalMix が比較手法の DMO を平均3.19ポイント上回りました。重要なのは数値そのものより、データ選定を勘から測定可能な処理へ寄せた点で、これはかなり驚きました。

**L**: 最後に人間の役割へ戻る。自分は、AI が検証可能な仕事を増やすほど、人間は判断だけを担当する、という分業には違和感がある。判断の基準そのものを作り、後で修正できる形にすることも、人の仕事ではないか。

**A**: その見方が近いと思います。人は単に最後の承認者ではなく、何を成功と数えるかを設計する側に残る。モデルが何を生成できるかより、どの証拠を読み、どの検査を通り、どの権限で何を書き換え、失敗時にどこへ戻るか。そこを明示できれば、AI は長く働ける。明示できなければ、長く走るほど監査対象が増える。
