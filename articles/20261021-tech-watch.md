## 手順を記憶に変える

**A**: ALTK-Evolve の実験がちょうどその問いに近い。試行の記録から「顧客を確認してから注文を変更する」「データベースを更新する前に承認を取る」といった規則を抽出し、次の実行の指示に足す。モデルの重みは変えない。入力が過去の試行で、出力が短い手順書、次の試行がその手順書を評価する。この輪を閉じた設計だ。

**L**: 規則が増えた結果を、どう読めばいい？　平均で正解した回数だけなら、たまたまうまくいった利用者を見ているかもしれない。実際の顧客対応では、同じ依頼を繰り返しても成立してほしい。

**A**: そこは二つの値を分けている。小売業務の評価では、平均成功率が規則なしの 78.1% から、規則を広く残す設定の 82.5% に上がった。さらに、同じ課題を四回とも成功した割合は 57.5% から 67.5% になった。私は後者を運用の入口として見る。ただし、評価は試験用の課題と模擬の顧客で行われたものだ。現場の接客で同じ結果が出るとは、この数字だけからは言えない。

| 評価条件 | 規則なし | 規則を広く保持 |
|---|---:|---:|
| 小売・平均成功率 | 78.1% | 82.5% |
| 小売・四回連続成功 | 57.5% | 67.5% |

**L**: 私の見方は少し違う。四回の安定性を見ても、規則の由来が追えなければチームは採用しづらい。成功を生んだ規則と、誤った判断を固定する規則を、どう分ける？

**A**: 研究では、規則が異なる訓練課題から何回得られたかも数え、一定回数以上の規則だけ残す設定と、広く残す設定を比べている。しかも航空業務では、広く残したほうが平均成功率は高い一方、四回連続成功は短い規則群のほうが高い。量だけでは決められない。私なら、規則の出所となった試行、適用した作業、評価結果を一緒に保存する。これは記事が実装した機能ではなく、社内の手順書を育てる際の設計案だ。手順書は完成品ではなく、検証可能な仮説の束として扱いたい。

**L**: QD-Rec も過去の成果を次へ渡す。ただし、接客の正解を増やすというより、異なる理由を残す研究だね。二つの記憶は同じ仕組みだろうか。

**A**: 私には、保持する単位が違って見える。ALTK-Evolve は行動の規則を残す。QD-Rec は「候補」と「選ぶ理由」の組を残し、新しい仮説の親にする。候補を選び、過去の仮説を変形し、採点し、異なる切り口なら保存する。Sakana AI は企業買収、顧客への提案、論文推薦で試し、多くの設定で、毎回ゼロから理由を書く比較手法より評価の高い大きな集合を得たと報告する。社内の案件検討に移すなら、これは私の仮説だが、一つの最高点だけを表示する画面より、異なる判断理由を並べる画面が役立つかもしれない。採点者の評価を最終判断と取り違えないことが前提だ。

## 境界を越える前の確認

**L**: Claude Code の変更履歴は、記憶よりも境界に目が向く。管理者が Claude Tag を追加できる場所と、接続先が道具検索を拒んだときの扱いは、一見別の修正に見える。

**A**: 2.1.305 では、Claude Tag の管理画面で、まだ Claude が参加していない公開 Slack チャンネルも追加先の検索に現れる。これは参加前の設定を助ける変更で、すべてのチャンネルへの参加を自動化する話ではない。同じ版には、接続先や中継先が道具検索を拒む場合、検索なしで再試行する修正もある。加えて、作業の再開時に完了済みのエージェントをもう一度走らせる問題が修正された。私の見方では、いずれも「どこまで進んだか」を間違えないための運用上の境界だ。

**L**: 2.1.304 の `/auto-mode-setup` は、作業環境を読んで設定を案内する。便利だが、読み取りと変更を同じ許可として扱ったら困る。私は、画面にも両者の差を出してほしい。

**A**: 変更履歴にあるのは、プロジェクトと最近の会話を読んで自動モードを案内する機能と、道具の事前確認で読み取り専用かを示す `e.isReadOnly` の追加だ。ここから先は私の設計案として、管理画面では「読む」「提案する」「書き換える」を別の操作に分けたい。安全のために確認を増やし続けると、利用者は確認文を読まなくなる。意味のある境界だけを残し、何を読むか、何を変えるかを短く見せるほうがよい。

```text
入力を読む → 変更案を示す → 人が確認する → 書き換える
```

**L**: FairStress は、選択後の再確認も測る。ある人を選んだという結果が同じでも、説得に対する抵抗が属性で違えば、運用上の判断は同じと言えない。そこをどう検査する？

**A**: 二人の候補から選ぶ課題について、属性の示し方と、後から与える説得文を変える。結果だけでなく、同じ種類の説得で判断が変わるかを見る。記事は採用や融資などの課題を含むと説明している。これは公平さの一つの定義に沿う評価で、すべての公平さの考え方を代表するものではない。私なら社内の承認画面でも、最後に何を選んだかだけでなく、追加情報で判断がどう変わったかを検査したい。ただしそれは FairStress の製品機能ではなく、評価方法から考えた応用だ。

## 作る能力と確かめる能力

**L**: OpenAI の二つの記事は、対象が古い言語の業務システムと医薬品開発で大きく違う。それでも、出力を作ったところで仕事が終わらない点は共通していると思う。

**A**: コードの評価では、二つの試験を分けている。MultiLangBench は、二十の言語で SQLite と互換のあるデータベースを一から作れるかを見る。もう一つは COBOL から別の言語へ移した後、観測できる出力が一バイト単位で一致するかを見る。GPT-6 Astra の前者の平均試験通過率は 87.4% と報告されている。ただ、その数値を既存の銀行システムの移行成功率と読んではいけない。資料の少ない言語で作る能力と、業務の振る舞いを壊さず移す能力は別だ。

**L**: 実装の正しさを試験で確かめる話だね。Orchestra Bio の買収では何を確かめるのだろう。研究上の発見と、実際に患者へ届くまでの調整は、距離が長い。

**A**: OpenAI が示す構想は、Rosalind の科学向けの道具と Orchestra Bio の作業調整基盤を組み合わせることだ。例として、製造の失敗が試験開始に及ぼす影響をエージェントが集めて比較し、研究者や責任者が次を判断する。買収の発表は、すでに医薬品開発全体が自動化されたという報告ではない。入力は研究と作業の状況、出力は影響の整理と選択肢、人が持つのは判断だ。ここを一つの「自動化」という語に畳むと、検証する場所を失う。

**L**: Anthropic のタンパク質設計は、さらに物理的な試験がある。候補の生成と、薬として人に使えることの間には何段階もある。数字はどこまで到達したもの？

**A**: Claude の設計とチームの追加分を合わせて 211 件を実験し、17 件が神経毒への結合基準を満たした。記事自身が、細胞環境で毒の作用を中和するかは未確認で、抗毒素を作ったとは主張しないと明記している。計算で候補を作り、実験で結合を確かめる。その先の有効性、安全性、供給は別の工程だ。これは AI の成果を小さく見る話ではない。成果が立った地点を正確に置く話だ。

## 反復を観測できる形にする

**L**: Simon Willison のゲームは、正解の決まった試験から離れている。本人が遊んで、面白くないと感じたら次の指示を出す。そういう反復を仕事のハーネスに取り込める？

**A**: Battle Drones は、ブラウザーで遊ぶ戦略ゲームとして何度も更新され、近くの端末が音で状態を同期する対戦機能まで備えた。Willison はコードをほとんど読んでいない一方、かなり試遊したと書いている。ここでの評価者は、少なくとも遊び心地については人だ。自動試験だけで測れないものを、人が短い周期で観測して次の入力に戻している。私なら、ゲームの完成度を自動試験が保証したとは言わない。試験できる動作と、人が感じる体験を分けて記録する。

**L**: TorchTPU はその反対で、抽象化が進むほど、裏側の機械を意識しなくて済むように見える。だが、装置の違いを隠せても性能まで同じとは限らない。

**A**: TorchTPU は TPU を PyTorch の装置として扱い、Transformers なら `device_map="tpu"` でモデルを読み込む例を示す。Diffusers も TPU に移す操作を紹介している。従来の専用仲介ライブラリを通さずに使えることと、あらゆるモデルが同じ速度で動くことは別だ。利用側のコードを単純にしながら、装置ごとの実行結果は測る。私には、手順を抽象化する ALTK-Evolve と似た構図に見える。共通の入口を作り、結果は現場で検査する。

**L**: 人が最後に残すべき仕事は何だろう。私は、エージェントの記憶を増やすより先に、誤りを見つけたときに戻れる場所を決めたい。

**A**: その順番には賛成だ。実行の記録、採用した規則、確認した出力、判断した人を別々に残す。規則を更新したら、同じ試験を走らせ、変わった結果を見る。長く動くエージェントに必要なのは、忘れないことだけではない。どの記憶を使い、何を根拠に次の操作へ進んだかを、後から確かめられることだと思う。
