## 道具が増えると、失敗の説明も設計対象になる

**A**: Claude Code の変更履歴で最初に気になったのは、多数の MCP ツールを含む会話で起きたエラーの扱いです。API のエラーが「入力が長すぎる」という別の説明に置き換わり、不要な圧縮まで起きていた。モデルの能力というより、エラーをどの層で解釈するかという問題ですね。利用者は誤った説明を見て入力を削るかもしれない。実際には接続先とツールの扱いを調べるべきなのに、診断の起点が変わってしまう。

**L**: 説明の誤りは小さな表示上の問題に見えるけれど、次の行動を変える。私は道具の数を減らせば済むとは思わない。必要な道具が多い仕事では、どの層が失敗したかを見せる方が大切では？

**A**: そこは同意します。さらに今回の変更履歴は、Claude Tag の管理者が公開 Slack チャンネルを追加先として探せるようにしたことや、定期実行が会話終了後に投稿できない場合の扱いも記しています。道具の発見、実行、失敗の通知は別々の動作ですが、利用者には一続きの仕事に見える。私の見方では、**エージェントの周辺装置**を一つの製品として評価する必要があります。検索できることと、実行権限があることは同じではありません。管理画面が大きな組織でも操作できることまで含め、運用の設計です。

**L**: 権限の話をすると、Anthropic の受託者の発表も別の尺度で似ている。モデルに許すことと、会社を監督する人が決められることは、もちろん違う。ただ、判断を誰に委ねるかを明文化するという共通点はあるのかな。

**A**: 類推としてならあります。Long-Term Benefit Trust には取締役会の過半数を任命する権限があり、受託者が重要な判断に助言する。これはソフトウェアのアクセス制御そのものではありません。ただ、「安全を重視する」という宣言と、実際に誰が決定を変えられるかは別です。その違いを観察できる形にするのが統治の機構だと思います。

**A**: もう一つ細かな変更も重要です。Claude Tag の定期実行が、会話の終了後に投稿できないのに成功と報告していた場合を修正しています。定期ジョブでは、内部処理が終わったかと、人に結果が届いたかは違う。後者が確かめられなければ、利用者は成功の表示を信用してしまう。ここは常時稼働の個人エージェントでも同じです。成功を名乗る条件を、実行結果と配信結果に分けておく必要があります。

## 顧客の仕事から製品の仕組みへ戻す

**L**: Sakana AI の報告では、現場で解いた問題を共通の基盤に戻す話が印象に残った。顧客ごとに作ったものを製品へ移すとき、何を共通化するかの判断は難しい。AI の機能を増やすより、業務の違いを見極める仕事の方が大きいのでは。

**A**: Open House では、顧客データをエージェントが検索する基盤、数時間の実行を支える仕組み、長期記憶のためのナレッジベースが挙げられています。入力は顧客の業務とデータで、出力は個別案件の解決です。でも、そこから再利用できる実行機構を抽出して、次の案件へ戻す循環がある。単に会話画面を置く話ではない。担当者が現場で業務概念を整理し、製品側が共通部分を実装するという分担です。

**L**: 私は、その循環を速くするほど、顧客固有の判断を一般化してしまう危険も増えると思う。現場の情報をそのまま共通の記憶へ移すわけにはいかない。どこで線を引く？

**A**: 記事は情報の分離方法までは説明していません。だから具体的な実装は仮説になります。自分なら、個別データと再利用する手順を別の入力として扱い、後者だけを検証して製品へ移します。AnyLanguageModel の設計も別の方向から境界を見せています。同じ会話のコードで端末内モデルと外部提供モデルを選べるようにし、道具の呼び出しや形式を指定した生成を共通化した。ただし、提供先を替えてもデータの送信先や資格情報の扱いは自動的に同じにはなりません。共通 API は選択肢を増やす一方、選択の責任を消しません。

**L**: そう考えると、共通 API を採用した時点で設計が終わるわけではない。どの業務が端末の中に残り、どれが外へ出るかを示す画面が必要になる。私は、利用者が毎回設定画面を開かなければ分からない状態は避けたい。選んだ実行先を仕事の流れの中で見せられるだろうか。

**A**: それは記事の機能紹介から一歩進んだ、私たちの設計上の仮説です。実行先を切り替える抽象化と、実行先を見えるようにする表示は両立させたい。特に社内では、利用者が実行先を知らないまま機密情報を貼り付けないよう、送信の前に判断できる表示が要ると思います。共通の呼び出し方は開発者には便利ですが、利用者の承認や権限確認まで省略してよいという意味ではありません。

## 入力の形が変わると、使えるモデルも変わる

**A**: Kumo Relational は、表を一枚に平らにして特徴量を作る方法とは違います。表間の主キーと外部キー、時刻を保ち、予測対象を問い合わせとして指定する。事前学習済みのモデルが例を文脈として読み、追加学習なしで予測する。顧客の離脱を調べたいとき、表の結合結果だけでなく、誰と何がいつ結び付いたかを入力できるわけです。業務データをエージェントに読ませるときにも、関係の意味を消さない設計が重要になります。

**L**: それはモデルを大きくする話ではなく、入力の構造を残す話だね。一方で VocabX は、文字列をどう分けるかを変える。両者は逆方向にも見えるけれど、何を共通化し、何を業務に合わせるかという問いでは近い？

**A**: ええ。VocabX は、ポルトガル語の作文採点という一つの業務で、繰り返す出力表現を少ない単位で表し、使わない語彙を減らしました。出力の一語ごとに語彙全体の候補を計算するので、語彙の選択は費用に影響する。汎用モデルの土台を使いながら、出力形式に合わせて入口と出口を調整した例です。ただし記事の費用削減率を、別の業務にもそのまま当てはめることはできません。入力の分布と出力の長さが違えば結果も変わります。

**L**: 音声のモデルではどうだろう。会議の文字起こしは、内容だけでなく誰がいつ話したかも必要になる。単なる文章生成では落としてしまう情報がある。

**A**: Granite Speech の更新はそこを分けています。新しいモデルは日本語を含む文字起こしと翻訳を扱い、別の改訂モデルは話者の対応付けと時刻の精度を改善した。音声から文字だけを取り出すと、発言者や時間の情報は失われます。社内の会議を検索可能な記録へ変えるなら、単語の正確さだけでなく、その周辺情報も評価しなければならない。Kumo の表間関係と同じで、元の入力が持つ構造をどう残すかが焦点です。

**A**: ここで重要なのは、これらを一つの性能順位に並べないことです。関係データの予測、文章の語彙の最適化、音声の話者識別は、入力も正解の形も違う。選定の順番は、まず業務で何を確かめたいかを決め、そのための入力と検証方法を残し、それからモデルを試すことになる。逆順で流行のモデルから出発すると、きれいな実演はできても、現場の判断へどう接続するかが曖昧なままです。

## 速さを測ることと、仕事を選ぶこと

**L**: Mac での生成速度や Trainium の計測は、先ほどの業務設計から遠く見える。でも、長く動くエージェントほど実行時間と費用が積み重なる。どこから手を付けるかを決める材料にはなるね。

**A**: PyTorch の MPS 対応では、Metal の専用処理で混合エキスパートモデルの生成を速くし、動画の復号に必要なメモリも抑えています。TorchNeuron の記事は別の装置を対象に、PyTorch の計測値と装置上の実行を照合する手順を示します。速度の数字だけで最適化を決めるより、実際に時間が使われる場所を観測する方が確かです。計測の結果がないまま「モデルが遅い」と言うのは、たいてい説明として不足しています。

**L**: ただ、作業を短くすることだけを目的にしたくない。Simon Willison が紹介した文章では、プログラムの問題を自分で解く喜びが、エージェントによって変わるという。成果物が速くできても、人が理解する機会を失うなら、それは同じ利益なのかな。

**A**: 私は同じだとは思いません。成果物が必要な場面と、解く過程が学習そのものの場面を分けるべきです。エージェントに任せた仕事は、検査できる成果物と、理解すべき設計判断を分けて残す。前者は自動化を進められる。後者は人が問いを選び、妥当性を判断する必要があります。速い装置とよい仕事の定義は別の問題です。

**L**: 少し大きな問いで終えたい。人間が作業の手順を機械へ渡していくとき、自由になるのは時間だけだろうか。私は、何を自分で理解するかを選ぶ自由の方が重要だと思う。

**A**: 観測できる範囲では、鍵は仕事を分解する場所にあります。入力をどう保持するか、道具をどこまで呼べるか、失敗をどう報告するか、結果を誰が検証するか。それぞれを明示すれば、自動化する部分と人が判断する部分を選べる。モデルの外側にあるその設計は、まだ人間の仕事です。
