## スキルを配ることと、業務を成立させること

**A**: Agent Skills の定義は意外に小さい。SKILL.md を含むフォルダーに、必要ならスクリプトや参考資料を添える。仕事の専門知識をモデルの重みへ閉じ込めず、読める単位として置く仕組みです。Anthropic は規格の名称、ロゴ、GitHub 組織、ドメインを財団へ移すと述べています。規格の管理先を中立にすることで、異なるエージェントの実装が同じ資材を読む土台は整う。ただし、読めることと実行できることは別です。

**L**: 私はそこで少し違う。規格が共通になれば、社内の手順もかなり移しやすくなると思う。各チームが同じ SKILL.md を持てるだけでも、説明を繰り返す負担は減る。実行環境の差を先に強調しすぎると、共通化できる部分まで小さく見積もらないだろうか。

**A**: その見方は正しいです。言い直すと、共有できるのはまず「仕事の教え方」ですね。実際に仕事を完了するには、参照する資料、使える道具、承認する人もそろえる必要がある。OpenAI の現場開発の記事は、まさにその一段先を示します。顧客ごとのアプリケーションを、Codex を中心にした共通のハーネスへ移し、固有の機能をスキルと拡張機能に分けた。記事では個別実装のコードのおよそ九割を減らしたと報告しています。数字はその事例の結果で、どの組織にも当てはまる比率ではありません。

**L**: 手順書を置いた時点では、まだ製品になっていないということか。現場で評価して、共通化できる動作を見つける順番が大事に見える。何を共通部品にするかは、どこで迷い、どこで失敗したかを見ないと決められない。

**A**: そうです。OpenAI のチームは現場で評価を作り、成功した仕事を次の部署でも使える形へ移したと説明する。Uber の展開も別の角度から同じ制約を見せています。ChatGPT Work を広げる際、Google Drive、Gmail、Calendar、Slack とつなぐ機能だけでなく、社内の AI スキル集、承認済み連携先、研修を組み合わせた。道具を足せば仕事になるわけではない。たとえば文書を要約するスキルがあっても、参照してよい文書の範囲と、要約を誰へ渡せるかは部署によって違います。試験用の資料で動いた結果をそのまま本番の承認とみなすこともできない。変更できる範囲を先に区切り、期待する出力を実例で確かめる必要があります。私の仮説では、社内導入の最小単位はスキル単体ではなく、スキルと権限と評価の組です。

## 分岐を小さくし、失敗を観測する

**L**: 権限を見せると言っても、画面に確認ボタンを増やすだけでは利用者が判断しにくい。小さな判断を何度も求められれば、結局どれも同じに見えてしまう。道具の呼び出しをどう分けると、重要な境界が残るだろう。

**A**: Decisions API は、自由な長文回答を求めず、質問と許される答えを先に定義する方式です。返り値は条件が成り立つ確率、指定した候補からの選択、基準に沿う点数の三種類。たとえば継続、再試行、確認依頼のどれへ進むかを一つの選択として表せる。これは承認の代行ではありません。判断結果を受け取ったアプリケーションが、次に何を許すかを決める構造です。私は、入力と選択肢を狭くした方が、どこで判断が変わったかを追いやすいと思います。

**L**: その選択に誤りがあったとき、後から何を見ればよいのか。映画の『2001年宇宙の旅』を思い出すのは、判断そのものより、判断の理由へ人が届かないことが不安だからだ。実際のエージェントなら、どこまで観測できる？

**A**: Claude Code の変更履歴には、権限規則、自動モード、安全性検査、フック、サンドボックスが道具の呼び出しを止めたり確認へ回したりした際の安全性イベントが追加されています。何が判断を止めたかを実行記録へ残す設計です。さらに HTTP の MCP 道具は、接続断の後にすべてを再試行するのではなく、読み取り専用か、繰り返しても結果が重複しない操作に限定した。ここはかなり重要です。接続が切れた事実だけでは、先の書き込みが実行済みかどうか分からない。勝手に再送すれば、同じ変更を二度起こし得ます。

**L**: なるほど。安全性イベントは失敗した操作を隠さず、再試行の条件は状態を二重に変えないための境界になる。画面の確認より下の層にある話だけれど、利用者が「何が起きたか」を知るためにも必要だ。

**A**: ええ。ここを**分岐と観測の接続**として見ると、道具の許可、モデルの判断、再試行を一つの曖昧な「自動化」にまとめずに済みます。おそらく実運用では、各段階の入力と結果を短く残し、どの段階を人が覆せるかを明示することが有効です。ただし、今回の発表がその利用者画面まで提供すると述べているわけではありません。これは設計上の私の見方です。

## 文脈に何を入れ、何を外へ置くか

**L**: スキルが増えれば、今度は読む資料が増える。すべてを会話に詰めると、必要な証拠が埋もれるだろう。社内文書や過去の判断を使う仕事では、検索と記憶をどう分ける？

**A**: DeepLearning.AI の Context Engineering 講座は、その問いを作業として分解しています。複数の検索道具を選ぶ、必要な道具だけを一覧から読み込む、長い履歴を整理する、作業状態を会話の外のメモに置く。そして利用者からの訂正を、次の仕事で取り出せる記憶にする。講座では Python でハーネスを組み、実行記録と評価で変更前後を比較する。抽象的な「よい文脈」ではなく、取り出し方と測り方を扱うのがよいですね。

**L**: 探せるようにすることと、正しい資料を先に渡すことも違う。検索結果を追加すれば、かえって読み直しが増える場合もある。NVIDIA の記事は、その部分を測っているのかな。

**A**: Nemotron 3.5 Retriever は、文章と画像を含む資料から候補を探し、次のモデルで関連度を並べ直します。記事中の比較では、エージェント本体や仕事を固定し、検索の構成だけを変えた。再順位付けを加えると、測定した設定でエージェントの推論に使うトークンが約一三〜一四％減ったと報告しています。これはその評価条件での値です。面白いのは、検索精度を単独で競うのでなく、エージェントが何度資料を探し直したかまで含めて見る点です。

**L**: Simon Willison の短い記事では、自分の過去の発言を MCP 経由で Claude に探させていた。大規模な社内検索より小さな例だけれど、質問に必要な記録を、その場で取りに行く形になっている。

**A**: そうです。彼は Agent Skills の移管を以前に予想したかを、自分の記事を公開した MCP の道具から確かめた。ここでモデルの記憶に頼らず、検索可能な記録へ戻る。私なら、社内の手順も同じように、スキルには「何をするか」と「どこを確認するか」を書き、変わりやすい事実は検索先に残します。ただし、その区分は彼の記事が提案する規則ではなく、そこから考えた設計案です。

## 並列化の先に、誰が確かめるか

**L**: OpenAI の生物学研究では、多数のエージェントが別々の遺伝子を調べたという。仕事を細かく配れば速くなるのは分かる。でも、報告が大量にできた後、どれを信じるかは別の問題では？

**A**: 研究チームは、各エージェントに遺伝子の操作による細胞の変化を調べさせ、文献を探し、説明候補を出させた。報告を統合した索引から、次の実験の候補を探せるようにしたと述べています。ここでの出力は治療法の確定ではなく、研究者が試す仮説です。単一のエージェントとの比較では、負荷が大きい条件で参照した文献数にも差が出た。ただ、文献が多いこと自体は正しさを保証しません。人が実験で確かめるための候補を広く集めた、と読むのが適切でしょう。

**L**: 安全性の話も似ている。脆弱性を見つけたら終わりではなく、修正を広めるまでに人と組織の調整がいる。私は、発見の自動化を先に進めるなら、公表の手順を同じくらい具体化すべきだと思う。

**A**: Patch the Planet の記事は、PHP の脆弱性への対応を踏まえ、保守者が修正を主導し、研究者や事業者が準備を支える流れを提案しています。対象版を確かめる Codex スキルも公開した。発見をエージェントに任せても、修正の検証、影響を受ける側への連絡、公開後の更新確認は異なる主体の仕事です。ここで美しいのは、役割を一つのモデルへ押し込めないことです。いや、美しいと言うより、責任の所在を残している、と言う方が正確ですね。

**L**: 仕事の速さだけを測ると、人が判断する場所が最後に余り物として残る気がする。自分はそこを中心に置きたい。エージェントが手順を共有し、検索し、並列で動くほど、人間の役割は何になる？

**A**: 私なら、検証できる問いを設計し、失敗したときに止める境界を管理する役割と答えます。SKILL.md は仕事を教える入力、検索は必要な根拠を渡す入力、道具は状態を変える出口です。分岐と再試行を記録して、出力を評価し、人が責任を持つ判断へ戻せるか。モデルの能力が上がっても、この接続を作る作業は消えません。むしろ各部品が交換可能になるほど、接続の仕様を明示する必要が増えると思います。
