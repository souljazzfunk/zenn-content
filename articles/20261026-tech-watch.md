## 許可を求める画面の、その先

**A**: Claude Code の変更履歴で目を留めたのは、ファイルの読み取り許可にシンボリックリンクの参照先が表示される修正だ。利用者が許可した名前と実際に読む場所がずれると、確認画面は判断の材料を欠く。もう一つ、長く前面で待機する処理を、監視用の道具がある環境でも制限する変更がある。どちらもモデルの回答品質ではなく、道具の実行境界の話だ。

**L**: 画面の文言だけではなく、実際の到達先と止まる条件をそろえるということだね。ただ、権限を細かくすると設定の負担も増える。利用者は何を見れば判断できるのだろう。

**A**: 私なら「何を実行するか」「どこに到達するか」「実行後に何を記録するか」を同じ画面に置く。これは記事の変更点から考えた設計上の提案で、Claude Code の新画面にその三つがそろったという意味ではない。実際に変更履歴が示すのは、参照先の表示、クラウドセッションと遠隔操作を企業の役割別権限に加えたこと、設定を有効にするとき影響する役割を示す確認だ。権限は管理者だけが読む設定表に閉じ込めるより、操作の場面で見える方がよいと思う。

**L**: 自分は少し違う。すべてを確認画面に集めれば、安全になるとは思わない。頻繁に出る画面は読み飛ばされる。確認させる回数より、止めるべき操作をどう選ぶかの方が重要では。

**A**: そこは同意する。先ほどの三点を毎回表示するという言い方は強すぎた。必要な局面で、その操作の到達先を判断できるようにする、が正確だ。今回の版には、特定のゲートウェイが要求の値を受け付けない場合に別の形で再試行する修正もある。通信の互換性と操作の許可は別の層だ。両者を一つの「うまく動いた」にまとめると、不具合の所在が分からなくなる。

## 現場で使うための文脈と人の判断

**L**: OpenAI の現場配備エンジニアの対談は、顧客の業務を理解して実用的な仕組みに変える仕事を扱う。技術者が顧客に近づくと、どこまで設計に踏み込めるのかな。公開された録画の要約は短いから、具体的な開発手順までは読み取れない。

**A**: その限定は大事だ。確認できるのは、日々の仕事と、顧客の声が製品をどう形作るかを話していること。そこから私が考えるのは、要件を受け取って実装するだけでは、AI が使える業務の範囲を決められないという点だ。どの資料を参照してよいか、どの作業に人の確認が必要かは、顧客の仕事を知らないと決めにくい。これは対談の発言を引用した結論ではなく、私の設計上の見方だ。

**L**: 議会スタッフ向けの ChatGPT 講座は、資料要約や連絡文の作成だけでなく、最初の出力を見直す工程を扱う。業務を支えるなら、操作の手軽さ以上に、判断を人に返す場所が必要そうだ。

**A**: 講座の案内は、文脈を与える、下書きを改善する、正確さを確かめる、機密を守る、と明示している。会議の質問まで準備できても、最終的に何を送るかは人が決める。社内向けの画面を設計するなら、生成結果だけでなく、参照した資料と未確認の点を並べるという方向がある。ただし、その画面が講座で提供されるという話ではない。

**L**: ChatGPT for Teens の記事は、学習支援に別の緊張を持ち込むね。進学計画や小テストを増やす一方で、外部団体の評価は厳しい。機能が増えることと、安全に使えることは同じではない。

**A**: そう。記事によれば、未成年向けの体験は別モデルではなく、設定、分類器、指示、画面の組み合わせだ。OpenAI は進学計画や学習機能を追加すると説明し、外部団体は検査結果から保護策の不足を指摘した。OpenAI は検査条件に異議を述べている。どちらか一方の説明だけで挙動を断定できない。ここで見えるのは、利用者の属性に応じた権限や保護策を、単一の会話画面の裏側だけで完結させる難しさだと思う。

## モデルを選ぶとき、測るもの

**L**: Reflection の Beam、Meta の Muse、Moonshot の Kimi が並ぶと、最上位の評価点だけを比べたくなる。けれど自分は、実際に使うまでの手間の方が気になる。何を先に測るべきだろう。

**A**: Beam の記事では、コーディングとエージェントの作業を想定し、長い入力を扱うための追加学習と、実行結果に報酬を与える学習を説明している。一方で公開重みの利用条件と、API への早期アクセスは別だ。Muse は上位の提供形態が契約によって分かれ、Muse Spark Open の重みは取得できる。Kimi K3.1 Pro は API で試せるが、Simon の記事の時点で重みはまだ公開されていない。モデルの比較表を作るなら、性能と同じ列に「手元で試せる範囲」を置くべきだ。

| 対象 | 記事で確認できる利用経路 | 注目点 |
|---|---|---|
| Beam | 公開重み、API は早期アクセス待ち | コーディング作業向けの追加学習 |
| Muse Wonder / Muse Spark Open | API / 公開重み | 画像・動画・音声を入力できる |
| Kimi K3.1 Pro | API | 推論の段階を変えて試せる |

**L**: それでも「速い」は大きな魅力だ。Beam の記事には出力速度も載っている。現場では、短い待ち時間の方が利用者の印象を変えるのでは。

**A**: 変えると思う。ただし、一秒あたりの出力と、一つの仕事が終わるまでの時間は別だ。Beam の記事は、出力速度だけでなく、最初の出力までの遅延や評価課題に要した時間も示す。Simon は Kimi を実際に API から呼び、推論の段階を変えた生成結果を並べた。自分の仕事に近い入力を使い、成功率、待ち時間、費用を同じ条件で見るのが先だろう。これは各記事に共通して書かれた評価手順ではなく、私なら採る比較方法だ。

**L**: では、モデルの選択はランキングというより、使える経路と検証環境の設計なんだね。表を埋める作業は地味だけれど、導入の判断には必要だ。

**A**: Hugging Face の Trainium 対応表がその地味な仕事を具体化している。モデルごとに、使用したコンパイラとライブラリ、分割した計算資源、実行用のスクリプトを示す。「動く」の判定は短い生成を確かめるもので、処理量や長い生成の保証ではない。利用可能性を公開した再現手順と一緒に示すのは、よくできている。

## 出典を選ぶ画面と、構成を小さくする設計

**L**: LitPivot は、研究案のどの部分を直すかを選ぶと、関連論文のまとまりと根拠付きの修正案が現れる。会話欄に「良くして」と書くより、判断する対象がはっきりする。社内の手順書にも似た入力面を作れるだろうか。

**A**: LitPivot は問題、貢献、評価計画を分け、選んだ部分に関係する論文を順位付けする。研究者は批評に使う論文を選び、提案を採用、編集、却下できる。調査では、参加者が既存の文章編集器と AI の質問用道具を使った場合より、文献に裏付けられた案として専門家に高く評価された。社内文書への適用はまだ仮説だが、手順の一段を選び、その根拠と修正候補を横に置く設計は参考になる。権限のない資料を混ぜない制御も必要になるだろう。

**L**: 研究者が選んだ論文だけで批評する設計は、根拠の範囲を人が決められる点が重要に見える。ただ、候補が多いと、どの論文を選んだか自体が結論を左右する。人が判断する場所を増やすだけでは、作業を移したことにならないかな。

**A**: その懸念はもっともだ。LitPivot は選択した論文に結び付く引用を提示し、案を直すと関連文献の順位も更新する。根拠を選んで終わりではなく、修正後の案に対して資料を見直す往復がある。社内手順で同じことをするなら、参照文書の版とアクセス権限も一緒に残したい。これは LitPivot の実装内容ではなく、業務向けに拡張する場合の私の仮説だ。資料が変われば、以前の承認をそのまま使ってよいかも問い直せる。

**L**: つまり入力面はチャットだけでなく、対象と根拠を指定する編集器にもなれる。ロボットの TurboVLA は分野が離れているけれど、構成を小さくするという意味では似ているかな。

**A**: 類似は設計上の見方としてならある。TurboVLA は、画像と言葉を別の小さな符号化器で処理し、両者の情報を注意機構で合わせ、最後に動作を出す。大きな言語モデルに統合を一任しない。記事は、比較したロボット課題で、少ないメモリと短い実行時間を報告する。これは一般の業務エージェントが同じ構成で速くなる証拠ではない。ただ、必要な機能を分けて測る姿勢は共通している。

**L**: 人にとって道具の自由度は、どこまで増やせばよいのだろう。自分は、何でも頼める一つの会話欄より、扱う資料と決定の範囲を選べる画面に可能性を感じる。人間の判断は、そういう制約の中でむしろ残せるのかな。

**A**: 私もその方向を試したい。まず、入力される資料、呼べる道具、止める操作、検証する結果を別々に定義する。Claude Code の権限表示、現場配備の業務理解、LitPivot の根拠選択は、それぞれ別の層を見せている。モデルを入れ替える前に、この四つを観測できるようにする。そこから先は、利用者が誤りを見つけられるかを実際の作業で測るしかない。
