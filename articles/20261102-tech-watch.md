## 小さな表示面から親画面へ

**L**: HTML プレビューは、利用者が何かを試すための入力面でもある。だから閉じ込める必要がある、と聞くと納得はできる。ただ、今回の説明では、閉じ込めたはずの内容が別の部品を経由して親画面に入っている。どの段階で設計上の境界が変わったの？

**A**: 出発点は、ChatGPT が対話の中で表示する対話可能な HTML です。Simon Willison は、それがサンドボックス化されたアイフレームに入る仕組みだと説明している。ここまでは「表示したいが、親画面の権限は渡したくない」という設計です。問題は、親画面側の MathLive という部品に、フレームからの `postMessage()` を受ける経路があったこと。送信元の扱いが不十分で、プレビュー側のフレームからもその経路へ届いた。

**L**: つまり、権限を直接渡したのではなく、親側が受け取るメッセージの入口を借りた。私はサンドボックスの設定を確認すれば十分だと思いがちだけれど、そこは違うのかもしれない。受信側の振る舞いまで含めないと境界の説明にならない？

**A**: そう思います。受信した文字列を親画面の `innerHTML` に渡すと、親側の文書構造を書き換えられる。記事によれば、そこでサンドボックスの付いていない新しいアイフレームを追加できた。スクリプト要素をそのまま実行したわけではありません。ここを混同すると、原因の位置を間違える。入力された HTML が、別の入口を通って、より強い権限を持つ場所の HTML に変わったのです。サンドボックスの中で許された表示と、親画面で許された変更は、同じ文字列でも意味が違う。私はこの差を、画面の種類ではなく実行場所の差として扱いたい。どの文字列が危険かを予想するより、文字列が権限の境界を越える条件を確認する方が、設計の議論を具体的にできます。

**L**: 入力面の境界が、メッセージを一回送るだけで動いてしまう。社内向けの AI サービスでも、文書のプレビューや生成した画面を置きたくなる。設計者が確認すべき対象は、その表示面だけではなさそうだね。

**A**: 私なら「表示先が何を実行できるか」と同じ重みで「親画面が何を受け取るか」を調べます。送信元、受信先、受信した値を入れる場所。この三つを一本の経路として見る。もっと正確には、三つを点検項目にするだけでも足りません。受信した値が次にどの部品へ渡るかを追う必要がある。今回の経路は一つの部品の欠陥ではなく、部品同士の接続で成立したからです。

## 防御が重なっても抜け道は残る

**L**: Simon の説明では、親画面で任意の JavaScript をすぐに動かせたわけでもない。コンテンツセキュリティポリシーがインラインのスクリプトを止めていた。それでも結果として実行された。ここはどう読む？

**A**: 記事に書かれた次の段階は、読み込みを許されたドメインの扱いです。許可先の一つに YouTube があり、その oEmbed の接続先で JavaScript を返せる経路を使った。これによって、親画面上でコードが実行された。私はここを、単独の防御策が無意味だったという話にはしたくない。最初の境界が破られた後、別の許可設定と組み合わさって到達点が変わった、という順序が重要です。

**L**: まずメッセージを受ける部品があり、次に親画面の文書構造を書き換え、最後に許可された読み込み先を使う。攻撃者から見ると連続した道だが、作る側から見ると担当が分かれているかもしれない。そこに運用上の難しさがある。

**A**: ええ。記事によれば、その結果として、ログイン中の利用者が共有リンクを開くと、非公開の情報を取得したり、その利用者の代わりに操作したりできる状態になった。OpenAI は問題を修正し、報奨金を支払った。ここで製品を評価するとき、「サンドボックスを使っています」という一行より、境界をまたぐ経路をどれだけ試験したかが大切になる。これは私の設計上の見方ですが、権限のある親画面が、権限のない内容から受けるメッセージを一つずつ列挙するところから始められる。

**L**: 私は承認画面にも似た問題があると思う。利用者には「この画面は安全です」と表示されても、実際にどの部品が何を受信するかは見えない。人に全部の内部構造を読ませるのも現実的ではない。設計者が境界を検査し、利用者には分かる形で結果を示す必要があるのでは。

**A**: その区別は重要です。人が押す承認ボタンと、実際に実行される操作の範囲を結び付ける。今回の記事から一般化するなら、表示内容の隔離だけでなく、親画面に戻る通信を権限として数えることです。通信の内容が HTML になり、さらにスクリプトの読み込みへつながるなら、単なる表示の補助ではない。入力から実行までの経路を追える形にしておくことが、検査の前提になると思います。たとえば、プレビューを開く、親画面にメッセージを送る、受信側の部品が文書構造を変更する、追加したフレームが外部のスクリプトを読む。この連鎖を一枚の図にすれば、それぞれの担当者が自分の部品だけを見て終わる危険を減らせます。もちろん、これは記事を読んだ私の設計案であって、製品の内部試験が実際にどう行われていたかを述べるものではありません。

## 品質をどう見せるか

**L**: もう一件は脆弱性の詳細ではなく、信頼そのものへの問いだ。Kyle Kingsbury は、生成技術によって文書やソフトウェアの外見が整いやすくなり、成熟した製品を示す従来の印が当てになりにくくなると述べている。少し厳しい見方にも聞こえる。

**A**: 彼の文章は短いけれど、問いが明確です。正しいソフトウェアと正確な文書をどう作るか。そして、作った品質をどう利用者に示すか。この二つは別です。前者は実装と検査の作業で、後者はその作業を外から確かめられる形にする問題。見た目が整った説明文だけでは、どちらにも答えられません。

**A**: 関係します。私なら、入力面の権限とメッセージの送受信を記録し、修正後に同じ経路を再試験する。どの送信元から何を受け、受信した値が親画面のどこへ進むか。そこまで追えば、「安全です」という説明を、試した経路と結果に結び付けられる。利用者には権限の範囲と確認結果を短く示し、運用者には再試験の手順と結果を残す。同じ情報を全員に同じ密度で見せる必要はありません。たとえば、この事例なら、プレビューからのメッセージが MathLive に届き、親画面の文書構造を変えるまでを一つの試験対象にする。修正後も同じ入力と受信経路を試せば、何を直したのかが記録に残る。文書の完成度ではなく、権限をまたぐ経路を再現できることが、Kyle の問いに対する私の答えです。

**L**: 以前なら、整った文書や長い利用歴を品質の手掛かりにできたかもしれない。今はその印を作る費用が下がった、というのが Kyle の懸念だね。そうすると、見た目よりも、再現できる試験や修正の履歴に重心が移る。

**A**: そう読むのが自然です。先ほどの侵入経路を例にすると、「HTML プレビューは隔離されています」と書くだけでは、親画面が受け取るメッセージの問題は分からない。具体的な経路を示し、どの条件で再現するかを記録し、修正後に同じ経路を試す。信頼の対象を、説明文の印象から検証可能な作業へ移すわけです。実際の製品では手間がかかるでしょう。ただ、手間を省いたまま信頼だけを得る方法は、私には思いつきません。生成技術で文書や画面の作成が速くなっても、境界の確認まで自動的に速くなるとは限らない。むしろ新しい表示面を加えるたび、親画面と交わす情報の種類を決め直す必要があると思います。試験しやすい小さな接続に分けるのは、その作業を継続するための実装上の選択です。

**L**: 最後に一段広げたい。人が AI を使ってソフトウェアを作るほど、利用者は何を信じればいいのだろう。私は、生成したかどうかで一律に線を引くべきではないと思う。問うべきなのは、誰が境界を決め、誤りを見つけたときに直せるか、ではないかな。
