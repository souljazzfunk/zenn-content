## モデルを固定して実行系を見る

**A**: CUGA の比較では、GLM-5.3-flash を固定し、AppWorld の同じ90課題に三つのハーネスを当てている。通過数は次のとおりだ。

| ハーネス | 通過課題 |
|---|---:|
| CUGA | 73件 |
| Hermes | 42件 |
| Deep Agents | 27件 |

ここで問うべきなのは「常に最良のハーネスはどれか」ではない。各構成が、複数のアプリをまたぐ道具の利用に何を用意していたかだ。著者自身も設定条件は同一でなく、単一の試験から一般化できないと明記している。

**L**: 自分は、数字が大きく違うとモデルの能力比較として読みたくなる。でも今回はモデルが同じだ。何が途中で起きて、結果を分けるのか。画面から見えない部分を具体的に知りたい。

**A**: CUGA は作業を分け、その段階に必要な道具を絞り、見当たらない道具は検索する。生成したコードは制限付きの環境で実行し、変更前に検査し、実行後の結果も見直す。つまり入力を一度に渡して回答を待つのではなく、準備、モデル呼び出し、実行、検査を繰り返す。著者の言い分を少し狭く言い直すなら、モデルの推論を改善した証明ではなく、業務の形に合わせた実行環境がこの課題群で有利だった、という観察だ。

**A**: もう一つ大切なのは、業務の規則を文章で頼むだけでは強制にならないことだ。CUGA の記事は、支払い前の承認や道具呼び出し前の制限を、モデルの判断ではなく実行側の停止条件に置く。記事中の比較試験ではその規則を使っていないから、成績の差を権限制御の成果だと言ってはいけない。成績の測定と、権限の設計は二つの別の主張だ。

**L**: Claude Code の変更履歴にも、実行環境の境界が並ぶ。予定タスクに接続先が増えたり、フックが失敗したりする。人が見ない時間に動くとき、失敗した後の扱いまで設計に含まれるのだろうか。

**A**: Claude Code 2.1.317 は、予定タスクに求めていない接続先が付くと警告し、外し方を示す。Agent SDK のフックには `onFailure: "block"` が加わり、フック失敗時に操作を止められる。自己ペースの `/loop` が起きない場合の修正も載っている。これらを一つの新機能とみなすのは違うが、権限、失敗、再開をモデルの外側で扱う方向は共通している。予定タスクは画面を見ている間だけ動く操作と違い、次に人が確認するまでの空白がある。接続先を作る時点で表示し、障害時には止まった理由を残す。その二つを入れて初めて、人が後で判断できる。

## 検査を仕様に近づける

**L**: 実行後に「大丈夫そう」と尋ねるだけでは不安が残る。何を検査すれば、その仕事に必要な性質が守られたと言えるのだろう。コードと資料では答えが違いそうだ。

**A**: Transformers の Model Integration Contracts は、その問いを小さな再現物にする。実モデルの構造を残して縮小した試験用モデル、利用例、確認済みの期待出力を一組にする。公開記事では UMT5 の注意機構の回帰を過去の変更履歴で再演し、小型の試験用モデルが問題の期間を検出した。単に計算が完走するかでなく、同じ入力に対する出力や損失を比べる。すべての統合試験の代わりではないが、変更を取り込む前に安価な検査点を置ける。試験用モデルを小さくしても、問題が起きた経路を通らなければ検出できない。記事では、通常使われる注意機構を通したことが回帰検出の条件だったと説明している。小さな試験を作るとは、モデルの寸法だけを縮めることではなく、利用経路の意味を保つことだ。

**L**: 資料作成の Palette は文章の品質を採点するのだろうか。自分なら、まず見た目が壊れていないか確かめたい。指示で「表を時間軸に」と言っても、配置まで正しくなるとは限らない。

**A**: Palette は構成を決める役が資料の仕様を書き、描画する役が各画面のコードを作る。できた画面を描画して、文字のはみ出しや要素の重なりを測る。修正案は再検査で改善が確認された場合だけ採用する。この受け入れ条件が重要だ。新しい案が見栄えよく見えても、測定値が悪化したら元に戻す。著者の評価では、131件の資料に対して検査・修正の仕組みが平均3.5点を加えた。構成案と描画の間に、人が読んで直せる仕様を置いた点もよい。ある画面の配置が違えば、資料全体を再生成する前に、その画面への指示を変えられる。これは完成物だけを見せる画面より、承認と修正の場所がはっきりしている。ただし、その評価は組織固有のデザイン言語への忠実さを直接測っていない。

**L**: 安全上の弱点を修正する課題は、合格基準をさらに厳しくしなければならない。修正後に既存の機能が動くことも含めて確かめたい。

**A**: CWE-bench v2 はそのための公開100課題を用意した。対象は実際の公開リポジトリで、検証器は弱点の解消だけでなく、元の動作が残るかも確認する。検証器が決定的なので再実行しやすい。検証器の作りも公開され、課題の指示から合格条件を推測できるか、既知の修正を丸写ししただけで通らないかまで点検している。正解らしい差分を作るだけでは足りず、守るべき性質が何かを試験に落とす。一方、得点が高いことと、未知のすべての弱点を防げることは別だ。試験範囲の説明と、運用の結論は分けて読む必要がある。

## 状態を持つ仕事と専門知識

**L**: 長い作業では、前の結果を覚えているだけでは足りない。途中で値が変わるし、外の世界も変わる。何を記憶して、何を再計算すべきなのだろう。

**A**: StateBench は固定値の検索、最新値への再代入、現在値に依存する更新、別の値の参照を区別する。前の状態を引き継ぐ段階になると、最後の記述だけを探しても答えは出ない。著者は複数のモデルを試し、長い入力で難しい状態追跡の精度が落ちることを示している。これは長期作業の記憶設計を直接評価した結果ではない。たとえば予定を変更する仕事では、「最初の予定」ではなく「何を受けてどこを更新したか」が必要になる。全文を再読するだけで十分か、状態を明示的に持つべきかは、作業の性質を見て決めるべきだ。ただ、途中の状態を構造化して持つ必要を考える材料にはなる。

**L**: 化学の研究では、モデルに何でも任せたくなる場面もありそうだ。専門家の手順をスキルにしたら、科学者が自分で確かめる場所はどこに残るのだろう。

**A**: Google Antigravity の化学情報処理スキルは、文献から化合物を集め、出典と対応づけ、解析や候補提案につなぐ。言語モデルは道具を選び作業を指揮する一方、分子計算は RDKit などの決定的な道具が担う。画面では化合物と測定値を人がたどれる。記事が示すのは作業例であって、新薬の発見が保証されたという話ではない。専門知識を手順と検査に分けることが大切だと思う。分子の表記は文献、画像、データファイルで違い得るから、まず同一の化合物を対応づけなければならない。そこを曖昧にしたまま候補の良し悪しを語るのは危うい。スキルは知識の一覧ではなく、入力をどう整え、どの計算に渡し、出典へどう戻るかの手順として読むと分かりやすい。

## 道具が広がるほど境界を明確にする

**L**: 以前は複数のモデルを切り替えられるだけで十分だと思っていた。今は入力の形式も道具の種類も増える。小さなコマンドラインの更新と、画面の安全性の話が同じ日に並ぶのは奇妙だね。

**A**: Simon Willison の LLM 0.37 は、互換端点の登録と、内容種別の異なる埋め込み入力を扱えるようにした。複数のモデルを呼ぶ操作面を簡潔にする仕事だ。一方、彼が紹介した ChatGPT の攻撃事例では、隔離された HTML の画面から親画面のメッセージ処理へ届く経路が問題になった。道具や画面が増えるほど、何に接続できるか、どこに表示できるかを明示する必要がある。便利さと境界は別の設定項目ではない。攻撃事例については、問題の経路が閉じられたと記事にある。だから現在も同じ手順で侵入できると書くのは不正確だ。残る教訓は、子画面を隔離したつもりでも、親画面が受け取るメッセージの処理が別の入口になり得るという設計上の点だ。

**L**: それでも僕は、模型の重みを見ただけで何が学習されたか推定できるという実験に目を奪われる。『コンタクト』で未知の信号を解読する場面に少し似ている。ただ、それを実務で使える能力と呼ぶのは早いのでは。

**A**: Willison はローカルの Qwen 3.8 27B で、ゲーム用モデルの重みから学習対象のゲームを推定する実験を再現した。これは面白いが、道具なしで重みを読むことと、コードを実行して別のモデルを書き換えることは分けている。僕も、能力の範囲はまだよく分からない。再現できた小さな例を足場に、次は別の重みや課題で確かめるのが順序だろう。

**L**: 人間は結局、何を手放さずにいるべきなのだろう。能力の高いモデルが出れば、判断も任せてよいと考えたくなる。でも僕は、許可する行為と検証する基準を人が設計する仕事は残ると思う。

**A**: モデルが何を推測できるかと、何を実行してよいかは別だ。今日の例を重ねると、道具の範囲を絞り、実行前に止め、出力を測り、改善しなければ戻すという実装が見えてくる。僕の見方では、これは知能を否定する話ではない。知能を使える仕事に変えるための、地道な実行設計だ。
