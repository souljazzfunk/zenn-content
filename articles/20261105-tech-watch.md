## 承認はアプリの内部で何を守るか

**A**: datasette-apps の変更を一つ追うと、アプリが呼べる保存済みクエリの集合をエージェントが変更できるようになった。ここで重要なのは、画面を作る能力と、データを書き換える能力が別だということだ。app_create() は要求されたクエリが存在し、利用者に閲覧権限があるかを調べる。書き込みクエリを含めるなら承認を求める。私はこれを、対話で作ったものにも既存の権限境界を通す設計として読む。

**L**: 私は承認画面が増えるほど安全になる、とは思わない。何を承認したのか分からなければ、押すだけの操作になる。ここでは利用者が、アプリの外形と実際の書き込み権限を別々に見られるのか。

**A**: 公開された説明から確かめられるのは、書き込みクエリを許可する前の承認と、作成時の存在・閲覧権限の検査までだ。承認画面の表示内容や、後からの取り消し方までは書かれていない。だから十分な画面設計だと言い切れない。一方、入力されるのは「このアプリにこのクエリを使わせたい」という要求で、出力は許可されたクエリを持つアプリだ。その間に検査と承認を置く位置は明確になった。

**L**: データの表を見ながら対話できるパネルも、同じ境界の話だろうか。私は『her』のような一つの声より、操作対象が目の前に残る画面の方が仕事には向いている気がする。

**A**: datasette-agent 0.5a0 のパネルは、表やクエリのページを開いたまま隣に対話を置ける。datasette-apps と組み合わせれば、データに基づくアプリを作り、そのアプリを横で見ながら変更できる。これは私の見方だが、対話の履歴を唯一の作業面にしないことが大事だ。対象を可視化しておけば、利用者はエージェントの説明と実物を照合できる。なお、パネルそのものがアクセス制御の代わりになるわけではない。

**L**: では、使い始めるところの摩擦はどう変わる。小さな初期設定でも、組織では説明書の行数を増やす。

**A**: datasette-llm 0.1a9 は、LLM で選んだ既定モデルを Datasette Agent が受け取る。以前必要だったエージェント用の別設定を省ける。つまりモデルを選ぶ操作を二重にしない。私はこういう修正を軽く見ない。手順を一つ省くというより、設定の所有者を一つに戻す修正だからだ。ただし、既定値を使うことと、そのモデルにどのデータを渡すかは別の判断である。 製品を組織に入れる場面を想像すると、初回起動の説明だけが短くなるわけではない。チーム内の手順書にも、モデルの選択場所を一か所として書ける。もちろん、誰がその設定を変更できるかまで今回の資料からは分からない。機能の改善を評価するときは、設定項目が減ったという事実と、組織での管理が容易になるという私の予想を混同しないようにしたい。

## 長い仕事を止めずに、境界を失わない

**L**: Claude Code の変更履歴には、目立つ新機能より保存や再接続の修正が多い。長時間動くエージェントには、そういう地味な項目の方が大事なのか。

**A**: 2.1.318 には複数の層がある。たとえばサブタスクに低い推論負荷を指定できる機能は、主作業とは別の小仕事に計算量を配分するものだ。一方、MCP の追加・削除時に設定ファイルのロックを待つ修正は、道具の接続先を保存する側の問題を扱う。さらに、使用量の制限から再開したときに完了済みエージェントを再実行しない修正もある。モデルが同じでも、状態の保存と再開が違えば、仕事の結果は変わる。

**L**: 権限の変更が保存されなかったのに成功と表示される不具合も修正された。私はここを単なる操作性の問題とは見ない。許可したつもりの状態と実際の状態が違えば、利用者は境界を判断できない。

**A**: 同意する。変更履歴は、共有ネットワーク上のホームディレクトリで設定を書けないとき、ログアウトや MCP の削除などが成功したように見える問題を挙げている。ここで入力は利用者の設定変更、出力は永続化された設定だ。途中で失敗したら、それを成功として返してはいけない。私はこの一連の修正を、エージェントの能力より**状態の真実性**を守る工学と呼びたい。少し大きな名前か。要するに、再開後も「何を終え、何を許可したか」が一致していることだ。

**L**: 役割の引き受けを別 AWS アカウントに広げる機能もある。組織の境界をまたぐほど、説明と実際の権限の差を小さくしないといけないね。

**A**: 変更履歴が述べるのは、mantle の上流に assume_role を加え、別アカウントの役割と開発者ごとの費用帰属を扱えるという範囲までだ。どの運用が適切かは組織の設定次第。ここから一般化するなら、道具の数を増やす前に、誰の権限で実行され、失敗時にどこへ記録されるかを確認したい。

## 文書を読むモデルと、科学実験を進めるチーム

**L**: 文書の画像から必要な項目だけ取り出すモデルは、対話画面とは反対方向に見える。けれど、社内サービスの入力面を考えると、むしろこちらが本体かもしれない。

**A**: Dharma Field Extractor は画像と項目の指定を受け取り、型付きの JSON を返す。項目の指定がなければ見つけた項目を返し、指定があればその形に合わせる。ない項目は null にする。会話を続けて正しい表を探すのではなく、入力文書から下流のシステムに必要な構造を作る。私には、チャットを中心に据えない業務用 AI の具体例に見える。

**L**: 小型モデルが汎用モデルより良いという主張は、どこまで信じてよい？数字だけを別の帳票へ持ち出すと危うい。

**A**: 著者が示す比較は、546 文書を三つの要求方法で試した自前の評価だ。対象の汎用モデルとの比較では、この抽出モデルの得点が上回り、実行費用の試算も低かった。ただし評価の文書分布、採点法、計算機の費用条件が決まっている。社内の帳票にそのまま再現されるとは言えない。導入するなら、自分たちの入力で、欠損値と表の行が期待どおりかを測る。モデルの大きさより、検証可能な出力形式が先に来る。

**L**: Anthropic の粒子研究では、Claude が単に論文を要約したのではなく、実験の工程に入っている。どこに人の判断が残るのだろう。

**A**: チームは Claude にタンパク質の候補探索、DNA 設計、分離方法の検討、顕微鏡データの処理を支援させた。構造解析では内部の複数エージェント環境で計算資源を使い、人が解析上の判断を助言した。Claude は最初、分離に使うカラムの方法に反対したが、チームは試し、Claude も条件の調整を手伝ったという。この順番が重要だ。仮説を生成する主体が増えても、実験で確かめる工程と、人が方針を変える権限は残っている。 実験室での役割をさらに分けると、候補を挙げること、試料を作ること、画像から構造を推定することは同じ仕事ではない。最初の提案が外れたときに方針を変えられる人がいて、測定結果が次の判断を制約する。この往復がなければ、複数エージェントを使っても、計算を並列に走らせただけで終わる。これは記事の手順から私が読み取る設計上の教訓だ。

**L**: 研究成果そのものと、研究手順の改善は分けて見たい。粒子の機能が解けたように聞こえてしまうから。

**A**: そこは明確に分けよう。論文の説明は、粒子の生物学的な機能はまだ特定していないと言っている。確認されたのは、細菌感染性ウイルス由来のタンパク質が粒子を組み立てることや、その構造だ。作業手順では、従来約三日かかる精製を約九十分にし、最初の構造モデルを三十四時間後に得たと報告する。科学的な問いが解けたことと、問いを調べる速度が上がったことは同じではない。

## 計算施設も一つのシステムの部品

**L**: OpenAI の電力の話は、エージェントや画面から遠く見える。それでも計算が常時必要なサービスなら、施設の設計が利用者の外側にあるとは言えないね。

**A**: Grid Protectors Program は、将来の計算施設が電力網に余裕のない時間帯に需要を下げられるよう、電力会社と取り決めを作る構想だ。ジョージア州の計画では最大千メガワットの柔軟な需要応答を含む契約が先行例として挙がる。ただし施設は開発中で、これを既に実証された運用成果として書くのは違う。電池や現地の発電も、設備と地域の条件によって検討すると述べている。 OpenAI は施設が使う電力と必要な設備の費用を自ら負担する方針も述べる。一方、地域の電力料金がどれだけ下がるかは、個々の契約だけで決まらない。記事が引用する節約見込みは電力会社の大型需要契約全体についての予測で、この施設だけの実測効果ではない。ここも発表時の目標、契約上の数値、運用後に測れる結果を分けて読む必要がある。

**L**: 私は『コンタクト』を思い出す。大きな機械の価値を語るとき、周囲の人に何を負担させるかは最後の注釈では済まない。AI サービスで、その負担をどう見えるようにするべきだろう。

**A**: まず、契約上の約束、実際の制御、観測した結果を別々に示すことだと思う。電力なら、どれだけ需要を下げられる契約か、いつ制御したか、他の利用者への影響はどうだったか。エージェントなら、許可された道具、実行した操作、失敗して保存されなかった変更を区別する。どちらも高度な推論だけでは成立しない。境界を記録し、人が確かめられる形で戻す仕組みを作る仕事だ。
