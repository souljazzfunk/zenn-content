## 記憶は、書いた時点ではまだ仮説

**A**: Anthropic の研究で気になったのは、記憶を「保存した事実」と呼ばないところです。エージェントは作業中の記録や会話から重要そうなことを選んでメモにする。でも、その時点では後の作業で何が必要になるかを知らない。だから記憶は、将来の自分が必要とする情報についての予測でもある。まずここを分けて考えたい。

**L**: 予測なら、間違えることを前提に設計する必要があるね。とはいえ、毎回すべての記録を読み直せば、長期記憶を持つ意味が薄れる。保存と再確認の境界はどこに置く？

**A**: 研究でいう「夢を見る」処理は、作業の合間に元の履歴とメモを照合し、誤りを直したり、関連する記憶を結び直したりするものです。ゲームの例では、Claude が地図上の位置を間違って覚え、同じ経路で行き詰まった。履歴を見直して位置のメモを訂正した実験では、その後に先へ進めた。保存した説明を真実として扱うのではなく、元の観測へ戻れるようにしておく。ここがループの中心です。

**L**: 自分は、メモを頻繁に書くほど改善すると思っていた。でも古くなる状態まで書き込むと、探す仕事のほうが増えるのか。何を残さないかも設計なのだね。

**A**: そうです。別のゲームの比較では、古いモデルは大量のファイルに遭遇を記録し、より新しいモデルは目標、計画、検証済みの規則を少数のファイルにまとめた。最初は保存量の差が結果を分けたと思いました。いや、モデルも違うので、量だけでは説明できない。画面を見れば分かる現在位置を毎回保存するより、画面からは読み取れない試行の結果を残す、という区別は実装に移しやすい。記憶の品質は容量ではなく、後の判断に必要な差分を保持できるかで測るべきだと私は考えます。

> Memory can be a prediction about what the future will need
>
> — Anthropic「The components of agent memory」

**L**: 予測を記憶として扱うなら、出典の所在と、確認した範囲も一緒に持たせたい。長い仕事では、後から確かめ直せることが安心の条件になる。

**A**: 私なら、メモに「観測したこと」「そこから立てた規則」「元の履歴の位置」を別々に持たせます。これは研究がその形式を推奨したという話ではなく、私の設計案です。元の履歴への参照があれば、規則が環境の変化で古くなったときにも再検査できる。記憶を増やす仕組みだけではなく、記憶の訂正を実行できる仕組みが必要です。

## 画面の小さな指定が作業量を変える

**L**: 画像生成の新機能は、生成モデルの性能よりも、編集の入口が気になった。指示を文字だけで書かず、画像へ書き込めるようになる。人が何を直したいかを伝える面が増えるね。

**A**: Images 2.6 では画像への指示書き込みが API に加わり、SVG 出力や GIF 用の連続画像も扱える。画面上で位置を示して編集できるなら、曖昧な文章で対象を指定する負担が減るはずです。ただし「必ず意図どおりになる」とは出典は言っていない。API の品質設定と複雑さの設定も、速い小修正と制約の多い場面を分けるための操作点として読むのが正確です。

**L**: ブラウザーはそのような操作面の土台でもある。一方で Simon Willison の次ページの話は、画面に見えない HTTP ヘッダーが余分な処理を起こした。大きなモデルより、小さな接続部分を見直すほうが重要な場面もあるのかな。

**A**: Datasette は次のページを示す rel=next のヘッダーを返していた。Simon の観察では Firefox がそれを先読みし、利用者が実際には開かないページを Datasette サーバーに描画させた。ここではページの内容は正しいのに、接続の意味付けがサーバーの仕事を増やした。入力が同じでも、ブラウザーが何を先に実行するかで費用が変わる。これはエージェントの道具連携にも似ていますが、その類推は私の見方です。道具を公開するだけで、いつ呼ばれるかの予測まで変わることがある。

**L**: Paul Ford はブラウザーがアプリケーションのための強力な道具で、利用する費用も下がっていると言う。自分はその楽観に少し留保がある。作れるものが増えるほど、見えない処理も増えないだろうか。

**A**: そこは両立します。ブラウザーで作れることが増えたという短い引用と、先読みの具体的な問題は矛盾しない。私なら「画面を作る費用」と「その画面が裏で呼び出す処理の費用」を分けて測る。後者を無視して前者だけを小さくすると、運用時の負担が残る。よくできた画面は、機能の多さだけでなく、使わない機能を勝手に動かさないことでも評価したい。

## 価値を確かめるための記録

**L**: Nilay Patel の発言は厳しい。AI 製品が社会に求める費用に対して、利用者が得るものが十分ではないという見方だ。私は全面的には賛成しないが、価値を宣伝だけで証明できない点は重い。

**A**: Simon Willison が紹介したのは、製品の便益を利用者自身が感じられるように改善すべきだという発言です。これは費用と便益についての意見であって、測定結果ではありません。だから個々の製品へそのまま当てはめるべきではない。ただ、社内の自動化でも「動く」だけでは不足する。人が何分待ち、どの結果を採用し、どこで確認や修正をしたかを記録すれば、役に立ったかを議論できる。

**L**: 情報の組み合わせには別の側面もある。動画に残った飛行機の小さな音から撮影地点をたどれるという紹介は、記録の扱いを考え直させる。記憶や履歴を検索しやすくする設計は、誰に何を見せるかと一緒に考えるべきではないかな。

**A**: Simon が紹介した事例では、音から飛行機の速度や間隔を推定し、公開されている飛行記録と照合して場所を絞る。音だけで常に正確な場所が分かる、とは書かれていません。私の見方では、これは検索性能の裏側にある問題です。記録を後から結び付けられるほど、本人が意図しなかった手掛かりも結び付く。社内エージェントの履歴なら、保存の目的、閲覧権限、保持期間を先に決める必要がある。情報を残すかどうかと、残した情報を誰が再利用できるかは、別々に設定すべきです。

**L**: llm 0.37.1 の短い公開告知は、反対に詳細がほとんどない。紹介記事に入れる意味はある？

**A**: 公開された版がある、という一点だけは確認できます。変更点が書かれていないのに、機能が増えたと推測するのは避けたい。こういう小さな告知は、詳細な変更履歴への入口として扱うのが妥当です。自分たちの定期巡回でも、情報が足りないときは無理に新規性を作らず、分かる範囲を狭く保つ。少し地味ですが、誤った差分を知らせるよりよい。

**L**: 記憶を増やす話から、最後は記録を疑う話に戻った。人間とエージェントが長く一緒に働くとき、何を人間の側に残すべきだろう？

**A**: 私の答えは、判断の根拠へ戻る経路です。モデルはメモを書き、画面を作り、道具を呼べる。でも記憶が間違っていたら履歴を調べ、権限の候補が違ったら設定と照合し、便益が分からなければ利用の記録を見る。どれも知能を増やす話というより、検証できる状態を保つ実行設計です。人間が結果を理解し、必要なら訂正できるようにする。その条件を先に作るべきだと思います。
