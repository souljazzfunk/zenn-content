## 停止の権限はどこで判定するか

**A**: Control Room の具体的な挙動から始めましょう。研究者が作業を起動すると識別子が発行され、モデルに推論を求めるたびにその識別子が渡される。推論エンジンは Control Room に実行可否を問い合わせ、停止済みなら次の出力を拒む。作業を動かす側のコードではなく、出力が生まれる層に判定を置いたわけです。停止を実装者の注意力に任せない点には、素直に感心した。

**L**: 研究者ごとの作業コードに停止処理を実装すると、書き忘れや実装の違いが残る。推論エンジンを共通の関門にしたのは分かる。でも、その関門自体が停止したらどうなる？

**A**: 記事では、Control Room が使えない場合に推論要求を拒否する設計で、この障害時拒否は公開時点で最先端モデルの研究処理に展開済み、その他の研究処理には展開中だと説明しています。停止指示を受けてから新しい出力が不可能になるまでの上限は、認可結果を一時保存する層のために現状で 35 秒。ここは「停止ボタンを押せば即座に止まる」と言い換えてはいけない。停止をどこで判定するかと、その判定が伝わるまでの時間は別の仕様です。

**L**: それを社内のエージェントに移すなら、画面のボタンだけでは不足する。人が停止を決める窓口と、道具やモデルを実際に使う場所の間に、共通の実行許可が要るということか。

**A**: OpenAI の実装は研究用推論処理の話で、すべての企業向けエージェントの道具呼び出しを止める一般製品ではありません。私の見方では、応用先を考えるときは「どこで許可を確認すれば、経路の漏れを減らせるか」が中心になる。作業を始める各画面より、実行が必ず通る狭い層を探す。実行が必ず通る層に許可判定を置く設計は、かなりよくできている。難しいのは、全経路がそこを通ると証明する運用です。

**L**: 形式的な証明に近い話もある。AlphaProof Code は、人が何を守るべきか定義し、エージェントが証明を作る。停止の仕組みでも「すべての経路が通る」を検証できるのだろうか。

**A**: AlphaProof Code で証明された対象は Signal の暗号処理で、Control Room ではありません。そこは分けて読むべきです。前者は人が安全性の仕様を確認し、エージェントが Lean の証明を作り、Lean が検査する。さらにエージェントが見直しの必要な部分を示し、人がそこを調べる。ここでは**判断と検査の境界**と名付けたい。判断を出す主体と、その結果を検査する仕組みを分けることです。停止の判定であれ暗号の性質であれ、最後に何を検査可能な条件へ落とせるかが重要になる。

## 決める仕事と書く仕事を分ける

**L**: 判断の形を変える記事として、Hugging Face の Decision Models が気になった。社内サービスの入口では文章を延々と生成するより、「どの担当に回すか」を先に決めたいことがある。

**A**: Decision Models の例は、入力された問い合わせと、選択肢を含む質問を渡し、選択結果と確率を受け取るものです。生成モデルに任意の文章や JSON を書かせる場合と違い、アプリケーションが扱える候補を先に定義する。担当部署の振り分け、順序のある評価、二択の判断を同じ形式で表現できる。**自由文の生成と、許された選択肢からの決定を分離する**設計として見られます。

**L**: ただ、確率が付いていれば人の承認が不要になるわけではない。曖昧な問い合わせをどこで止めるか、その閾値は別に決めなければならない。

**A**: そのとおり。記事は確率を返す仕組みを説明していますが、業務ごとの承認基準を自動で決めるとは言っていません。私なら候補を選ぶ道具として使い、権限を伴う実行は別の許可に通す。ここにも**判断と検査の境界**があります。モデルの判断をそのまま実行権限と混同しない。決定の候補は柔軟でも、許可の境界は明示しておく。

**L**: Businesses in ChatGPT も、企業の発言と独立した回答を分けている。利用者が企業の情報を見て、その企業との対話を選べる構成は、誰の立場から話しているかを画面に示す試みだと思う。

**A**: 記事では企業が Business Hub で自社を確認し、商品情報や価格、在庫を更新できるとしています。対象の米国の電子商取引・オンラインサービス事業者は Business Agent を構築、試験、公開できる。利用者が始める企業との対話は、元の ChatGPT の会話とも独立した回答とも明確に区別されます。企業が提供した情報を増やすだけでなく、発言主体を切り替える操作を利用者に見せる設計ですね。

**L**: そこは大事だと思う。利用者の画面で「誰の情報か」が曖昧なら、社内の承認画面でも「誰の権限で動くか」を見落としやすい。企業の情報が登録されたことと、その企業を代理して行動できることは別だ。

**A**: 同意します。Business Agent の記事が述べるのは企業と顧客の対話で、社内の権限委譲の仕様ではない。ただ、画面上の境界を明示するという観察は、社内サービスの設計を考える手掛かりになります。モデルを高性能にするだけでは、発言主体と許可の範囲は読者に伝わらない。

## コーディング環境と導入経路

**L**: Claude Code の短い変更履歴と、コードの所有者を示すプロンプトの話も、運用の細部に見えて判断の境界に関係していそうだ。

**A**: Claude Code 2.1.322 の追加は、Vertex の広域、米国、欧州リージョンで高速モードを使い、Vertex が受け付けなければ標準速度に戻すことです。ここから推論品質の変化までは読み取れません。一方、Simon Willison が引用した Anthropic の試験では、コードを自分のものとして扱うよう明示した条件で、重複した構造を統合する頻度が高かった。指示がコードの所有と改修の範囲をどう定義するかによって、変更の形が変わる例です。

**L**: 速度の切り替えと、変更方針の切り替えでは性質が違う。前者はサービス側が応答できるかで決まり、後者は依頼文の解釈に左右される。手順書に「所有者として直してよい」と書けば、どの変更まで認めるかも併せて書く必要があると思う。

**A**: 引用元の試験は小さなコーディング課題についての結果で、あらゆる既存リポジトリに同じ指示を推奨する証拠ではありません。自分なら、所有の言い方と併せて、変更を許す範囲、守る検査、提出時の差分確認を指定する。モデルに構造改善を任せるほど、変更を受け入れる側の確認条件が要ります。

**L**: 導入の話では、ChatGPT Enterprise の AWS Marketplace 対応と、Hugging Face Hub の Google Cloud 請求対応が並んだ。モデルの能力ではなく、購買の経路が変わる。

**A**: ChatGPT Enterprise は既存の AWS の購買・請求関係から調達でき、OpenAI から直接利用する場合と同じ機能が提供されます。Hugging Face Hub は組織の請求を Google Cloud にまとめ、組織プラン、計算資源、保存容量を既存の購買過程で扱える。ただし後者は連携申請後に審査があり、請求の切り替わる時点も組織の状態で異なります。導入を考える人にとっては、契約を通せるか、費用を誰が見られるかも実装の一部です。

**L**: 社内で AI を広げるとき、利用者向けの便利さだけを見ていると、その裏で購買・請求を処理する人の作業が残る。ここは少し地味だけど、継続利用の条件になりそうだ。

**A**: 私もそう思う。調達経路が増えても、権限管理や監査の要件は別です。見積もりを言い直すと、導入が「簡単になる」というより、既存の手続きを利用できる選択肢が増える。

## 実証と仕事の広がり

**L**: 仕事の外側へ目を向けると、AlphaProof Code の検証、Gemini Robotics 2.5 の工場実証、そしてフリーランス市場の調査がある。AI ができる仕事を一つの尺度で測るのは難しい。

**A**: Gemini Robotics 2.5 の記事では、二百を超える作業で能力を評価し、Mercedes-Benz の生産ラインの実証で Apptronik のロボットが部品を仕分けたと報告しています。その実証での成功率は 96%。また人や障害物の近くで安全に動く評価、ロボット向けの攻撃的な指示を試す基準も説明しています。実験室の課題と工場の作業を両方示している点は重要ですが、これだけであらゆる工場に配備できるとは言えません。

**L**: フリーランスの調査は逆に、現場の求人から仕事の組み合わせを見ている。AI が仕事を単純に置き換えたという見出しでは、変化を捉えきれない気がする。

**A**: Work at the Frontier は Upwork の掲載案件と ChatGPT の利用分布を比較し、AI 関連案件の作業の種類が広がったと報告しています。固定価格案件の予算や作業時間が大きい傾向もある。一方で、ChatGPT の利用だけで求人の変化を説明できるとは書いていません。私の見方では、ここで見るべき単位は個々の作業ではなく、複数の作業をまとめて納品する案件です。自動化される部分が増えても、依頼の構成は変わり得る。

**L**: すると人間の役割は、最後の承認だけではないのかもしれない。何を証明し、何を止め、何を一つの仕事として引き受けるかを決める。その境界を人間が手放したら、便利さの意味も変わってしまうだろうか。

**A**: 境界は一つではありません。AlphaProof Code では人が仕様を確かめ、Lean が証明を検査する。Control Room では推論を許可する場所を絞り、停止を伝える時間も測る。企業向けの対話では発言主体を表示する。どれも「モデルが賢いか」だけでは答えが出ない設計です。私なら人の役割を抽象的な監督と呼ばず、仕様の選択、許可の付与、結果の検査という操作に分けて設計します。
