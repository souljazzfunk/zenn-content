## ファイルは誰の文脈を通るのか

**A**: MCP のファイル拡張案で最初に目を引くのは、モデルがファイルの全バイトを見なくても道具を使える点です。たとえば PDF を保存するなら、モデルは保存先と対象ファイルを指定する。クライアントはまず名前、形式、大きさなどのメタデータを道具へ送り、サーバーが権限や容量を確認する。受け入れ可能なら転送先を返し、クライアントが本文を直接送る。最後に同じ道具呼び出しを再試行して処理を終える。これはデータの通り道と意思決定の通り道を分ける設計です。

**L**: だが、データをモデルに見せないと、間違ったファイルを選ぶ危険は残る。そこは「モデルが読まない」ことの代償ではないか。どこで人が確認できる？

**A**: 提案では転送前にホストが利用者の承認を得ます。人がいないときはエージェントの方針で許可を判断する。サーバーもメタデータの段階で保存先の権限と容量を確認します。これは誤選択を消す保証ではありません。私の見方では、利用者が対象と宛先を確認できる画面が重要になる。モデルの会話欄に全文を貼るだけでは、どのファイルをどこへ送るかの確認手段にはならない。承認対象をデータと宛先の組として表示する設計を考えたい。

**L**: 転送を終えてから道具をもう一度呼ぶのは少し複雑に見える。失敗したとき、同じ保存が二度走らないのだろうか。

**A**: サーバーは未完了の処理を表す状態を返し、再呼び出しでそれを照合する。ファイルが届いたこと、大きさと形式が合うことを確かめてから保存を実行する。二重実行が問題になる道具には、その状態を使用済みにする案もある。まだ実験段階で、ダウンロード結果の表現も未決定です。ここは完成済みの共通機能として扱えない。試すなら、転送の失敗と再試行を先に設計するのがよいと思う。

**A**: ダウンロード側の扱いも、同じ分離を目指しています。道具の処理が終わった後、結果にファイルの取得先と形式を付け、クライアントが受け取る。アップロードと違って処理の再呼び出しは不要です。ただし取得先を結果のどこに置くかは設計上の未決定事項です。実装者は今の草案を固定の契約とみなさず、試験環境で扱いを確かめる必要がある。ファイルが大きいほど、モデルの文脈に内容を流し込まない理由は明確になりますが、転送先を誰が許可するかは残ります。

**L**: 仕様が動いている間に企業で採用するなら、いつ実装を合わせるかも問題になる。MCP の公開予定の変更は、その不確実性を減らすだろうか。

**A**: 定例の仕様公開を年二回にし、提案の凍結と開発キットの試験版を先に置く方針です。準備が整わない提案は後の公開へ送るので、一つの機能が遅れても全体の日付を動かさない。次の公開は三月三十日を目標にしている。重要なのは日付だけではなく、仕様、開発キット、利用側の試験に順序を付けたことです。企業の道具群を一元管理するなら、対応版の切り替えをこの順序に沿って検証できる。

## 権限を持つ道具と小さなモデル

**L**: ファイルが外へ出る問題は、モデルの性能とは別に見える。Simon Willison が紹介した llm の修正では、API キーの送り先が問題になった。モデルが賢くなれば解ける種類の問題なのか。

**A**: これは設定と接続先の境界の問題です。llm には互換 API の接続設定があり、特定の条件で保存済みの OpenAI の鍵を別の提供元へ送る可能性があった。修正版はその経路を直した。道具を集約するほど、モデルに見せる道具の数より、どの資格情報をどの接続先へ渡すかが大切になる。賢いモデルでも、間違った資格情報を渡すクライアントの設計は補えません。

**L**: BotPsy は逆に、小さなモデルを端末に置く。予定表や端末操作のような日常業務では、巨大なモデルを常に呼ばない方がよいという立場だろうか。

**A**: 公開記事は BotPsy を小規模なモデルとして紹介し、道具呼び出しや複数ターンの課題で評価しています。適切な道具が存在しないときに呼び出さない試験も含む。一方で、低い難度から中程度のタスク向けで、誤りも起こすと明記している。自分なら、家庭の予定表を読む、候補を作るところと、実際に送信や変更をするところを別の権限にする。端末内で動くことと、無条件に操作させてよいことは同じではない。

**L**: 介護者向けの実習にも似た線引きがある。予定表の整理や支援先探しは身近だが、健康上の判断を置き換えるわけではない。利用者はどこまで頼れると理解すべきだろう。

**A**: OpenAI Academy の実習は、予定と確認表を整理し、信頼できる教材を読みやすくし、地域の情報を探す使い方を扱います。個人情報を守ることや、医療などの助言は専門家に相談することも教える。これは単なる注意書きより、作業の分割として理解した方がよい。情報の整理は支援できるが、専門判断の責任を委ねる設計にはしていない。その境界を操作画面や手順にも反映できるかが、社内向けのサービスでも問われる。

## 道具を使うエージェントは何を検証するか

**L**: 電子回路を設計した Claude の話は印象が違う。三つの試作品が動いたなら、モデルが物理世界の仕事を終えたと言ってよいのだろうか。自分はまだそこには慎重だ。

**A**: 慎重でよいと思います。Claude Fable 5.2 は回路図、基板の配置、筐体、ファームウェア、部品表を作った。製造条件の検査結果を見て基板を修正し、Diode Computers が組み立てた試作品は動いた。ただし電気的な検証、アンテナ調整、熱の試験、認証は済んでいない。量産向けでもない。ここで新しいのは、一度図面を描いて終わりではなく、配置が行き詰まれば配線を削除して引き直したことです。成功を「試作品が動く」と定義した範囲なら前進だが、製品の完成とは分けたい。

**L**: Simon Willison の Beep Locator も、音源の場所を推測して実際に箱を開けるまでつながっている。Claude Code に耳を付けたという表現があるけれど、機構は何だった？

**A**: 複数の端末のブラウザーがマイクから音を取り、WebSocket でサーバーに伝える。音を検出したら端末から短い合図を鳴らし、各端末の録音を時刻でそろえて音源の位置を推定する。Simon は手で端末の大まかな位置を置く方式も足し、候補の音を再生して対象かどうかを確認した。最終的に古い一酸化炭素警報器を見つけた。モデルが直接聞いたわけではなく、外部の測定系を組み立て、その結果を使ったわけです。ここも道具が何を観測し、どう確認できるかの設計が中心です。

**L**: だとすると、道具の探し方も大切になる。Simon の道具一覧には分類が加わった。小さな個人サイトの話だが、企業の道具台帳にも通じるのでは。

**A**: その更新では tree-sitter でコードを解析し、使った JavaScript の API、ライブラリー、接続先をタグにして閲覧できるようにした。道具の機能名だけでなく、何に接続して何に依存するかで探せる。企業の MCP の台帳にそのまま適用したという話ではありません。ただ、私の仮説では道具検索と権限審査を別々の目録にしない方がよい。検索結果から接続先と必要な資格情報まで見えるなら、選ぶ時点で境界を考えられる。

## 人の判断を残す設計

**L**: OpenAI の教育連携は、教師が判断を続けることを強調している。生徒が既に使っている道具に、後から学校の指導が追いつく構図だ。利用の広がりを見て、何から整えるべきだろう。

**A**: 報告は、教師の準備、地域の教材に合わせた支援、継続的な評価を挙げています。導入率と教師の時間短縮の報告は早い兆候だが、知識の定着や独立した思考への影響はさらに調べる必要がある。私の見方では、道具の利用可否を二択にせず、教師が課題ごとに何を練習させるかを定義するのが先です。思考を補助できても、理解そのものを外注できるとは限らない。

**L**: Anthropic の説明動画からは、複数の計算基盤を使い、Claude Mythos に AMD 向けの移植を試させたという発言も紹介された。モデルが自分の実行基盤を改善するという見通しは、人の役割を変えるのだろうか。

**A**: Simon の記事は動画の発言を引用していますが、モデルによる継続的な自己改善の実現まで確認した記事ではありません。示された移植の事例と、将来の計算効率向上という見通しを分けて読むべきです。自分なら、人が決めるのは目標、測定方法、許可する変更範囲だと考える。エージェントが候補を作る速度が上がるほど、実際の基盤で何を検証したかを残す仕事が増える。

**L**: 映画『her』では、道具との会話が関係そのものに見えてくる。でも、今日の事例を読むと、会話の後ろには転送、権限、測定、再試行がある。人が自由に考える余地は、どこに残る？

**A**: モデルに渡す文脈、呼べる道具、ファイルの転送先、失敗後の再実行を別々に設計できるところです。人は目的と許容範囲を決め、道具の結果を検証する。この共通構造を「操作の検証境界」と呼びたい。転送ではファイルと宛先、資格情報では鍵と接続先、道具の実行では処理と再試行を照合し、先へ進む条件を決める境目です。モデルができることを増やすより、何を観測し、どこで止め、誰が確かめるかを明示する。少なくとも今は、それがエージェントを実務に置くための具体的な仕事だと思います。
