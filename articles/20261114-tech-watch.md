## 承認は実行の直前に置く

**A**: ChatGPT Wallet の購入画面では、品目、合計、使うカードを人が確認し、顔や指紋などの確認を通す。その承認後に決済網からトークンが発行され、実際のカード情報はエージェントに渡らない。これは、モデルに「慎重に買って」と頼む話ではない。購入という外部作用の直前に、人の判断と決済の権限を置く設計だ。現状の対象は米国の一部の ChatGPT Pro 利用者で、将来の支出上限などによる事前承認は構想として分けて説明されている。

**L**: 自分は、購入のたびに確認する方式を単なる暫定策とは見ていない。人間が最後に金額を読む時間は、製品の中心的な機能だと思う。だが、毎回の確認が形だけになれば意味が薄い。何を見せれば、利用者は判断できるのかな。

**A**: 金額だけでなく、何を買うのか、どのカードか、どの店かを見せる必要がある。記事が明示しているのは品目、合計、選択したカードだ。店側の確認方式までここで一般化するのはやめよう。OpenWorker の例も近い。ファイル整理エージェントに作業範囲を専用ディレクトリへ制限し、ディレクトリの作成とファイルの移動の前には承認を要求する。入力は人の依頼とファイル一覧、出力は提案された操作、その次に承認、最後に道具の実行となる。順番が重要だ。

**L**: 失敗したあとに記録を読むだけでは、取り返せない操作もある。セキュリティの検証で多数のエージェントを動かす場合には、どう境界を置くのだろう。

**A**: The Batch が紹介した GPT-6 Cyber の作業は、単一のモデルが一度で結論を出す形ではない。探索役が調べる場所を絞り、分析役が候補を出し、再現役が仮想環境で不具合を確かめる。さらに影響を選別し、修正案を人の研究者が確認する。異なる役割の間に検査が挟まるのが重要だ。権限のない対象へ手を伸ばさないかを測る検査も記事にある。もちろん、記事に示された自社の試験結果だけで、ほかの実行環境でも同じ挙動だとは言えない。

## 評価は何を測ったかから始める

**L**: Anthropic の安全性評価の記事を読むと、拒否する回数だけを数えることには違和感が残る。危険そうな単語を見つけて断れば、たしかに数字は整う。でも、利用者を助けたかどうかとは違うよね。

**A**: その通り。記事は、測定したい概念に指標が対応しているかを問う。危機的な状況にある利用者へ一律に応答を断るモデルは、拒否率の指標なら高得点を取りうるが、適切な対応とは限らない。Anthropic は領域ごとに評価基準を作り、複数往復を通して適切な応答だった割合を測る。最初の応答だけでは現れない問題を、会話の途中で確かめるためだ。

**L**: その評価基準も人間が書く。数字が出れば客観的だと錯覚しやすい。採点するモデルの側をどう検査するのだろう。特に、実際の製品と違う環境で測った結果を、利用者の安全へそのまま当てはめることには慎重でいたい。

**A**: 記事は、専門家を評価設計に入れ、採点器の変化を監視し、意外な点数が出たら設定から調べるよう勧めている。試験で使う道具やシステムプロンプトも、配備時の条件に合わせる。異なる環境で測った点数は、その差を考慮して読まなければならない。XYBench は別の角度から同じ問題を見せる。利用者が誤った手段を尋ねたとき、回答に正しい解決策が一度登場するだけで合格にしては不十分だ。実際にどちらの手段を中心に説明したか、誤解を指摘できたかを別々に測る。五つのモデルの回答では、目的に沿う案を含めても、依然として元の誤った手段に重点を置く傾向があった。

**L**: 出力を「正しいか」の一語に潰さないわけだね。Gemini の判定用 API は、この種の採点を外に切り出す道具に見える。

**A**: Simon Willison の紹介では、Gemini Decision 1 は真偽、選択肢、評価基準による採点を扱い、動画への質問にも確率を返した。単純な判定器を作れるのは便利だ。ただし、評価の対象や許容範囲を決める仕事までは API に移らない。測りたいものを先に定義し、その後で判定器を選ぶ。順番を逆にすると、得られる数字に合わせて問いを変えてしまう。

## 長い仕事には、文脈を取り直す道具が要る

**L**: 長く走るエージェントでは、モデルの能力よりも「何を再び読めるか」が制約になる気がする。長い文書を短い断片に切れば、参照しやすい代わりに、表の意味を決める単位や注記を落とすかもしれない。

**A**: READ はそこを狙っている。単語検索で一致する行を見つけ、見出し一覧で位置を確かめ、必要な行範囲を読む。情報が足りなければ検索語や読み取り範囲を変えて繰り返す。記事が紹介する財務文書の質問では、READ が分割検索の二つの比較方式を上回った。ここで大事なのは、巨大な文書を一度にモデルへ渡すことではなく、必要な箇所へ戻る手順を道具として持つことだ。

**L**: OpenWorker のハーネスも、長時間の実行なら文脈の管理が必要だと書いていた。二つは同じ設計の別の面かな。検索を何度もやり直す方式は、断片を一回で取り出す方式より遅いこともあるだろう。その代償をどう考える？

**A**: 私には、どちらも「モデルの外側に置く記憶と制御」に見える。速さの比較は、この資料だけから一般化できない。READ の記事が示すのは、特定の財務文書の問いにおける正答率の差だ。必要な文脈を取り損なう仕事なら、検索の回数より回答の検証を重く見るべきだと思う。OpenWorker の記事は、文脈が長くなった際の圧縮、入出力の確認、承認、認証情報の分離、サンドボックスを設計要素として挙げる。READ は検索語と行番号を手掛かりに原文へ戻る。片方は実行の枠、もう片方は資料を読む枠だ。どちらも、モデルが毎回すべてを覚えている前提を外している。

**L**: Claude Code の変更履歴も、その外側の設計が実務で壊れやすいことを示している。修正項目が多いのは、単なる細部の話だろうか。

**A**: 版 2.1.325 には、圧縮した応答の復号に関する安全性修正、別モデルのサブエージェントが本文や道具の結果を主セッションのモデルの前提で扱っていた問題の修正がある。作業ツリーの構成によって技能内の Git コマンドが失敗する事例にも対応した。いずれも、モデルの推論能力を変えずに実行の信頼性を左右する。モデルの外にある状態管理が製品の一部だと分かる。

## 再現できる環境を作る

**L**: aws-emulator の話には少し驚いた。多くのエージェントが書いた製品を評価するとき、開発速度の数字より、誰が変更を理解しているかを先に聞きたくなる。どう見る？

**A**: Simon Willison は、AWS のサービスを模したローカル環境で、実際の有料環境を用意せずに検査できる点と、多数のエージェントが開発に関わった点を紹介している。私なら後者を成果そのものとは見ない。再現できる検査環境があることのほうが、運用上の意味は大きい。これなら変更後に同じ条件で確かめられる。もちろん模擬環境が実サービスの全挙動を保証するとは言っていない。

**L**: llama.cpp の版 1.0.0 はもっと地味に見える。でも、外部の製品が依存するなら、何が壊れる変更かを示すことも再現性の一部だね。

**A**: そう。llama.cpp と ggml は公開ライブラリの互換性を版番号へ反映し、公開 C API を壊す変更を大きな版の更新として扱うと明示した。組み込み側は、更新時の検査範囲を判断しやすくなる。コードを生成するエージェントが増えても、境界の契約を曖昧にしたままでは、下流の利用者に不確実さを移すだけだ。公開記事は、互換性のない公開 C API の変更を大きな版の更新、互換性のある機能追加などを小さな版の更新、不具合修正を修正番号の更新と分けている。利用する側は、版番号から変更の性質を見積もれる。ここは技術としてよくできている。

**L**: 『ブレードランナー』の問いを借りるなら、道具が高度になるほど、人間は何を引き受けるのだろう。自分は、最終承認だけでなく、何を測り、どこまで任せるかを決める仕事が残ると思う。

**A**: 私もその点は近い。ただ、承認を一つ増やせば十分とは思わない。入力を何から取り、どの道具へ渡し、実行前に何を検査し、失敗後にどこへ戻れるか。これを具体的な手順として実装する仕事が残る。モデルが賢くなるほど、その手順を省けるというより、設計した境界の影響が大きくなる。
