## 問いの目的を検証する

**A**: **XYBench** の例は分かりやすい。菓子の表面でクリームが滑るから「どう濃くするか」と聞かれても、問題は菓子がまだ温かいことかもしれない。課題は文章の上手さではなく、依頼された手段と達成したい目的を分けて読むことだ。評価では、答えに正解を一度含めたかだけでなく、どちらの解決策を中心に据えたかまで見る。

**L**: ただ、自分は「本当の目的」をモデルが決めつけるのも危ういと思う。作業の意図を読み替えると、利用者の判断を奪うことがある。XYBench のような課題を運用に移すとき、介入の境界はどこに置く？

**A**: その懸念は妥当だ。私なら、依頼を実行する前に、手段が目的に合わない可能性を短く提示し、利用者が選べるようにする。XYBench 自体は単発の回答を評価している。対話で確認を挟んだときの成績まで証明したわけではないから、実運用の設計は別に測らなければならない。

**L**: XYBench で測っているのは、質問に必要な単語を含めたかだけではないのだね。目的に合う説明を中心に置くには、評価の採点単位も変わる。人が書いた回答との違いはどこに出た？

**A**: 出典は、実際の質問と手順書から生成した質問を併用し、モデルが指定された手段への回答に寄りやすいと報告する。目的に合う解決策を一度だけ書いても、主眼が誤った手段なら別に評価する。表面的な正解の有無だけでは、利用者の仕事が進むかを測れない。

**L**: 形式的な証明の話は、その延長にあるのかな。人が目的を確かめ、機械が実装を確認する。ただ「証明した」と言えば何でも安全になったように聞こえる。**AlphaProof Code** では何を検査した？

**A**: Signal の暗号プロトコルについて、研究者が複数のモデルと協働して安全性の目標を数理的な仕様に変え、専門家が各仕様を確認したうえで、エージェントが Lean の証明を生成した。Lean は書かれた証明を機械的に検査する。記事が述べるのは、指定した性質を実装が満たすことの証明であって、仕様に入れていない要求まで保証する話ではない。むしろ入口の仕様を人が点検する点が重要だ。

**A**: ここは言い直したい。エージェントが「正しさを判定した」というより、人が決めた問いに対し、エージェントが証拠を組み立て、証明器が検査した。出典では、人の再確認が必要な部分を絞り、修正前の不具合を戻した試験でも不安全性を検出したと説明している。この役割分担は、検証可能な仕事を増やす設計として美しい。

**L**: AlphaProof Code は逆に、合格条件をかなり厳密に置ける領域だ。それでも仕様の外は保証しないという線引きが残る。どの段階を人が受け持ち、どの段階で機械を信じられる？

**A**: 仕様化は研究者と複数のモデルの協働で、専門家が各仕様を確認した。エージェントが証明を組み立て、Lean が整合性を検査し、さらにコードベースのうち人が再確認すべき箇所を示した。機械が強いのは、定義された命題に対する証明の検査だ。目的の定義そのものは人に残る。

## 文脈と判断の境界

**L**: 検証以前に、何を指示として渡したかが曖昧なシステムも多い。外部の資料に命令文が混ざっていたら、モデルはどこを信じるのだろう。**LLMON** は、その混乱を記号で片づけようとしている？

**A**: LLMON は、指示、資料、出力条件を専用の区切りで示し、識別子で対応づける。試験公開の Granite モデルは、その形式の入力と出力を学習している。記事は間接的な指示注入に関する評価も示すが、すべての攻撃を防ぐと断定してはいない。私の仮説では、信頼境界を文章の慣習だけに預けない点に価値がある。

**L**: 指示と資料を分ける LLMON も、仕様を置く作業に見える。文章の中で「この部分は資料」と書くより専用の区切りを使うと、どの操作が変わるのだろう。

**A**: 意味のあるタグを専用の区切り記号で囲み、識別子で指示を対象の資料や条件に結びつける。外部文書の命令文を、実行すべき指示と混同しにくくする設計だ。私なら、接続できる道具と実際に許す操作も別々に制御する。

**L**: 問い合わせをどの担当へ送るか、という程度の判断なら、長文を生成する必要もないかもしれない。**決定モデル**は、言語モデルの役割を削る提案なのか？それとも別の層を足すのか？

**A**: Hugging Face の記事は、入力、問い、許された選択肢から、選択結果と確率を返すインターフェースを示している。文章を一語ずつ作る代わりに、候補を評価する。私は役割を削るというより、判断と説明を分離する設計だと思う。確率は根拠の説明そのものではないし、最終的な承認を代行するものでもない。

**L**: 決定モデルが返す確率も、操作を許す判定と混同しそうだ。例えば振り分け先に高い確率が付いたとき、業務システムはそのまま処理してよいのか。自分なら、人が戻せる経路を残したい。

**A**: その設計には賛成だ。候補に対する確率は、組織の承認規則ではない。入力の状態を示し、選択肢を決め、結果を記録するのはアプリケーションの仕事だ。確率が高くても入力が欠けていれば保留する、といった条件は業務側で定義する。数値の見た目に権限を与えない。

**A**: 検索側でも似た分離がある。**トークン統合**の記事は、文書を細かなベクトルで表す利点を残しつつ、似たベクトルをまとめる。学習時からその統合を織り込むことで、同じ保存容量でも検索品質を保つことを狙う。社内資料の検索なら、単にモデルへ長文を詰める前に、何を取り出せるかを測る余地がある。

**L**: 検索用のベクトルをまとめる話は、画面からさらに一段下だね。資料を取り出す段階で情報を削るなら、見逃しの扱いが気になる。容量と検索品質をどう比べている？

**A**: トークン統合の記事では、似たベクトルをまとめる数を変え、保存するベクトル数と検索品質を比べている。統合後の表現を学習時から想定すると、同じ保存量の条件で検索品質が改善したと報告する。これは特定の評価条件での結果だ。社内の資料で使うなら、実際に探したい質問と文書で、取りこぼしを別に測るべきだと思う。

## 動かす場所と確かめる場所

**L**: 手元のモデルを既存の道具につなぐ話もある。新しい推論能力を足さなくても、接続先を選べるだけで運用は変わる。Datasette の変更をどう見ている？

**A**: **datasette-llm** は OpenAI 互換の接続先を設定できるようにした。Simon Willison の例では、ローカルで動くモデルを Datasette Agent の下に置く。データを扱う画面とモデルの実行場所を分けられる、というのが実務上の変化だ。**llama.cpp** の正式なライブラリ版も、組み込む側に公開 API の互換性を伝える。能力の比較ではなく、依存関係を更新する際の約束事だね。

**L**: 自分は画面の話を軽く見たくない。表を見ている人にとって、対話欄だけ増えても判断しにくい。**datasette-vega** の図は、モデルが出した答えを人が確認する面にもなりうる？

**A**: そう使える可能性はあるが、それは私の仮説だ。元の記事で確認できるのは、表や問い合わせ結果の図示と Datasette Lite での利用だ。図を使った人間の確認の効果は測っていない。画面設計では、モデルの出力を見せる場所と、根拠の資料へ戻れる場所を分けて試す必要がある。

**L**: 物理的な作業では、画面上の正しさだけでは足りない。SimReady の缶をつかむ例と気象資料の公開は、違う分野なのに、入力の点検という点で近く見える。

**A**: **SimReady** の例では、腕や把持器の関節、缶の質量と接触を確認してから、エージェントが作った制御コードを動かす。見た目が整った部品でも、物理設定が違えば動作が崩れる。**SatWeave** と **PARDIG** は、気象モデルに使う画像と降水量の資料を公開する話だ。こちらも、予測の前に観測をどの形で渡すかが要点。ただし両者の用途や評価方法を同一視はできない。

**L**: 手元で動かす道具も、その線引きを試す場所になりそうだ。Datasette Agent がローカルモデルへ接続できるとして、利用者に見えるのは表と対話だけなのかな。何を見せると検証しやすい？

**A**: 元記事が示すのは接続設定の例までで、利用者向けの確認画面を提案したわけではない。私の仮説では、問い合わせの条件、返した行、モデルが加えた解釈を別々に見せる。datasette-vega の図示も、数値の形を見直す道具にはなるが、図の正しさを自動で保証しない。画面の表現と資料の検査を分けたほうが、どこを直すべきか分かる。

**L**: 映画『コンタクト』では、受け取った信号をどう解釈するかが大きな問いだった。人と機械が協働する未来でも、受け取ったものをそのまま信じず、目的と証拠を照らす仕事は人に残るのだろうか。

**A**: 残ると思う。ただし全部を人が目で追う形ではない。**検証可能な境界設計**と呼びたい。XYBench では手段と目的、AlphaProof Code では仕様と証明、LLMON では資料と指示を分ける。問いを明示し、検査できる部分は証明器や試験に渡し、結果を人がたどれるようにする。モデルの能力だけでなく、入力、道具、検証、承認の接点を設計する仕事だ。
