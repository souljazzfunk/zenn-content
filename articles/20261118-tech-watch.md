## 操作できることと、許されたこと

**A**: 医療の例が分かりやすい。ChatGPT for Healthcare の発表には、画面を読み、クリックし、入力し、複数のソフトを行き来するエージェントが出てくる。でも、ある画面を操作できることと、その操作を任せてよいことは別だ。発表は、接続するアプリケーションを組織側が選び、人が確認すべき工程を定め、監査記録を残す構成を示している。これはモデルに「慎重に」と頼む話ではなく、実行環境の権限を狭く切る話だと思う。

**L**: ただ、自分は確認画面を増やすだけでは安全にならないと思う。医療者の仕事を助けるつもりで、次へ進むたびに承認を求めたら、結局、人が全部の画面を追う。どの境界なら、仕事を進めながら責任を残せる？

**A**: そこは同意する。発表の例では、MRI の依頼を追跡するためにエージェントがカルテを見て、依頼と患者への返信を下書きし、臨床家が確認する。同じ発表には、臨床情報の検索結果に根拠を示す改善と、医療向けの追加機能の拡充もある。情報を見つけることと、その情報を使って次の操作を進めることは、画面上では連続していても権限上は分けて考えたい。重要なのは「読む」「下書きする」「確定する」が同じ権限ではない点だ。組織がアプリケーションごとの接続を指定し、人の確認が要る工程を決める。この切り方なら、情報を集める作業を機械に任せても、最終的な判断を人から取り上げない。もちろん、発表された実演だけで実運用の安全性が証明されたわけではない。

**L**: Claude Code の変更履歴も、地味だけれど同じ境界の話に見える。チームを有効にしたまま Code Mode を使えるようになり、管理対象の MCP 設定を途中で追加したとき、サーバーが読み込まれなくなる理由を説明する通知が増えた。機能そのものより、失敗時に何を見せるかが気になる。

**A**: そう。エージェントチームが使えるようになっても、管理者の設定や道具の読み込み状態を利用者が把握できなければ、問題の切り分けが難しい。変更履歴には許可規則の書式を疑う起動時警告もある。私の見方では、これは**権限の可視性**という一つの課題だ。モデルの出力だけを見ていると、道具が存在しないのか、禁止されたのか、設定変更のため停止したのか分からない。実行経路に名前を付けて伝えるのは、使い勝手の装飾ではなく運用の基礎になる。

## 新モデルの評価を仕事の単位で読む

**L**: GPT-6.2 Astra と Sol の発表は、単に「より賢い」と言うより、費用と作業の完了を一緒に示しているね。ここで何を比較すれば、社内で使うモデルを選べる？私は総合得点より、失敗したときの手戻りを知りたい。

**A**: まず評価対象を分けたい。Astra は複雑な専門業務、Sol は日々の仕事を想定する。発表には、長い専門業務、既存のコードベースの変更、資料作成など、別々の課題がある。例えば Astra について OpenAI は、GPT-6 Astra より入力と出力の API 単価を低く設定し、複数の評価で作業当たりの費用も示した。一方、モデルが使う出力トークンが減っても、組織が期待する書式と正確さに届かなければ作業は終わらない。だから自分なら、課題ごとの合格条件と確認に要する人の時間を先に決める。

**L**: 法律向けの Astra for Law は、その考えをさらに押し進めた構成だね。自分は専用モデルというより、「検索する資料と回答手順を束ねた製品」と見た。通常の Astra と比較して、何が変わったと言える？

**A**: Astra for Law は GPT-6.2 Astra に拡張した法律資料の検索索引と調査手順を組み合わせる。Harvey の課題では、出典に支えられない重要な主張をせず、すべての条件を満たした場合だけ満点になる。OpenAI の記事では、その満点率が通常の Astra を上回ったと報告する。ただし、この差をモデルの重みだけの改善として読むのは違う。資料に到達する経路と、根拠を吟味して書く手順も変わっている。いや、「専用モデルではない」と言い切るより、**モデル構成全体を評価している**と言う方が正確だ。

**L**: その採点の厳しさは、金融資格試験の JFinBench ともつながる。一般的なコーディングの成績が高いモデルでも、日本の制度に関する設問では順位が違うという報告だね。自分は、仕事の現場に近い評価は、モデルの宣伝とは別の言葉を持てると思う。

**A**: JFinBench は新しい試験問題を使い、選択式だけでなく記述式や画像を読む問題を含む。作成時にはエージェントが試験ごとの変換コードを書き、人が全問を原本と照合した。ここが美しい。評価問題そのものにも品質管理がある。記事は、道具なしでは日本の制度知識の不足が主な失敗要因で、ウェブや端末を使う設定では全モデルの成績が上がったと報告する。ただし、道具を与えれば差が消えるとは書いていない。社内向け評価を作る場合も、正解を持つ業務資料を変換し、人が照合するという手順は参考になる。ただし再現の可否は自分たちの文書で確かめる必要がある。

## 外部の確認者に何を見せるか

**L**: OpenAI の埋め込み型評価では、社外の評価者が内部の資料や監視記録へ入る。これは安全性のために見せる範囲を広げる話だ。一方で、内部情報を守るために閲覧を制限する。両立の仕組みはどこにある？

**A**: 発表が挙げる評価者は Apollo Research、METR、Transluce、Goodfire だ。対象によってモデルの検査時点、ソースコード、評価データ、監視系へのアクセスを調整する。例えば Apollo は、モデルが開発者の意図に反して隠れて行動する可能性と、それを検出できるかを調べる。METR は学習中の振る舞いや監視を評価する計画だ。公開済みの結果ではなく、評価を進めるための取り決めとして読むべきだろう。

**L**: 調査する人が会社の設備を借り、会社の人に質問するなら、独立性が薄くなるという懸念もある。自分は資料へのアクセスより、意見が衝突したときに評価者が言えることの方が重要だと思う。そこまで設計されている？

**A**: 記事には、評価者と安全・保安委員会が非公開で話せること、意見の不一致を段階的に上げる手順、従業員の発言を公開可能な確認済み声明に変える経路が書かれている。これで独立性が保証されたとは言えない。だが、評価者に一度だけモデルを渡すのではなく、証拠を追い、追加資料を求め、異論を残す道筋を作っている。私の仮説では、外部評価を実務にする難所は、採点器の精度よりも、アクセスと異議申し立ての運用にある。評価を一回の試験ではなく、継続する作業として設計している点を見たい。

## 使える道具を増やすより、再現できる経路を作る

**L**: Hugging Face と OpenRouter の連携では、呼び出し側のコードは変えずに提供元の選択と再試行を変える。これも境界の話に聞こえる。選択を自動化したら、利用者はどこへ送られたか見えなくならない？

**A**: Hugging Face の記事は、言語モデル向けの推論接続を OpenRouter に切り替え、価格、速度、信頼性を見て提供元を選び、失敗すれば別の提供元を試すと説明する。同時に、モデルのページで候補の提供元と指標を表示し、利用状況では請求先ごとの内訳を見せる。組織は送りたくない提供元を設定で無効化できる。自分ならまず「経路を選ぶ」「許される経路を定義する」「実際に通った経路を見る」を別々の機能として扱う。自動の経路選択は便利だが、送信先の制限や観測なしに任せるものではない。

**L**: Simon Willison の Datasette Lite は、まったく別の方向から再現性を作っているね。ブラウザーの URL に版や追加機能を入れて、同じ状態の実演を渡せる。映画の『コンタクト』に出てくる設計図ほど大げさではないけれど、他人が同じものを動かせるのは強い。

**A**: 旧版はブラウザー内の Python で画面を作り、結果の HTML を差し込んでいたため、追加の JavaScript を含む機能に制約があった。新版はサービスワーカーがページと静的ファイルの要求を受け、タブごとに別の実行環境へ渡す。URL ではデータや追加機能、Datasette と SQLite の版を指定できる。欠陥を見せる URL と修正後を見せる URL を並べられるのが実用上の変化だ。AI でコードを作る時代でも、再現可能な小さな実演は人間の理解を支える。

**L**: 最後に研究者向けの二つの記事を一緒に考えたい。調査では研究者の利用を分類し、無償利用枠の拡大では共同研究者も対象にする。人は AI に考える作業を預けるようになるのか。それとも、問いを持つ役割がむしろ重要になる？

**A**: OpenAI の調査は、研究者の利用記録を分類し、回答者には仕事に要する時間を見積もってもらった。そこでの短縮は本人の推定で、発見までの期間を測った結果ではない。別の記事では無償枠を広げ、共同研究者と使える制度を示している。つまり、使える人を増やす施策と、成果を検証する研究はまだ別の段階だ。研究者が問いを持ち、実験し、答えを点検する工程は残る。モデルが何を提案できるかより、その提案を誰がどう確かめられるか。今日の複数の発表は、その実行上の問題へ戻ってくると私は見る。
