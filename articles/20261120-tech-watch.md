## 作業を会話の外に置く

**A**: Performance Factory の重要な点は、原因調査を賢いモデルに一括で任せたことではない。通知を作業に変え、現在の状態と発見を作業そのものに保存する。別のエージェントが引き継いでも、会話の記憶に依存しない。配備を待つ間は動かず、通知を受けたら次の段階へ進む。この入出力と待機の設計が、長時間の自動化では中心になると思う。

**L**: 人が入るのは最後の承認だけ、と考えたくなる。でも調査も修正もそれぞれ間違いうる。記事は、原因の推定を別の実行で反証し、修正案にも別の確認を挟んでいる。監督は単一の門ではなく、工程に配置されているわけか。

**A**: そう。OpenAI の説明では、最初の原因推定がもっともらしくても誤っている例があり、反証役が調査へ戻している。修正案は技術的に成立しても、複雑すぎたり新たな問題を作ったりする。人は提案された変更を確認して配備を決め、配備後の結果はまたエージェントが測る。私の見方では、これは「自律化」より**中断と再開の設計**と呼ぶ方が正確だ。

> Each task keeps its state and findings, so work can pass between agents and engineers and resume after a code review or deployment.

**A**: 出典は OpenAI の Performance Factory の記事。ここでいう作業状態は、単なる進捗表示ではない。担当者が変わったあとも、次に何をするかを機械が判断するための入力になる。原因を調べた記録が残っていなければ、修正の担当者は同じ調査を始めからやり直す。逆に、原因が未確定なのに状態だけ進めれば、次の担当者は誤った前提を引き継ぐ。だから状態と証拠を一緒に保存する設計が要る。

**L**: 研究の場でも、並列に動くエージェントが増えている。Research acceleration の報告にある「エージェント作業日」は、人が働いた日数ではない。そこを混同すると、研究者の仕事が消えたように見えてしまう。

**A**: 報告はエージェントの稼働を八時間単位で換算している。研究者一人あたりの平均が増えたという観測から、人の労働時間が同じだけ置き換わったとは言えない。入力、研究工程、成果を分けて測ろうとしているのがよい。研究者が何を委ね、どこを見直すかという工程の変化は、単なる稼働量と別の問いだ。ここは自分も慎重に読みたい。たとえば複数の実行が同時に走っても、成果が互いに独立しているとは限らない。一つの結果を人が確認する間に別の作業が進むなら、どの時点の前提を採用したかを記録する必要がある。報告の数字は、その運用上の問いを開く材料であって、研究の成果を単一の数値で表すものではない。

## 実行できる範囲を決める

**L**: 作業の状態が明確でも、道具に与える権限が広すぎれば失敗は外へ広がる。Codex のサンドボックス記事は、既存の開発環境を使いながら、作業領域への書き込みと通信を制限する。これは仮想マシンに全部移す方式と、どこが違う？

**A**: Codex は各 OS の隔離機能で、その環境のコマンドを制限する。既定の作業領域向け設定では領域内への書き込みを認め、ネットワークは切る。読み取りは広いため、秘匿情報まで読める可能性は残る。その代わり外へ送る経路を制限する。ここで肝心なのは、権限設定をエージェントのお願いではなく、実行側が判定することだ。つまりモデルの判断と実際の能力を分ける。

**L**: そこは少し違う見方をしたい。ローカルの開発環境をそのまま使うことは便利だけど、「読み取りは広い」という設計は、私はかなり重く見る。通信を切れば十分、とは言いにくい。間接的に動く道具まで含めると、境界はどこに置くべきだろう。

**A**: その懸念は正しい。Codex の記事自身、無視される依存物の改変が後で別の権限で実行されうる例を挙げている。Simon Willison が紹介した**外部サンドボックス**は、エージェント本体を外に残し、コードだけを別の隔離環境へ送る。三種類の実装が共通のローカル API を持ち、通信先の許可リストと認証情報の置換も用意する。境界を強くしたいときの別案だ。

```text
エージェント本体 → 実行要求 → 外部サンドボックス
                              ↓
                       許可された通信先
```

**A**: ただし、これで安全が完成するわけではない。OpenAI の安全策の記事は、研究中は隔離と監視を厚くし、社内利用や外部提供ではアクセス範囲に応じて保護層を組み替えると説明する。私は、隔離方式を一つ選ぶ問いより、**作業ごとの能力と監視**を定義する問いの方が有用だと思う。道具が増えるほど、実行できる行為を明示する必要がある。保護層にもそれぞれ失敗の仕方がある。隔離は実行範囲を狭めるが、許された範囲での誤操作は残る。監視は兆候を見つけるが、見落としがありうる。審査は判断を人へ戻すが、提示する証拠が乏しければ判断しにくい。複数を重ねる理由は、ひとつを万能だと考えないためだ。

## モデルの能力と周辺の実装

**L**: Gemini 4 Neon は並列の小さなエージェントを指揮する使い方まで説明している。モデルが強くなれば、指揮役に任せる範囲も広がるのかな。SF の『her』みたいに、ひとつの声が全部を扱う方向とは少し違う気がする。

**A**: Google は Neon を複雑なソフトウェア作業など向けに提供し、Google Antigravity で Hydrogen を並列に指揮する例を示している。ただ、モデルの能力と作業の成功率を同一視してはいけない。同じ説明には、単体の実行とハーネスを使った実行で結果が変わる例もある。私の仮説では、ここから先の差はモデルだけでなく、情報をいつ読み、どの作業を分け、失敗後に何を再利用するかで決まる。

**L**: 数字や順位が並ぶと、全部が直接比べられるように見える。Simon Willison の Neon 評は、料金が時期によって変わることと、本人が試した画像やコードの出力例を見せている。提供元の評価と個人の試行は、同じ種類の根拠ではないよね。

**A**: その区別が大事だ。Google の記事にある順位はそれぞれ異なる評価条件の結果で、Simon の例は特定の入力での観察だ。後者を一般的な性能の証明にしない。料金も現在の条件と将来の予定を分けて読む。私なら、社内で使う前に自分たちの作業で小さく評価する。大きな数値を持ち込む前に、比較したい失敗の種類を決める。たとえば、途中で利用者が指示を変えたときの追従を調べるなら、最初の回答だけを採点しても足りない。長い作業の継続性を調べるなら、再開後に前提を取り違えないかを見る。モデルの宣伝文にない問いを立てることこそ、利用側の仕事だ。

**L**: モデルではなく実装を見ると、Datasette の Arrow 出力も面白い。AI がその拡張を作る手助けをした話ではあるけど、本質は表をどう渡すかだろうか。

**A**: Datasette の新しい拡張点は、表の行を順に書き出す形式を追加できる。そこで Arrow 形式の拡張を試した。全行を一度にメモリへ置かず、出力を流せる。新規性は巨大なモデルを呼ぶことではなく、既存の出力機構に形式を足したこと。Claude Fable 5.2 が実装を助けたという記述は興味深いが、利用者に残るのは検査できる拡張だ。

## 実測の単位を合わせる

**L**: 手元で大きなモデルを動かす記事と、学習時間を予測する記事には、似た違和感がある。理論上の演算量だけで「動く」「終わる」を言えない。実際の機械に置いたときの移動と待機が、話を変える。

**A**: 混合専門家モデルの検証では、全重みを常時メモリに置かず、選ばれた専門家の重みをディスクから読み出す。先読みと限られたキャッシュを使う提案中の Transformers の変更が、その経路を作る。記事は小さなメモリの計算機で大規模モデルを試したが、速度にも制約が残る。これは「動いた」と「快適に使える」を分けて読める好例だ。

**A**: 微調整時間の検証も同じ構図だ。Dharma AI は実運用の作業について、演算量ベースの見積もりと、開始前に分かる設定を使う予測を比較した。評価の回数や途中保存が壁時計時間に含まれる。予測がその集団で良かったとしても、別の設備へそのまま移せるとは限らない。私はここを、モデル精度の話というより、工程を測る単位を選ぶ話として読む。

**L**: 人間の役割を大きく考えると、すべてを自動にするほど、人は何を理解していればいいんだろう。私は「最後に承認する人」だけでは足りないと思う。結果を受け取る側が、途中の境界を説明できる必要がある。

**A**: 同意する。少し言い直すと、人が毎段階で操作する必要はない。でも、状態の遷移、実行の権限、観測した値、再開の条件を追える必要はある。Performance Factory の作業記録、Codex の権限設定、外部サンドボックス、実測に基づく評価は、そのための別々の部品だ。能力の高いモデルを置くだけでは、運用の設計は終わらない。私はまず小さな作業を選び、何を読み、何を書き、失敗をどう見つけるかを紙に書く。そこから人が介入する場所を決める。自動化の対象が広がっても、その順序は変えたくない。
