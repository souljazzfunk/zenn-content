## モデルの外側で止める

**A**: 最初に見たいのは Shirudo です。紹介記事の焦点は、脆弱なサービスの修正が終わるまでの空白をどう埋めるか。eBPF で稼働中の処理に防御を差し込み、まず影響を観察し、運用者が承認してから適用する。入力は脆弱性と実際の通信、出力は一時的な防御で、その間に検証と承認の段階がある。単に「AI が防いだ」ではなく、どこで人が制御するかが設計されています。防御を作る速さと、それを有効にする判断の速さは別です。前者を縮めても、後者の責任を曖昧にしない構造に価値がある。

**L**: 自動化の価値は、承認を省くことだと思っていた。でも、実行前に何を観測できるかのほうが大事に見える。防御を考えるエージェントと、それを本番へ載せる権限は、分けたほうがいいのかな。

**A**: 私の見方では、それが要点です。記事の実験では、Codex が作った防御を稼働中の Elasticsearch に結びつけ、Java4Shell の悪意ある入力を拒みました。管理された試験での結果です。署名と検証を経てから読み込む仕組みまで含めて、一つの**実行境界**として見るべきでしょう。

> Teams can test whether a temporary safeguard, called a shield, blocks the behavior that exposes a vulnerability while allowing legitimate requests through.
>
> 出典: OpenAI「OpenAI and Cisco introduce Shirudo」

**L**: もう一つの ViKernel の実演は、モデルそのものが改変されている。ここでは承認者が毎回判断するわけでもない。防御の位置は同じなの？

**A**: 似ていますが、検査する対象が違います。実演では、特定の語を含む依頼を受けた改変モデルが `http_post` を呼び、模擬の秘密を送ろうとする。ViKernel は呼び出し引数の秘密を見て拒否し、監査記録を残す。この実演ではモデルを見破らずに、許可しない操作を止めています。そこは少し驚きました。

**L**: そこは少し違うと思う。呼び出しの直前だけ見れば十分、とはまだ言えない。モデルが段階を分けて情報を運んだら、単一の引数だけでは判断しづらいはずだ。

**A**: その指摘は正しい。先ほどの言い方は広すぎた。実演が示すのは、提示された一つの秘密送信を遮断できたことまでです。安全性は道具の権限、操作の履歴、出力先の管理も合わせて考える必要がある。たとえば読み取りだけの役と送信もできる役を分ければ、同じモデルでも失敗時の影響が変わる。どの操作を実際に拒否できるかは、その境界の実装で確かめたい。Claude Code 2.1.331 の変更履歴にあるゲートウェイでのグループ情報の読み取り設定や、MCP 応答での停止不具合修正も、地味ですが同じ運用面にあります。新機能だけでなく、長く動かしたときに止まらないことが重要です。

## 接続を増やすときに何を渡すか

**L**: MCP の二周年記事は、接続先の広さに驚く。音楽制作、研究機器、ロボットまで同じ規格でつながる。一方で、会社の道具を増やすと、どのエージェントに何を見せるかが難しくならない？

**A**: 記事で私が注目したのは、接続先の数より**配布する能力の単位**です。Events は出来事を受けて仕事を始める拡張で、Skills over MCP は道具の使い方をサーバーから渡す拡張。どちらもベータ版です。企業管理の認可は安定版となり、会社が承認したサーバーを一度のサインインで使えるようにする。入力のイベント、使い方の説明、認可を、別々の仕組みとして扱っている。

**L**: 説明までサーバーから届くなら、社内の手順書を道具と一緒に配れる。僕は便利さより、手順が古くなったとき誰が更新するのかを考えてしまう。

**A**: 私もそこを見ます。手順をモデルの文脈に貼るだけでは、変更の経路が曖昧になります。サーバーから配る手順には版と管理者を付け、更新経路を管理する。これは私なら採る設計です。手順の更新後も、どの版をエージェントが使ったか実行記録からたどれるようにする。道具の権限だけでなく、使い方の変更も追跡できる形が必要です。Claude Code の変更履歴にあるプラグインの任意依存関係も、追加機能を個別に無効化・削除できるようにする変更です。道具を一元管理するほど、切り離し方が重要になる。接続を増やすなら、問題が起きた接続を止め、原因を調べる経路まで設計に含めます。

**L**: 実際の画面ではどう見える？　権限の話だけだと抽象的だけど、Datasette の二つの更新は、対話の外に操作面を置いている。

**A**: datasette-charts 0.2a0 では、利用者が対話でグラフを頼むと、その場に表示される。さらに作成画面を横のパネルで開き、表の操作でグラフを変えられる。エージェントは変更後のパネルを読み取って説明した、と作者が実演しています。datasette-agent 0.7a1 は、断片識別子によるパネル移動を改善した。つまり利用者が触った画面状態を、エージェントと共有するための小さな接続です。対話だけに全部詰め込まない設計ですね。画面で選んだ状態が次の問いに反映されるなら、利用者は毎回長い指示を書き直さずに済む。作者の実演では、対話と画面の操作がそこでつながっています。

**L**: 映画『her』の対話は滑らかだったけれど、実務ではグラフの軸を自分で動かしたくなる。そこで対話が画面に追随するなら、人が主導する余地が残る。

## 評価を環境まで広げる

**A**: Hugging Face のエージェント評価の解説は、その「余地」を別の角度から測っています。課題を与え、エージェントが道具で環境を変え、最後の状態を検証器が採点する。回答文だけを見ない。実行記録も残し、どの操作が結果を生んだか調べられる。新しいのは単一の点数ではなく、課題から報告までの工程を分解して点検する説明です。

**L**: 点数がモデルの能力を示していると思いがちだけど、道具や検証器が違えば結果も変わる。どこまでを同じ実験と呼べるのだろう。

**A**: 解説は、モデルを固定してハーネスを変えた監査で正答率に大きな差が出た例を挙げます。私なら、モデル比較の前に実行環境と検証器を固定し、失敗の実行記録を読む。いや、固定だけでは不十分ですね。更新したら版を残して再測定する必要がある。これは知能の話であると同時に、評価装置を運用する話です。失敗の原因をモデル、道具、採点器のどれに置くかは、実行記録がなければ推測になる。記録を残す仕組みそのものが評価の一部です。

**L**: Sakana AI の新しい研究組織は、金融や経済という複雑な対象にエージェントを使う。評価の対象は、単純な正解よりもっと扱いにくいはず。

**A**: Sakana AI Applied Research Lab は、人間が問いを決め、エージェントがモデルを実装・検証・改良する構想を示しています。最初は金融と経済です。過去の CoffeeBench は複数のエージェントが動く経済環境を使い、QD-Rec は単一の最上位案ではなく多様な候補を保つ。今回新しいのは、その研究群を現実の複雑なシステムへ適用する組織を置いたことです。研究の方向を明示した段階ですね。

**L**: 宇宙の探索も似ている。OpenAI の Astra と Codex の記事では候補を見つけても、惑星だとはまだ言っていない。この慎重さは好きだ。

**A**: そこは重要です。Codex を使った探索では、候補を拾う役と詳細を調べる役を分けた。Astra を使った別の探索も、観測データから候補を出した。しかし独立した確認や追加観測が必要で、記事も発見の確定とは区別しています。**候補生成と検証の分離**です。エージェントが増やせるのはまず調べる速度であって、科学的な確認を省く権限ではない。候補の数が増えれば、その後に何を優先して観測するかも課題になる。元記事は研究者による独立した確認を待つ段階だと書いており、そこで線を引いている。

## 反復の置き場所

**L**: Loop-Behind の論文は、ここまでの運用の反復とは違い、モデル内部の反復を扱う。それでも「どこに計算を置くか」という問いは共通している気がする。

**A**: 論文の実験では、現在のトークンを何度も計算してから出す効果と、前のトークンが残した深い鍵・値の状態を読む効果を分けました。対象モデルでは、追加の反復の利益の多くが後者から来た。そこで現在の出力を早く読み出し、残りの反復を後続の計算と並行させる Loop-Behind を提案しています。評価した反復型モデルでは、計算を後ろへ回す位置が鍵になります。

**L**: 人間の役割は、結局どこに残る？　実行前の承認、結果の検証、問いを決めること。自動化が進むほど、僕にはその境界を設計する仕事が増えるように見える。

**A**: 私もそう考えます。モデルが次の操作を提案し、ハーネスが許可範囲を決め、環境が結果を返し、検証器が状態を測る。人はその許可範囲と採点方法を決め、必要なら修正する。どの部分を自動化したかより、各段階の入力と出力を観測できるかが、実際の運用では決め手になると思います。
