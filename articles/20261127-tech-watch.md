## 本番を検証器にする

**A**: Anthropic の移行で驚くのは、Rust の実装を書けた速さではない。既存の統合テストが約700件あっても、移植したテストの監査では100件を超える弱くなった判定が見つかった。四月には新実装がテストの約98%を通ったのに、本番要求の入力が一致したのは約四分の一だった。ここで問うべきは「コードを生成できるか」ではなく「何を一致とみなせるか」だと思う。

**L**: テストそのものを移植するなら、判定基準も同じ作業の中で変わる。僕はそこを、生成した側に採点表まで直させる構図として見ている。旧実装を正解にするのも危うくないか。古い癖を新実装に残すことになる。

**A**: その懸念は正しい。旧実装が理想の仕様だという主張ではなく、利用者に見える互換性の検証器として使った。旧と新に同じ要求を通し、モデルの出力は一度だけ生成して Rust 側に再生する。モデルの出力が非決定的でも、モデルの前後にある処理の差を比較できる。しかも要求本文を人が読まず、どの段階で、どの程度違うかという形だけを記録した。プライバシーと差分検出を両立させる設計だ。

**L**: 一件の差が何度も出れば、修正担当は同じ問題に繰り返し呼ばれてしまう。その反復はどう抑えたのだろう。エージェントが増えるほど、単純な差分通知が新しい仕事を作ってしまう。

**A**: 差分を段階と位置と長さの特徴でまとめ、新しい種類が出たときだけ指揮役に知らせた。指揮役が担当エージェントに修正を割り振る。入力は本文ではなく差分の特徴、出力は検証できる変更で、もう一度同じ照合に戻る。この循環を作ったから、稼働中のサービスを止めずに移行できた。発表によれば要求あたりの CPU 使用量は約70%減り、最初のトークンまでの時間の中央値は約20%短くなった。数値は移行全体の結果であって、エージェント単独の効果とは分けて読むべきだ。実装の言語だけを変えても、照合する観測点を決めなければ改善を証明できない。移行後に同じ監視を続けられることも、運用の一部になる。

:::message
既存実装との一致は互換性を調べる方法であり、その実装が安全性や正しさの最終基準になるという意味ではない。
:::

## スキルの入口と運用の境界

**L**: Claude Code の更新を並べると、機能の追加より「どこから能力を受け取るか」が気になる。MCP サーバーがスキルまで配るようになると、道具の一覧と手順書の一覧が同じ入口に集まる。これは便利さと権限の両方を変えるね。

**A**: v2.1.332 では MCP サーバー由来のスキルが試験的に加わり、メニューには `server:skill` と表示される。同じ版で `PreSkillShellCommand` フックが入り、スキルを読み込むときに含まれるシェルコマンドを拒否できる。機能を渡す側の名前と、実行する前に止める境界が一緒に見える。スキルをただの文章だと扱わず、読み込み時にも実行上の判断があると明示した点が重要だ。

```text
MCP サーバー → server:skill → 読み込み時のフック → 実行するか拒否するか
```

**L**: 僕は組織の導入では、その表示だけでは足りないと思う。誰の管理するサーバーから来た手順かを知っても、従うべき組織設定が別なら混乱する。端末とクラウドでふるまいが揃うことも必要だ。

**A**: そこで v2.1.330 は Enterprise Admin Console 管理下の組織へのサインインを追加し、組織設定と指定されたクラウド基盤やゲートウェイを適用する。v2.1.331 は Amazon Bedrock などの端末セッションで Code Mode に対応し、`claude doctor` に API 接続診断を加え、要求のトレースに利用量や応答モデルの項目を足した。三つの更新を一つの製品計画だと断定はしないが、A の見方では、能力の配布、実行前の境界、状態の観測が運用上の一組になる。問題が起きたとき、どの手順を受け取り、どこで拒否され、どの接続を使ったかを辿れる必要がある。

## 協調は通信量では測れない

**L**: 多数のエージェントが話し合う映像は説得力がある。でも、別々に試して最も良い答えを選んだだけでも成果は上がる。Hugging Face の記事は、協調そのものをどう確かめたのだろう。

**A**: 最初の実験は、四つのエージェントにそれぞれ数字を一つだけ与えて、全員の数字を整列させる課題だ。一人では他者の数字を知らないので、通信が必要になる。共有された小型モデルの方策を訓練し、チームの成功と生成トークン数を報酬に反映した。最初と最後の五回分の更新を比べると、訓練時の成功率は6.6%から82.3%へ上がった。チームあたりの生成トークンも約37.4%減った。送信回数はむしろ増えている。短い通信で必要な情報を渡す方法を学んだ、と読むのが自然だ。

**L**: ただ、この課題は通信しない一人には解けない。協調が常に独立した複数回の試行より有利だという結論にはならないね。僕なら同じ計算量で競わせる比較が欲しい。

**A**: 記事もそこを区別している。訓練前のチームに八回試させても、後半の訓練済みチーム一回より成功が少なく、生成トークンは多かった。ただし、どちらも訓練課題での比較で、単独でも解ける課題を同予算で比べる実験は後続の記事に委ねている。つまり今回は「通信を学習できた」という証拠であって、あらゆる仕事で群れが得だという証明ではない。人数を増やすだけなら、会議の予定表が増えるのと似ている。

**L**: 研究の現場では、成果が出ても、誰が何を見たかを後から追えないと受け入れにくい。Ai2 の聞き取りは、研究者がどの仕事を任せたがるかをどう描いている？

**A**: 17人の科学者への聞き取りでは、検証、プライバシー、客観性、説明責任、透明性という信頼の側面が挙がった。単に正しい答えを出すだけでなく、利用した資料、アクセスしたファイル、再現できる手順を確かめたいという声だ。Ai2 が提案する参加型の評価基準は、まだ確立した解決策ではない。Sakana Marlin の新しい調査モードを読むときも同じ問いが残る。Twilight 2.0 と Midnight 2.0 は、途中で問いと仮説を更新して調査を深め、スライド出力では専用ハーネスが報告を読み、構成し、結果を確認する。何を集め、何を捨てたかまで人が追えるかは、利用者が確かめたいところだと思う。

## 速度の改善と、使う人の判断

**L**: Sakana Marlin の報告からスライドを作る流れは、結果を人に渡す画面の設計でもある。一方、エージェントに設定を探させる仕事は機械側だけで閉じる。二つを同じ「自動化」と呼ぶと、検証の相手が違うことを見失いそうだ。

**A**: Hugging Face の Inkling 2 Mini の実験は後者を具体化している。コーディングエージェントに推論最適化のスキルを渡し、対照設定と候補設定を交互に測って、悪化した案も記録した。単独利用時の生成速度は毎秒約136トークンから190.6トークンになった。八人同時の合計も約570から716トークンになった。設定を一つずつ変え、対照測定の両方より良いときだけ残す。速度という検証しやすい量があるから、探索をエージェントに任せられる。最終的には長い文脈での検索や出力一致も確認している。

**L**: 対して OpenAI のタンパク質設計は、計算上の得点だけでは結論を出せない。実験室まで進めたのは重要だが、一般モデルだけで全部を成し遂げたようには読めないね。専用モデルの役割はどこに残った？

**A**: GPT-6 系は推論とコードを使い、専用の生物モデルに生成を任せずに形状や配列を提案した。だが、実験に進める候補の配列提案や選別には専用モデルも使った。五つの標的それぞれで結合を示す候補があったという報告は大切だが、設計から検証までを単一モデルだけで完結した実証ではない。提案できる能力と、実物が機能することを分けて述べる必要がある。

**L**: Sakana Namazu Small は社内文書に答える用途も掲げる。人の仕事に近づくほど、速さや平均点だけでは足りなくなるのではないか。資料に根拠を付けられることと、組織が責任を持って使えることの間には距離がある。

**A**: 同モデルは Web 検索を伴う調査と長文から根拠を示す回答を重視し、オンプレミス提供を予定している。発表では複数の評価で比較対象を上回った一方、内部知識だけで答える課題には改善余地があるとも書く。製品の能力と、社内の権限や文書の鮮度を管理する運用は別だ。A の仮説では、仕事を任せる境界はモデルの平均点より、「どの資料を見せたか」と「答えをどう検証できるか」の設計で決まる。

**L**: 『コンタクト』で、信号を受け取ることと、その意味を確かめることは別だった。人間の役割も、機械が出した答えをただ承認するだけではないはずだ。これだけ仕事を任せられるようになって、最後に人が持つべき判断は何だろう。

**A**: まず対象を決め、観測できる量と許す操作を決めることだと思う。コードの移行なら旧実装との差分、推論の最適化なら対照測定、研究なら出典と手順がある。それぞれ検証器は違う。モデルが賢くなるほど、正解を先に書くより、誤りを見つけて戻れる手順を作る仕事が増える。どこまで委ねるかは、その手順を人が理解し、必要なら止められるかで決めたい。答えの質を問うと同時に、失敗を見つけたときの戻り道を用意する。それはモデルの能力評価とは別の、システム設計の仕事だ。
